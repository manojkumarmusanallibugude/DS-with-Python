# Python `dict` — Internal Hash Table

---

## 1. Introduction

You have used Python dictionaries since your first week of programming.

```python
phone_book = {
    "Alice" : "555-1234",
    "Bob"   : "555-5678",
    "Charlie": "555-9999"
}

print(phone_book["Alice"])   # Output: 555-1234
```

That lookup returns the answer **instantly** — regardless of whether your dictionary has 3 entries or 3 million.

Before answering *how*, let's honestly ask: *could we do the same thing with the data structures we already know?*

**Array / Python List** stores values at numbered positions. To find "Alice", you'd scan every entry, comparing names one by one. With 1 million entries, that's potentially 1 million comparisons. Not instant.

**Sorted List + Binary Search** cuts that to about 20 comparisons for 1 million entries — much better. But every insertion must keep the list sorted, which requires shifting elements. Slow for writes.

**Linked List** — even worse than an array for searching. You must walk the chain node by node from the beginning. No shortcuts.

**Binary Search Tree** gives you O(log n) lookup — about 20 comparisons for 1 million entries. Good. But it still takes 20 steps. And it can degrade to O(n) if the tree becomes unbalanced.

None of these is "instant." But Python's `dict` is.

```python
import time

d = {i: i for i in range(1_000_000)}   # 1 million entries

start = time.perf_counter()
_ = d[999_999]                          # Look up the very last key
end   = time.perf_counter()

print(f"Lookup time: {(end - start) * 1e6:.2f} microseconds")
# Output: Lookup time: 0.08 microseconds
```

One microsecond. For a million-entry dictionary. That is not a fast scan. That is a **single jump** to the exact location.

This document explains exactly how Python makes that jump — and what it has built, layer by careful layer, inside every `dict` you have ever used.

## 2. Real-World Applications

Before diving into internals, appreciate just how pervasive Python's `dict` is:

**Every Python object is a dict**
When you write `obj.name = "Alice"`, Python stores that attribute in a hidden dictionary called `obj.__dict__`. Classes, modules, function local variables — all managed as dicts internally.

**Every Python module's namespace is a dict**
When you do `import math`, Python creates a dict mapping `"pi"` → `3.14159...`, `"sqrt"` → `<function>`, and so on.

**Web frameworks**
In Django and Flask, every HTTP request comes in as a dictionary of headers, parameters, and body fields. Every database row fetched maps column names to values — a dict.

**JSON**
Every JSON object in the world (`{"name": "Alice", "age": 30}`) maps directly to a Python dict. JSON parsing is, at its heart, building a hash table.

**Caches and memoisation**
Function result caches (`@lru_cache`), DNS resolution caches, browser caches, CPU translation lookaside buffers — all implemented as hash tables, conceptually identical to a Python dict.

Understanding the internals of `dict` is not academic — it is understanding the mechanism that makes Python fast enough to power Instagram, YouTube, and Dropbox.

## 3. The Core Idea — Hashing as a GPS Coordinate

Imagine you manage a warehouse with 8 storage bays, numbered 0 through 7.

A package arrives labelled "Alice". You don't think, you don't search — you run the label through a **formula** that immediately tells you: *"Alice always goes to bay 3."* You walk straight to bay 3. Done.

That formula is a **hash function**. It converts any key into a fixed-range integer — a bay number, an array index, a storage address.

```
hash("Alice") % 8  →  3
hash("Bob")   % 8  →  5
hash("Charlie") % 8  →  3   ← collision: same bay as Alice
```

The hash function is the GPS. Given the key, it tells you exactly where to look — in O(1) time, without examining any other entry.

This single idea — *"convert the key into its own address"* — is what makes `dict` different from every other data structure.

## 4. Key Terminology

These terms appear throughout Python's source code and documentation. Know them before going further.

```
Python dict internals:

  ┌────────────────────────────────────────────┐
  │              Hash Table                    │
  │   ┌──────┬──────────┬───────┬───────────┐  │
  │   │  i   │   hash   │  key  │   value   │  │← each row is one "slot" (entry)
  │   └──────┴──────────┴───────┴───────────┘  │
  │                                            │
  │   load_factor = used_slots / total_slots   │
  └────────────────────────────────────────────┘
```

| Term | Meaning |
|---|---|
| **Hash function** | Converts a key into an integer. `hash("Alice")` → some large number |
| **Index** | `hash(key) % table_size` — the slot in the array where the entry belongs |
| **Slot / Bucket** | One position in the internal array — holds one `(hash, key, value)` entry |
| **Collision** | Two different keys produce the same index |
| **Probe** | Examining a slot to see if it's the right one (or empty, or a tombstone) |
| **Load factor** | `n / m` — entries used ÷ total slots. Python resizes at 2/3 (≈ 0.67) |
| **Resize / Rehash** | When load factor hits the threshold, the array is grown and all entries re-placed |
| **Compact dict** | CPython 3.6+ internal layout — separates the index array from the entry storage |

## 5. What Python Actually Stores in a Dict

You might expect Python to store just `(key, value)`. It actually stores three things per entry:

```python
entry = (hash_value, key, value)
#        ↑            ↑    ↑
#        cached        the  the
#        forever       key  data
```

**Why cache the hash value?**

Computing `hash("Alice")` is not free — for long strings or complex objects, it takes time. By storing the hash alongside the entry, Python can do a **cheap integer comparison first**:

```
Does cached_hash == search_hash?
  No  → definitely not the same key. Skip.
  Yes → probably the same key. Now compare the actual keys to confirm.
```

This avoids calling the expensive `==` operator on keys that can't possibly match. A small detail that, across millions of lookups, adds up.

## 6. CPython's Internal Layout — The Compact Dict (Python 3.6+)

Before Python 3.6, a dict was a single flat array of `(hash, key, value)` triples — simple, but wasteful. Many slots sat empty and still consumed memory for all three fields.

Python 3.6 introduced the **compact dict**, designed by Raymond Hettinger. It splits the table into two separate structures:

### Structure 1 — The Indices Array (Small and Sparse)

A compact array of integers. Each cell is just an index — a tiny number pointing into the entries array, or one of two sentinel values:

```
EMPTY    = -1   (slot never used)
DUMMY    = -2   (tombstone — slot was used, then deleted)
```

```
indices = [-1, -1,  0, -1,  1, -1,  2, -1]
           ↑               ↑         ↑
          EMPTY          points    points
                         to entry  to entry
                         [0]       [2]
```

Each cell in `indices` takes only 1, 2, or 4 bytes (Python chooses the smallest integer size that fits the table length). This array is sparse by design — many `-1`s. But because each cell is tiny, the memory cost is low.

### Structure 2 — The Entries Array (Dense and Ordered)

A compact, tightly-packed array of `(hash, key, value)` tuples — one per actual entry, with **no gaps**:

```
entries = [
    (hash("Alice"),   "Alice",   "555-1234"),   ← entry[0]
    (hash("Bob"),     "Bob",     "555-5678"),   ← entry[1]
    (hash("Charlie"), "Charlie", "555-9999"),   ← entry[2]
]
```

Entries are stored in **insertion order** — exactly the order you added them. This is why Python 3.7+ guarantees that `dict` preserves insertion order. It is not a coincidence or a side effect. It is a direct consequence of this architecture.

### How They Work Together

```
To look up "Bob":

  1. Compute: hash("Bob") % len(indices) = 4
  2. Look at: indices[4] = 1
  3. Go to:   entries[1] = (hash("Bob"), "Bob", "555-5678")
  4. Confirm: cached hash matches AND key matches → return "555-5678"

  One hop through indices.
  One hop into entries.
  Done.
```

Visually:

```
  indices array              entries array
  ┌────┬────┬────┬────┐     ┌───────────────────────────────────────┐
  │ -1 │ -1 │  0 │ -1 │     │ [0]  hash("Alice"),   "Alice",  "555-1234" │
  ├────┼────┼────┼────┤     │ [1]  hash("Bob"),     "Bob",    "555-5678" │
  │  1 │ -1 │  2 │ -1 │     │ [2]  hash("Charlie"), "Charlie","555-9999" │
  └────┴────┴────┴────┘     └───────────────────────────────────────┘
       ↑
  indices[4] = 1
  → go to entries[1] → "Bob"
```

**Why is this better than the old flat layout?**

- The `entries` array is dense — no wasted slots between entries. Better cache performance when iterating.
- The `indices` array is small integers — much less memory than storing full `(hash, key, value)` triples at every sparse position.
- Insertion order is inherently preserved because `entries` is an append-only log of arrivals.

## 7. Open Addressing — How Python Resolves Collisions

Python's dict uses **open addressing** for collision resolution. There are no linked lists, no chaining — everything lives inside the `indices` array.

When two keys hash to the same index slot, Python probes for the next available slot. But unlike the simple strategies from the previous topic, Python uses a **more sophisticated probe formula** that mixes two approaches.

### Python's Probe Formula

```python
# Python's actual probe sequence (simplified):
perturb = hash_value
slot    = hash_value % size

while True:
    if indices[slot] is suitable:
        break
    # Key step: the perturbation shifts on every probe
    perturb >>= 5
    slot = (slot * 5 + perturb + 1) % size
```

This is **not** simple linear probing (+1 each step) and **not** simple quadratic probing (+k²). It is a custom formula that:

1. **Starts** at `hash % size` — the natural home of the key.
2. **Mixes in bits of the original hash** (`perturb`) on every probe step.
3. **Guarantees** it will visit every slot in the table before repeating (for power-of-2 table sizes).

**Why not just use linear probing?**

Linear probing causes **primary clustering** — long runs of occupied slots pile up and slow down insertions and lookups. Python's formula avoids this by incorporating the hash's upper bits into the probe path. Two keys that collide at the same starting slot will immediately diverge onto different paths because their `perturb` values (which are their full hash values) will differ.

```
Two keys, both starting at slot 3:

Linear Probing:        3 → 4 → 5 → 6 → ...  (same path — they fight)
Python's formula:      key A: 3 → 9 → 2 → 11 → ...
                       key B: 3 → 7 → 14 → 1 → ...
                              ↑ diverge immediately after the first collision
```

## 8. The Hash Function — `hash()` in Python

Python's built-in `hash()` function converts any **hashable** object to an integer.

```python
print(hash("Alice"))    # e.g. -8659209558884891702  (changes per session)
print(hash(42))         # 42   (integers hash to themselves)
print(hash(3.14))       # 322818021289917443
print(hash((1, 2, 3)))  # 2528502973977326415
```

### Hash Randomisation — Why the Numbers Change Each Run

```python
# Run 1:
print(hash("Alice"))   # -8659209558884891702

# Run 2 (restart Python):
print(hash("Alice"))   # 1507777225505560487   ← completely different!
```

Python randomises string (and bytes) hashing at startup using a random seed — a security feature called **hash randomisation** (PEP 456, enabled by default since Python 3.3).

**Why?** To prevent **hash flooding attacks** — a category of denial-of-service attack where a malicious user crafts thousands of inputs that all hash to the same slot, forcing a dict to degrade to O(n) per operation. With a secret random seed, attackers can't predict which inputs will collide.

**What is stable?** Integers always hash to themselves (with some wrapping for very large numbers). Floats follow IEEE 754 rules. The randomisation only affects string and bytes objects.

### What Makes an Object Hashable?

For an object to be used as a dict key, it must:

1. Implement `__hash__()` — to generate its hash value
2. Implement `__eq__()` — to confirm equality when hashes match
3. Be **immutable** — if the object could change after being inserted as a key, its hash would change, and Python could never find it again

```python
# Hashable (immutable) → valid dict keys
hash("hello")       # ✓ strings are immutable
hash(42)            # ✓ integers are immutable
hash((1, 2, 3))     # ✓ tuples are immutable (if contents are also hashable)

# Not hashable (mutable) → cannot be dict keys
hash([1, 2, 3])     # ✗ TypeError: unhashable type: 'list'
hash({"a": 1})      # ✗ TypeError: unhashable type: 'dict'
hash({1, 2, 3})     # ✗ TypeError: unhashable type: 'set'
```

The moment you try to use a list as a dict key, Python tells you: *"I can't use this as an address — it might change and I'd lose the entry forever."*

## 9. The Lookup Algorithm — Step by Step

This is the most important sequence to understand. Every `d[key]` runs these exact steps.

```
To look up key K in dict d:

Step 1:  Compute h = hash(K)
Step 2:  Compute slot = h % len(d.indices)
Step 3:  Look at d.indices[slot]

    Case A: d.indices[slot] == EMPTY (-1)
            → K is definitely not in the dict. Return KeyError.

    Case B: d.indices[slot] == DUMMY (-2)  [tombstone]
            → This slot had a deleted entry. Keep probing.
            → Apply probe formula to compute next slot. Go to Step 3.

    Case C: d.indices[slot] == i  (a valid entry index)
            → Go to d.entries[i]
            → Check: d.entries[i].hash == h ?
                No  → hash mismatch, not our key. Keep probing. Go to Step 3.
                Yes → Check: d.entries[i].key == K ?
                        No  → key mismatch (hash collision). Keep probing.
                        Yes → FOUND. Return d.entries[i].value.
```

Notice the two-stage comparison:
1. **Hash comparison first** — cheap integer equality check
2. **Key comparison second** — only if hashes match

This is why custom objects must implement *both* `__hash__` and `__eq__` consistently. Python's rule: **if two objects compare equal (`==`), they must have the same hash.** If you break this rule, lookups silently fail.

```python
class BrokenKey:
    def __eq__(self, other): return True     # Everything is "equal"
    def __hash__(self):      return 42       # But only one hash value

# Python requires: a == b  →  hash(a) == hash(b)
# Violating this produces silent, maddening bugs
```

## 10. The Insertion Algorithm — Step by Step

```
To insert (K, V) into dict d:

Step 1:  Compute h = hash(K)
Step 2:  Compute slot = h % len(d.indices)
Step 3:  Look at d.indices[slot]

    Case A: EMPTY or DUMMY
            → This slot is available.
            → Append (h, K, V) to d.entries  (insertion order preserved!)
            → Set d.indices[slot] = len(d.entries) - 1
            → Increment used count.
            → If load factor > 2/3: trigger resize.

    Case B: Valid entry index i
            → Check d.entries[i].key == K ?
                Yes → Update d.entries[i].value = V  (key already exists)
                No  → Hash collision. Apply probe formula. Go to Step 3.
```

The critical detail: new entries are always **appended to `d.entries`**. The entries array is never reordered. This guarantees insertion-order iteration.

## 11. Deletion — The Tombstone Mechanism

Deletion in open addressing cannot simply blank a slot with `EMPTY`. As we saw in the previous topic, blanking a slot breaks the probe chain for any key that was placed beyond it.

Python uses the `DUMMY` sentinel — a tombstone — exactly as described in the Open Addressing topic.

```python
del phone_book["Bob"]
```

Internally:

```
Before deletion:
  indices[4] = 1          entries[1] = (hash("Bob"), "Bob", "555-5678")

After deletion:
  indices[4] = DUMMY (-2) entries[1] = (hash("Bob"), None, None)
                ↑
           tombstone — search will skip this but keep probing
           insertion will reuse this slot
```

**What about `entries[1]`?**

The entries array slot is cleared (key and value set to `None`) to release the reference, allowing Python's garbage collector to reclaim the memory of the key and value objects. But the *position* in the entries array stays occupied.

This means after many deletions, the entries array can have gaps. Python accounts for this during resizing — when the table is rebuilt, deleted entries are simply not copied over, compacting the entries array back to a clean dense state.

## 12. Resizing — Growing the Table

Python resizes the dict when the **load factor exceeds 2/3** (approximately 67%).

This is more aggressive than many textbook implementations (which use 0.75 or higher) because Python's open addressing probe formula performs better at lower load factors.

### Resize Steps

```
1. Compute new size:
      If table is large:  new_size = used_entries * 2
      If table is small:  new_size = used_entries * 4
   (new_size is always rounded up to the next power of 2)

2. Allocate a fresh indices array of new_size (all EMPTY).

3. Allocate a fresh entries array.

4. Walk the OLD entries array. For each live (non-DUMMY) entry:
      a. Re-compute slot = entry.hash % new_size
      b. Apply probe formula if needed
      c. Place entry index into new indices
      d. Copy entry into new entries array

5. Discard the old arrays.
```

Tombstones (`DUMMY`) are **not** copied. They vanish during resize, compacting the entries array. This is why heavy deletion followed by reinsertion doesn't permanently degrade a dict's performance.

**What is the cost?** A resize takes O(n) — you visit every live entry. But it happens rarely (every time the table doubles), so the **amortised cost per insertion is still O(1)**.

### Initial Size and Growth Pattern

```
Python's internal dict sizes (power-of-2 growth):

 Entries added:  Resize triggers at:    New total capacity:
       0                  —                    8   (initial)
       6            6 > 8 × 2/3 = 5.3          16  (next resize: at 10)
      11           11 > 16 × 2/3 = 10.6         32  (next resize: at 21)
      22           22 > 32 × 2/3 = 21.3          64
     ...
```

The table always has at least 1/3 empty slots. This headroom keeps probe sequences short and performance fast.

## 13. A Complete Simulation in Python

The code below is not CPython's actual source (which is C) — but it faithfully models the logic, slot states, and probe sequence so you can watch it execute.

```python
class SimulatedPythonDict:
    """
    Simulates CPython's compact dict behaviour:
    - Separate indices array and entries array
    - Open addressing with a perturbation-based probe sequence
    - EMPTY (-1) and DUMMY (-2) sentinel values
    - Resize at 2/3 load factor
    """

    EMPTY = -1
    DUMMY = -2

    def __init__(self, initial_size=8):
        self._size    = initial_size               # indices array length (power of 2)
        self._indices = [self.EMPTY] * self._size  # sparse index array
        self._entries = []                         # dense (hash, key, value) list
        self._used    = 0                          # live entries (not tombstones)

    # ── Probe Sequence (simplified CPython formula) ──────────────────────────

    def _probe(self, hash_val):
        """Yield slot indices using CPython's perturbation-based sequence."""
        perturb = hash_val & 0xFFFFFFFFFFFFFFFF     # treat as unsigned 64-bit
        slot    = hash_val % self._size
        while True:
            yield slot
            perturb >>= 5
            slot = (slot * 5 + perturb + 1) % self._size

    # ── Resize ───────────────────────────────────────────────────────────────

    def _resize(self):
        live_entries = [(h, k, v) for (h, k, v) in self._entries if k is not None]
        new_size     = max(8, len(live_entries) * 4)  # grow generously
        # Round up to next power of 2
        p = 1
        while p < new_size:
            p <<= 1
        self._size    = p
        self._indices = [self.EMPTY] * self._size
        self._entries = []
        self._used    = 0
        for (h, k, v) in live_entries:
            self._raw_insert(h, k, v)

    def _raw_insert(self, h, key, value):
        """Insert without triggering resize (used during resize itself)."""
        for slot in self._probe(h):
            idx = self._indices[slot]
            if idx == self.EMPTY or idx == self.DUMMY:
                self._entries.append((h, key, value))
                self._indices[slot] = len(self._entries) - 1
                self._used += 1
                return
            entry_h, entry_k, _ = self._entries[idx]
            if entry_h == h and entry_k == key:
                # Update existing — replace in-place in entries
                self._entries[idx] = (h, key, value)
                return

    # ── Public Interface ─────────────────────────────────────────────────────

    def __setitem__(self, key, value):
        h = hash(key)
        # Check if key already exists (update path)
        for slot in self._probe(h):
            idx = self._indices[slot]
            if idx == self.EMPTY:
                break
            if idx == self.DUMMY:
                continue
            entry_h, entry_k, _ = self._entries[idx]
            if entry_h == h and entry_k == key:
                self._entries[idx] = (h, key, value)   # update value
                return
        # New key — insert
        self._raw_insert(h, key, value)
        # Resize if load factor > 2/3
        if self._used > (self._size * 2) // 3:
            self._resize()

    def __getitem__(self, key):
        h = hash(key)
        for slot in self._probe(h):
            idx = self._indices[slot]
            if idx == self.EMPTY:
                raise KeyError(key)
            if idx == self.DUMMY:
                continue
            entry_h, entry_k, entry_v = self._entries[idx]
            if entry_h == h and entry_k == key:
                return entry_v
        raise KeyError(key)

    def __delitem__(self, key):
        h = hash(key)
        for slot in self._probe(h):
            idx = self._indices[slot]
            if idx == self.EMPTY:
                raise KeyError(key)
            if idx == self.DUMMY:
                continue
            entry_h, entry_k, _ = self._entries[idx]
            if entry_h == h and entry_k == key:
                self._indices[slot] = self.DUMMY        # tombstone
                self._entries[idx]  = (entry_h, None, None)  # release refs
                self._used -= 1
                return
        raise KeyError(key)

    def display(self):
        print(f"\n  Table size: {self._size}  |  Live entries: {self._used}"
              f"  |  Load factor: {self._used / self._size:.2f}")
        print("  Indices array:")
        for i, idx in enumerate(self._indices):
            if idx == self.EMPTY:
                label = "EMPTY"
            elif idx == self.DUMMY:
                label = "DUMMY (tombstone)"
            else:
                _, k, v = self._entries[idx]
                label = f"→ entry[{idx}]  ({k!r}: {v!r})"
            print(f"    [{i:2d}] {label}")
        print("  Entries array (insertion order):")
        for i, (h, k, v) in enumerate(self._entries):
            if k is None:
                print(f"    [{i}] DELETED")
            else:
                print(f"    [{i}] ({k!r}: {v!r})")


# ── Run the Simulation ────────────────────────────────────────────────────

d = SimulatedPythonDict()

d["Alice"]   = "555-1234"
d["Bob"]     = "555-5678"
d["Charlie"] = "555-9999"
d["Dave"]    = "555-0001"

print("=== After 4 insertions ===")
d.display()

print("\n--- Lookup 'Charlie':", d["Charlie"])
print("--- Lookup 'Alice':  ", d["Alice"])

d["Alice"] = "555-0000"   # update existing key
print("\n=== After updating 'Alice' ===")
d.display()

del d["Bob"]
print("\n=== After deleting 'Bob' ===")
d.display()

print("\n--- Lookup 'Charlie' after Bob deleted:", d["Charlie"])
# Charlie is still findable — tombstone preserves the probe chain
```

## 14. Time and Space Complexity

| Operation | Average Case | Worst Case | Notes |
|---|---|---|---|
| `d[key]` (lookup) | **O(1)** | O(n) | Worst case: all keys collide into one probe chain |
| `d[key] = val` (insert) | **O(1)** amortised | O(n) | O(n) only when resize triggers; amortised O(1) |
| `del d[key]` | **O(1)** | O(n) | Tombstone placement is O(1) |
| `key in d` | **O(1)** | O(n) | Same as lookup |
| Iteration | **O(n)** | O(n) | Must visit all n entries |
| `len(d)` | **O(1)** | O(1) | Count is maintained as a variable |

The O(n) worst case requires every single key to collide — essentially impossible with hash randomisation and a good hash function. For all practical purposes, every dict operation is O(1).

**Space complexity:** O(n) — but the constant matters. The indices array is compact (1–4 bytes per slot). The entries array stores one `(hash, key, value)` triple per live entry. Python's compact dict uses roughly **50% less memory** than the pre-3.6 layout for most real-world dicts.

## 15. Common Mistakes and Misconceptions

### Mistake 1 — Using a Mutable Object as a Key

```python
# WRONG — lists are not hashable
d = {}
my_list = [1, 2, 3]
d[my_list] = "data"   # TypeError: unhashable type: 'list'

# Why? If Python allowed it:
d[my_list] = "data"   # stored at slot based on hash([1,2,3])
my_list.append(4)     # list changes → hash([1,2,3,4]) is different
d[my_list]            # looks at wrong slot → KeyError. Data lost forever.

# Fix: use an immutable equivalent
d[tuple(my_list)] = "data"   # ✓ tuples are hashable
```

Mutability and hashability are the same constraint, stated two ways.

---

### Mistake 2 — Assuming Key Order Before Python 3.7

```python
# Python 3.6: insertion order preserved as CPython implementation detail
# Python 3.7+: insertion order preserved as LANGUAGE GUARANTEE

d = {"banana": 1, "apple": 2, "cherry": 3}
print(list(d.keys()))   # ['banana', 'apple', 'cherry'] — guaranteed order
```

Before Python 3.6, dicts had no guaranteed order. Code that relies on dict order and must support Python 3.5 or earlier will break silently.

---

### Mistake 3 — Modifying a Dict While Iterating Over It

```python
d = {"a": 1, "b": 2, "c": 3}

# WRONG — RuntimeError: dictionary changed size during iteration
for key in d:
    if d[key] == 2:
        del d[key]

# FIX — iterate over a copy of the keys
for key in list(d.keys()):
    if d[key] == 2:
        del d[key]
```

Python detects concurrent modification and raises `RuntimeError` to protect the iteration state. This is not a bug — it is a safety guard.

---

### Mistake 4 — Expecting `hash()` to Be Consistent Across Python Runs

```python
# This will silently break your cache:
cached_slot = hash("my_key") % 100   # computed in run 1
# ... save to file ...
# run 2: hash("my_key") is completely different → wrong slot

# Fix: never persist hash() values across runs.
# Use deterministic hashers (hashlib.md5, hashlib.sha256) for persistent keys.
import hashlib
stable_hash = int(hashlib.md5("my_key".encode()).hexdigest(), 16) % 100
```

`hash()` is for in-process, in-memory use only. It changes every time Python restarts.

---

### Mistake 5 — Defining `__eq__` Without `__hash__`

```python
class Employee:
    def __init__(self, name):
        self.name = name
    def __eq__(self, other):
        return self.name == other.name
    # ← forgot __hash__!

# Python's rule: if you define __eq__, Python sets __hash__ = None
e = Employee("Alice")
d = {}
d[e] = "present"   # TypeError: unhashable type: 'Employee'
```

Python enforces the contract: if `a == b` must hold, then `hash(a) == hash(b)` must also hold. Since Python can't know how your `__eq__` works, it disables hashing entirely until you explicitly define `__hash__`.

**Fix:**
```python
def __hash__(self):
    return hash(self.name)   # hash based on the same field used in __eq__
```

## 16. How Python's `dict` Compares to Our Implementations

Over the last few topics, we built hash tables from scratch. Here is how those concepts map directly to what Python does:

| What we built | What Python does |
|---|---|
| A flat array of `(key, value)` | Two arrays: compact `indices` + dense `entries` |
| `hash(key) % size` | Same formula, but on the `indices` array |
| Linear / quadratic / double hashing | Custom perturbation-based probe: `(slot * 5 + perturb + 1) % size` |
| `DELETED` tombstone | `DUMMY = -2` sentinel in the `indices` array |
| Resize at load factor 0.75 | Resize at load factor **2/3** (more aggressive) |
| Power-of-2 table size | Always power-of-2 (enables bitwise `&` instead of `%`) |
| Store `(key, value)` | Store `(hash, key, value)` — cached hash avoids recomputation |
| No order guarantee | Insertion order guaranteed (entries array is append-only) |

The ideas are identical. Python's implementation adds engineering refinements on top of the same foundations.

## 18. Summary

| Concept | What It Means |
|---|---|
| `hash(key)` | Converts a key to an integer address. Randomised per Python session for strings. |
| `hash(key) % size` | Maps the integer to a valid slot in the indices array |
| Compact dict | CPython 3.6+ layout: small `indices` array + dense `entries` array |
| Insertion order | Guaranteed because `entries` is an append-only array |
| Probe formula | `(slot * 5 + perturb + 1) % size` — avoids clustering, covers all slots |
| EMPTY (`-1`) | Slot never used — search stops here |
| DUMMY (`-2`) | Tombstone — slot was deleted — search keeps probing |
| Load factor 2/3 | Resize threshold — more aggressive than 3/4 for better probe performance |
| Resize | Doubles the table, re-hashes all live entries, clears all tombstones |
| Hashable requirement | Keys must be immutable and implement both `__hash__` and `__eq__` |

Python's `dict` is not magic. It is a precisely engineered hash table that applies every principle from this series — hashing, probing, tombstones, resizing — and wraps them in a layer of Python-specific optimisations: cached hash values, randomised seeds, the compact two-array layout, and the power-of-2 size trick that replaces expensive modulo operations with fast bitwise AND.

Once you can see the hash table inside the dict, you see it everywhere — in sets, in class attribute lookup, in module imports, in JSON parsing. You have not just learned a data structure. You have learned the engine that runs beneath most of Python itself.
