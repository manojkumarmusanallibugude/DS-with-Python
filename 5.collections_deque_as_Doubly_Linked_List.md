# collections.deque — Python's Doubly Linked List

---

## The Problem with One Direction

In the previous topic, we built a Singly Linked List. Each node pointed forward — and only forward. To get to the last node, you had to walk every node from the beginning. To delete the last node, you needed to find the second-to-last node first.

This is fine when your work happens mostly at the front. But what if you frequently need **both ends**?

Think of a text editor. Every time you press **Backspace**, the editor removes a character from behind your cursor. Every time you type, it inserts a character at your cursor. Sometimes you press **Ctrl+Z** to undo, and now it needs to walk **backwards** through your action history.

A singly linked list fails here. You can't walk backwards. You have no `previous` pointer.

And this is the problem that the **Doubly Linked List** was built to solve.

---

## What Is a Doubly Linked List?

A Doubly Linked List is a chain of nodes where **each node knows its two neighbours** — the one before it, and the one after it.

Each node holds:
1. **Data** — the value being stored
2. **`next`** — a pointer to the node ahead
3. **`prev`** — a pointer to the node behind

```
         head                                        tail
          │                                           │
          ▼                                           ▼
      ┌──────────────┐      ┌──────────────┐      ┌──────────────┐
None◄─┤prev│data│next├──►◄──┤prev│data│next├──►◄──┤prev│data│next├─► None
      └──────────────┘      └──────────────┘      └──────────────┘
           A                 B                 C
```

Two things immediately become possible:

- You can walk **forwards** (following `next`) or **backwards** (following `prev`)
- You can efficiently access and modify **both the head and the tail** without traversal

This is why doubly linked lists are the natural engine behind anything that needs to move in two directions — undo/redo histories, browser navigation, media player queues, and operating system schedulers.

---

## Python's Answer — `collections.deque`

Python does not expose a raw doubly linked list in its standard library. Instead, it ships something more refined: `collections.deque`.

**Deque** stands for **Double-Ended Queue** (pronounced *"deck"*).

Internally, CPython implements `deque` as a **doubly linked list of fixed-size blocks** rather than individual nodes. This is a practical optimisation — instead of allocating a separate object per element (expensive), it groups elements into contiguous chunks and links those chunks. The observable behaviour, however, is identical to a node-per-element doubly linked list: O(1) access and modification at both ends.

```python
from collections import deque

d = deque()
```

That one line gives you a fully functioning doubly linked list, battle-tested and production-ready, built into the language.

---

## Building Intuition — Before the API

Before looking at methods, look at the structure.

```python
from collections import deque

d = deque([10, 20, 30])
```

In memory, this is conceptually:

```
head                                    tail
 │                                       │
 ▼                                       ▼
[None ← 10 → ] ←──► [ ← 20 → ] ←──► [ ← 30 → None]
```

The deque keeps two internal references:
- **`leftmost`** — the head, where the chain begins
- **`rightmost`** — the tail, where the chain ends

Because both ends are directly accessible, adding or removing from either end requires **no traversal**. You simply update a pointer. This is the core advantage over both singly linked lists and Python's built-in `list`.

## Core Operations

### Appending — Adding to Either End

```python
from collections import deque

d = deque([20, 30])

d.append(40)       # Add to the RIGHT end
d.appendleft(10)   # Add to the LEFT end

print(d)           # deque([10, 20, 30, 40])
```

**What happens internally:**

`append(40)`:
```
Before: [10 ←→ 20 ←→ 30]
After:  [10 ←→ 20 ←→ 30 ←→ 40]
         tail's next now points to new node(40)
         new node(40).prev points back to old tail
         tail reference updated to node(40)
```

`appendleft(10)`:
```
Before: [20 ←→ 30]
After:  [10 ←→ 20 ←→ 30]
         head's prev now points to new node(10)
         new node(10).next points forward to old head
         head reference updated to node(10)
```

Both are **O(1)**. No iteration. No shifting. Just pointer updates.

Compare this to a Python list:

```python
lst = [20, 30]
lst.insert(0, 10)   # O(n) — every element shifts right to make room
```

For front insertions, `deque` beats `list` at any scale.

---

### Removing — Popping from Either End

```python
d = deque([10, 20, 30, 40])

right = d.pop()        # Removes and returns 40 (from the right)
left  = d.popleft()    # Removes and returns 10 (from the left)

print(d)               # deque([20, 30])
```

**What happens internally for `pop()`:**

```
Before: [10 ←→ 20 ←→ 30 ←→ 40]
                              ▲
                             tail

Step 1: Store node(40).data = 40
Step 2: new tail = node(40).prev = node(30)
Step 3: node(30).next = None
Step 4: node(40) unreferenced → garbage collected

After:  [10 ←→ 20 ←→ 30]
                       ▲
                      tail
```

Both `pop()` and `popleft()` are **O(1)**. Again, just pointer updates.

If you call `pop()` or `popleft()` on an empty deque, Python raises `IndexError`. Handle this:

```python
d = deque()

try:
    d.pop()
except IndexError:
    print("Cannot pop from an empty deque")
```

---

### Extending — Adding Multiple Elements at Once

```python
d = deque([3, 4, 5])

d.extend([6, 7, 8])         # Add multiple to the right
d.extendleft([2, 1, 0])     # Add multiple to the left

print(d)    # deque([0, 1, 2, 3, 4, 5, 6, 7, 8])
```

**`extendleft` reverses the input order.** This is not a bug — it is a direct consequence of how `appendleft` works. Each element is added one at a time to the left, so the last element ends up at the front.

```
extendleft([2, 1, 0]):

Step 1: appendleft(2) → [2, 3, 4, 5]
Step 2: appendleft(1) → [1, 2, 3, 4, 5]
Step 3: appendleft(0) → [0, 1, 2, 3, 4, 5]
```

If you need to add a sequence to the left **in the same order**, reverse it first:

```python
d.extendleft(reversed([0, 1, 2]))    # Preserves order at the left end
```

### Rotating — The Operation Unique to Deque

`rotate(n)` moves elements from one end to the other. It is one of the most elegant operations in the deque API.

```python
d = deque([1, 2, 3, 4, 5])

d.rotate(2)     # Rotate RIGHT by 2
print(d)        # deque([4, 5, 1, 2, 3])

d.rotate(-2)    # Rotate LEFT by 2
print(d)        # deque([1, 2, 3, 4, 5])   (back to original)
```

**Rotating right by 1** means: take the last element and move it to the front.

```
Before:  [1, 2, 3, 4, 5]
              ↑ take 5 from the tail
After:   [5, 1, 2, 3, 4]
              ↑ place it at the head
```

**Rotating left by 1** means: take the first element and move it to the back.

Because both ends are O(1) in a deque, a single step of rotation is O(1). Rotating by `n` is O(n).

**Real-world use case:** Round-robin scheduling. A system with five processes can take the current process from the front, run it, and push it to the back — all with a single `rotate(-1)`.

```python
processes = deque(["P1", "P2", "P3", "P4", "P5"])

for _ in range(8):                    # Simulate 8 time slots
    current = processes[0]
    print(f"Running: {current}")
    processes.rotate(-1)              # Current process goes to the back
```

### Bounded Deques — Automatic Overflow Management

This is where `deque` becomes genuinely exceptional. You can give it a **maximum length**.

```python
d = deque(maxlen=3)

d.append(1)    # deque([1])
d.append(2)    # deque([1, 2])
d.append(3)    # deque([1, 2, 3])
d.append(4)    # deque([2, 3, 4])  ← 1 was automatically removed from the left
d.append(5)    # deque([3, 4, 5])  ← 2 was automatically removed from the left
```

When the deque is full and a new element is added to the right, the leftmost element is automatically discarded. Add to the left when full, and the rightmost is discarded.

This behaviour implements a **sliding window** or **fixed-size history** with zero extra logic:

```python
def recent_n(stream, n):
    """Returns only the last n elements seen from a stream."""
    window = deque(maxlen=n)
    for item in stream:
        window.append(item)
    return list(window)

recent_n(range(100), 5)   # [95, 96, 97, 98, 99]
```

The same pattern powers browser history, log buffers, moving averages in financial systems, and sensor data windows in embedded systems.

---

### Counting and Searching

```python
d = deque([10, 20, 30, 20, 10, 20])

print(d.count(20))      # 3 — how many times 20 appears
print(d.index(30))      # 2 — position of first occurrence of 30
```

`count()` is O(n) — it walks the entire deque.
`index()` is O(n) — it walks until the value is found.

Neither is a fast operation. If you need frequent membership checks, a `set` or `dict` is the right tool. The deque excels at ordered insertion and removal, not lookup.

---

### Other Useful Methods

```python
d = deque([1, 2, 3, 4, 5])

d.reverse()          # Reverse in place → deque([5, 4, 3, 2, 1])

d.remove(3)          # Remove first occurrence of a value
                     # Raises ValueError if not found

d.clear()            # Empty the deque completely

d.copy()             # Shallow copy of the deque
```

`remove()` is O(n). All others are O(1) or O(n) where expected.

## Practical Patterns

### Pattern 1 — Implementing a Stack (LIFO)

A stack adds and removes from the same end.

```python
from collections import deque

stack = deque()

stack.append("action_1")     # push
stack.append("action_2")     # push
stack.append("action_3")     # push

print(stack.pop())            # "action_3" — last in, first out
print(stack.pop())            # "action_2"
```

**Is `list` not sufficient for a stack?**
It is — `list.append()` and `list.pop()` are both O(1) amortised. For pure stack behaviour, a `list` is equally valid and arguably more readable. Prefer `deque` when you need **both ends**, or when communicating that the structure is a queue-like container.

---

### Pattern 2 — Implementing a Queue (FIFO)

A queue adds at the back and removes from the front. This is where `deque` is decisively better than `list`.

```python
from collections import deque

queue = deque()

queue.append("request_1")      # enqueue
queue.append("request_2")      # enqueue
queue.append("request_3")      # enqueue

print(queue.popleft())         # "request_1" — first in, first out
print(queue.popleft())         # "request_2"
```

`list.pop(0)` is O(n) — every element shifts left.
`deque.popleft()` is O(1) — one pointer update.

For any queue with high throughput, this difference compounds significantly.

---

### Pattern 3 — Palindrome Check

A deque's ability to inspect and remove from both ends makes palindrome checking clean:

```python
from collections import deque

def is_palindrome(word):
    d = deque(word)
    while len(d) > 1:
        if d.popleft() != d.pop():
            return False
    return True

print(is_palindrome("racecar"))   # True
print(is_palindrome("python"))    # False
```

Compare the first and last characters. If they match, discard both. Repeat until one or zero remain.

---

### Pattern 4 — Sliding Window Maximum

A bounded deque can maintain a window of the last `k` elements from a stream:

```python
from collections import deque

def moving_average(values, window_size):
    window = deque(maxlen=window_size)
    averages = []
    for v in values:
        window.append(v)
        averages.append(sum(window) / len(window))
    return averages

data = [10, 20, 15, 30, 25, 35]
print(moving_average(data, 3))
# [10.0, 15.0, 15.0, 21.67, 23.33, 30.0]
```

No manual index tracking. No slicing. The window manages itself.

## Deque vs List vs Singly Linked List

| Operation | `list` | Singly Linked List | `deque` |
|---|---|---|---|
| Append to right | O(1) amortised | O(n) — walk to end | O(1) |
| Append to left | O(n) — shift all | O(1) | O(1) |
| Pop from right | O(1) amortised | O(n) — walk to end | O(1) |
| Pop from left | O(n) — shift all | O(1) | O(1) |
| Access by index | O(1) | O(n) | O(n) |
| Insert in middle | O(n) | O(n) | O(n) |
| Memory layout | Contiguous | Scattered | Blocked chunks |
| Max length cap | No | No | Yes (`maxlen`) |

The pattern is clear:
- Need fast **random access** by index → use `list`
- Need fast operations at **both ends** → use `deque`
- Need to build custom linked structures → build from `Node`

## Common Mistakes

### Mistake 1 — Using `deque` for Random Access

```python
d = deque(range(1000))

# This works, but it is O(n) — not O(1) like a list
value = d[500]
```

`deque` does not support O(1) index access. It must walk through its internal block structure to reach position `n`. If your workload requires frequent indexing by position, a `list` is the right tool.

---

### Mistake 2 — Expecting `extendleft` to Preserve Order

```python
d = deque([4, 5])
d.extendleft([1, 2, 3])   # Adding [1, 2, 3] to the left
print(d)                   # deque([3, 2, 1, 4, 5]) — reversed!
```

`extendleft` applies `appendleft` one element at a time, which reverses the sequence. If order matters:

```python
d.extendleft(reversed([1, 2, 3]))
print(d)   # deque([1, 2, 3, 4, 5]) — correct order
```

---

### Mistake 3 — Treating Bounded Deque Loss as an Error

```python
log = deque(maxlen=3)
log.append("event_1")
log.append("event_2")
log.append("event_3")
log.append("event_4")   # event_1 silently disappears

print(log)   # deque(['event_2', 'event_3', 'event_4'], maxlen=3)
```

The deque does not warn you when an element is discarded. If you need to know whether overflow occurred, check `len(d) == d.maxlen` before appending.

---

### Mistake 4 — Using `deque` as a Thread-Safe Queue Without Understanding Guarantees

`deque` is thread-safe only for `append()`, `appendleft()`, `pop()`, and `popleft()` in CPython, because the GIL protects single operations. Combined operations are **not** atomic:

```python
# UNSAFE in a multi-threaded context
if d:              # check and pop are two separate operations
    d.popleft()    # another thread could pop between these two lines
```

For genuine multi-threaded producer-consumer queues, use `queue.Queue`, which provides full locking and blocking semantics.

## The Full Picture — Complete Reference

```python
from collections import deque

# Creation
d = deque()                          # Empty deque
d = deque([1, 2, 3])                 # From iterable
d = deque([1, 2, 3], maxlen=5)       # With capacity limit

# Adding elements
d.append(x)                          # Right end — O(1)
d.appendleft(x)                      # Left end  — O(1)
d.extend(iterable)                   # Multiple to right — O(k)
d.extendleft(iterable)               # Multiple to left, reversed — O(k)
d.insert(i, x)                       # At position i — O(n)

# Removing elements
d.pop()                              # From right — O(1)
d.popleft()                          # From left  — O(1)
d.remove(value)                      # First occurrence — O(n)
d.clear()                            # Remove all — O(n)

# Inspection
d[0]                                 # Peek at left  — O(1)
d[-1]                                # Peek at right — O(1)
d[i]                                 # Index access  — O(n)
d.count(value)                       # Count occurrences — O(n)
d.index(value)                       # First position — O(n)
len(d)                               # Number of elements — O(1)

# Rearranging
d.rotate(n)                          # Rotate right by n (left if n < 0) — O(n)
d.reverse()                          # Reverse in place — O(n)
d.copy()                             # Shallow copy — O(n)
```

## Where Doubly Linked Lists and Deques Live in the Real World

**Browser Navigation**
Your browser's back and forward history is a doubly linked list. Clicking back follows `prev`. Clicking forward follows `next`. Navigating to a new page from the middle discards all forward nodes.

**LRU Cache**
The most common interview question involving doubly linked lists. A Least Recently Used cache keeps elements ordered by access time. When the cache is full, the least recently used item (at the tail) is evicted. Every access moves the node to the head. Python's `functools.lru_cache` and `OrderedDict` are built on exactly this structure.

**Text Editor Cursor**
Every character you've typed occupies a node. Moving the cursor left or right follows `prev` and `next`. Backspace removes the node behind the cursor. Insert adds a new node at the cursor position. Gap buffers and rope data structures — used in professional editors like VS Code and Emacs — are descendants of this idea.

**Operating System Scheduler**
The Linux kernel maintains a doubly linked list of runnable processes. Inserting a new process, removing a completed one, and traversing the list during scheduling decisions all rely on the O(1) properties of doubly linked list pointers.

**Python's Own `OrderedDict`**
Prior to Python 3.7, `dict` did not preserve insertion order. `OrderedDict` maintained order by keeping an internal doubly linked list of keys alongside the hash table. In modern Python, regular dicts preserve order, but `OrderedDict` still offers O(1) `move_to_end()`, which is the core operation of LRU Cache.

## Summary

| Concept | What It Means |
|---|---|
| Doubly Linked List | Each node holds `prev`, `data`, and `next` |
| `collections.deque` | Python's built-in doubly linked list implementation |
| `append` / `appendleft` | O(1) insertion at either end |
| `pop` / `popleft` | O(1) removal at either end |
| `rotate(n)` | Move n elements from one end to the other |
| `maxlen` | Fixed-size deque that auto-evicts on overflow |
| Index access | O(n) — deque is not an array |

The doubly linked list — and `collections.deque` as its practical form — represents the last major insight of the linear data structures: that a chain becomes dramatically more powerful when every node can look in both directions. This is what makes undo histories, LRU caches, and operating system schedulers tractable at scale.

With this, the foundation of linear structures is complete. Every structure ahead — stacks, queues, trees, and graphs — is built on these primitives. The node is the atom. The linked list is the molecule. Everything else is chemistry.
