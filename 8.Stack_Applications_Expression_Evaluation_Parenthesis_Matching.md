## Motivation: Why These Two Problems?

In the previous topic, we built a stack backed by a linked list. Push was O(1) always. Pop was O(1). The structure was a chain that grows at the front and shrinks from the front — no arrays, no indices, no wasted capacity.

Now the question is: **what is the stack actually good for?**

There are dozens of problems a stack solves elegantly, but two appear so consistently across compilers, calculators, code editors, and interview rounds that they deserve dedicated treatment:

**Parenthesis Matching** — Given a string containing brackets, determine whether every opening bracket has a correctly placed, correctly typed closing bracket. Used in every code editor, every compiler, every formula parser.

**Expression Evaluation** — Given a mathematical expression as a string, compute its result without `eval()`. This requires handling operator precedence, parentheses, and associativity — the full machinery of how compilers parse arithmetic.

Both problems share the same insight: **the stack's LIFO order is not a coincidence — it mirrors the natural nesting structure of the problem**. The most recently opened parenthesis must be the first to close. The most recently encountered operator must be the first to resolve. The stack enforces exactly this discipline.

## The Stack Interface

Both problems in this topic use the linked-list-backed `Stack` built in the previous topic. The interface is unchanged:

```python
class Node:
    def __init__(self, data):
        self.data = data
        self.next = None


class Stack:
    def __init__(self):
        self.top = None
        self._size = 0

    def push(self, data):
        node = Node(data)
        node.next = self.top
        self.top = node
        self._size += 1

    def pop(self):
        if self.is_empty():
            raise IndexError("pop from an empty stack")
        data = self.top.data
        self.top = self.top.next
        self._size -= 1
        return data

    def peek(self):
        if self.is_empty():
            raise IndexError("peek from an empty stack")
        return self.top.data

    def is_empty(self):
        return self.top is None

    def __len__(self):
        return self._size

    def __repr__(self):
        elements = []
        current = self.top
        while current is not None:
            elements.append(repr(current.data))
            current = current.next
        return "Stack(top→bottom): [" + ", ".join(elements) + "]"
```

Every operation used in this topic — `push`, `pop`, `peek`, `is_empty` — runs in O(1). The solutions built on top inherit that efficiency.

## Part I: Parenthesis and Bracket Matching

### Problem Statement

A code editor receives this input:

```
{ [ ( a + b ) * c ] - d }
```

Every opening bracket `{`, `[`, `(` must eventually be closed by its matching counterpart `}`, `]`, `)`. The matching must respect nesting: a bracket opened later must be closed before one opened earlier.

These are **valid**:

```
()
()[]{}
{[()]}
((()))
{[a + (b * c)] - d}
```

These are **invalid**:

```
(]        ← wrong type — opened with ( but closed with ]
([)]      ← wrong order — inner pair closed after outer pair started
{         ← unclosed — opening bracket with no matching closer
)         ← extra closer — closing bracket with no matching opener
```

The question is not just whether the number of openers equals the number of closers — `([)]` has one of each pair but is still wrong. The question is whether the **sequence** is valid.

### Why a Stack Solves This

Think through what you need to track as you scan left to right.

When you see `{`, you cannot yet match it. Something else might come first. So you remember it.

When you see `[`, you still cannot match `{`. Now you are remembering two things.

When you see `(`, you are remembering three things.

When you see `)`, you do not match it with `{` or `[`. You match it with the most recently remembered opener — `(`. If they match, the innermost pair is resolved and discarded.

This is LIFO: the last opener pushed is the first one that the next closer must match. That is the stack's defining property.

```
Input: { [ ( ) ] }

Scan {    → push {          Stack: [{]
Scan [    → push [          Stack: [[, {]
Scan (    → push (          Stack: [(, [, {]
Scan )    → pop → ( ← matches )   ✓   Stack: [[, {]
Scan ]    → pop → [ ← matches ]   ✓   Stack: [{]
Scan }    → pop → { ← matches }   ✓   Stack: []
End       → stack empty            → VALID
```

### Algorithm

```
For each character ch in the expression:
    If ch is an opening bracket → push it onto the stack
    If ch is a closing bracket:
        If the stack is empty → INVALID (closer with no opener)
        If stack.peek() does not match ch → INVALID (wrong type)
        Otherwise → pop the opener (the pair is matched)
At the end:
    If the stack is empty → VALID
    If the stack is not empty → INVALID (unclosed openers remain)
```

### Implementation

```python
def is_balanced(expression):
    """
    Return True if every bracket in expression is correctly matched and nested.
    O(n) time — one pass through the string.
    O(n) space — at most n/2 unmatched openers on the stack at any time.
    """
    s = Stack()

    matching = {')': '(', ']': '[', '}': '{'}   # Each closer maps to its opener
    openers  = set(matching.values())             # {'(', '[', '{'}
    closers  = set(matching.keys())               # {')', ']', '}'}

    for ch in expression:
        if ch in openers:
            s.push(ch)                            # Remember this opener
        elif ch in closers:
            if s.is_empty():
                return False                      # Closer with no opener
            if s.peek() != matching[ch]:
                return False                      # Wrong type of opener
            s.pop()                               # Matched — discard the pair

    return s.is_empty()                           # Unclosed openers fail
```

### Extension: Locating the First Error

In practice, a real editor needs to know not just whether the expression is valid but **where it fails**. This version tracks positions and returns a descriptive error.

```python
def validate_brackets(expression):
    """
    Validate brackets and return the position of the first error.
    Returns (True, None) if valid.
    Returns (False, message) describing the error location.
    """
    s        = Stack()                    # Each entry: (bracket, position)
    matching = {')': '(', ']': '[', '}': '{'}
    openers  = set(matching.values())
    closers  = set(matching.keys())

    for pos, ch in enumerate(expression):
        if ch in openers:
            s.push((ch, pos))             # Remember opener AND its position
        elif ch in closers:
            if s.is_empty():
                return False, f"Position {pos}: unexpected '{ch}' — no matching opener"
            top_ch, top_pos = s.peek()
            if top_ch != matching[ch]:
                return False, (
                    f"Position {pos}: '{ch}' does not match "
                    f"'{top_ch}' opened at position {top_pos}"
                )
            s.pop()

    if not s.is_empty():
        top_ch, pos = s.pop()
        return False, f"Position {pos}: '{top_ch}' was never closed"

    return True, None


# Tests
cases = [
    "{[()]}",
    "([)]",
    "((a+b)",
    "x + (y * [z - 1])",
    "}",
]

for expr in cases:
    valid, msg = validate_brackets(expr)
    status = "✓ VALID" if valid else f"✗ INVALID — {msg}"
    print(f"  {expr!r:25} → {status}")
```

**Output:**

```

  '([)]'                    → ✗ INVALID — Position 2: ')' does not match '[' opened at position 1
  '((a+b)'                  → ✗ INVALID — Position 0: '(' was never closed
  'x + (y * [z - 1])'       → ✓ VALID
  '}'                       → ✗ INVALID — Position 0: unexpected '}' — no matching opener
```

## Part II: Expression Evaluation

### Problem Statement

Given a mathematical expression as a string:

```
3 + 4 * 2
```

Compute its value — respecting operator precedence (`*` before `+`) and parentheses. The correct answer is `11`, not `14`.

There are three equivalent forms of a mathematical expression:

```
Infix:    3 + 4 * 2     ← what humans write; operators sit between operands
Prefix:   + 3 * 4 2     ← operators come before operands (Polish notation)
Postfix:  3 4 2 * +     ← operators come after operands (Reverse Polish notation)
```

Postfix is closely related to how many compilers and stack-based virtual machines represent expressions internally, and it is simpler to evaluate than infix because there are no precedence rules left to resolve at evaluation time — the order of operations is already encoded in the sequence itself.

The full pipeline to evaluate an infix expression using a stack:

```
Infix string  →  [Infix to Postfix conversion]  →  Postfix string
                                                          │
                                               [Postfix Evaluation]
                                                          │
                                                        Result
```

Each stage uses a stack. We build them separately and then combine them.

---

### Stage 1: Postfix (Reverse Polish Notation) Evaluation

This is the simpler stage. Postfix needs no precedence rules: scan left to right, push operands, apply operators immediately.

**Algorithm:**

```
For each token in the postfix expression:
    If token is a number → push it
    If token is an operator:
        b = pop()   ← right operand (pushed more recently)
        a = pop()   ← left operand  (pushed earlier)
        push(a operator b)
At the end:
    pop() → the result
```

**Trace through `3 4 2 * +` (which equals `3 + 4 * 2 = 11`):**

```
Token   Action                                    Stack (top→bottom)
────────────────────────────────────────────────────────────────────
3       push 3                                    [3]
4       push 4                                    [4, 3]
2       push 2                                    [2, 4, 3]
*       b=pop()=2, a=pop()=4, push(4*2=8)         [8, 3]
+       b=pop()=8, a=pop()=3, push(3+8=11)        [11]

Result: pop() → 11 ✓
```

**Implementation:**

```python
def evaluate_postfix(expr):
    """
    Evaluate a postfix (Reverse Polish Notation) expression.
    Tokens must be separated by spaces.
    O(n) time — one pass through the token list.
    O(n) space — at most n/2 operands on the stack at any time.
    """
    s = Stack()

    operators = {
        '+':  lambda a, b: a + b,
        '-':  lambda a, b: a - b,
        '*':  lambda a, b: a * b,
        '/':  lambda a, b: int(a / b),    # Integer division truncated toward zero
        '**': lambda a, b: a ** b,
    }

    for token in expr.split():
        if token in operators:
            b = s.pop()                   # Right operand — pushed last
            a = s.pop()                   # Left operand  — pushed first
            s.push(operators[token](a, b))
        else:
            s.push(int(token))

    return s.pop()


print(evaluate_postfix("3 4 2 * +"))           # 3 + (4*2) = 11
print(evaluate_postfix("5 1 2 + 4 * + 3 -"))   # 5+((1+2)*4)-3 = 14
print(evaluate_postfix("2 3 ** 1 +"))           # 2**3 + 1 = 9
print(evaluate_postfix("10 2 8 * + 3 -"))       # 10+(2*8)-3 = 23
```

**Why does order of pops matter?**

When you see `-`, you pop `b` first (the number pushed most recently) and `a` second (pushed earlier). `a - b` is correct. If you reversed it and computed `b - a`, subtraction and division would give wrong results.

```
Expression: 10 3 -   (means 10 - 3 = 7)

Token   Stack
10      [10]
3       [3, 10]
-       b = pop() = 3
        a = pop() = 10
        a - b = 10 - 3 = 7   ✓
        (b - a = 3 - 10 = -7  ✗)
```

### Stage 2: Infix-to-Postfix Conversion — The Shunting-Yard Algorithm

This is the Dijkstra Shunting-Yard algorithm, designed in 1961. It converts a human-readable infix expression into postfix using a stack to hold operators until they can be correctly ordered.

**The rules of operator precedence and associativity:**

```
Operator   Precedence   Associativity
──────────────────────────────────────
**         3            Right  (a**b**c = a**(b**c))
* /        2            Left   (a*b*c = (a*b)*c)
+ -        1            Left   (a+b+c = (a+b)+c)
```

Higher precedence = binds more tightly = goes first.

**Algorithm:**

```
output_queue = []    ← tokens in postfix order
op_stack     = Stack()

For each token:

  If token is a NUMBER:
      → append directly to output_queue

  If token is an OPERATOR (call it op):
      While op_stack is not empty AND
            op_stack.peek() is not '(' AND
            (op_stack.peek() has higher precedence than op
             OR  (same precedence AND op is left-associative)):
          → pop from op_stack, append to output_queue
      Push op onto op_stack

  If token is '(':
      → push onto op_stack (acts as a barrier)

  If token is ')':
      While op_stack.peek() is not '(':
          → pop from op_stack, append to output_queue
      Pop and discard the '('   (do not add it to output)

After all tokens:
    Pop everything remaining from op_stack to output_queue
```

**Trace through `3 + 4 * 2` → expected postfix: `3 4 2 * +`**

```
Token   Action                          Output Queue      op_stack (top→bottom)
────────────────────────────────────────────────────────────────────────────────
3       number → output                 [3]               []
+       op_stack empty → push +         [3]               [+]
4       number → output                 [3, 4]            [+]
*       * has higher prec than +        [3, 4]            [*, +]
        → push * (do NOT pop +)
2       number → output                 [3, 4, 2]         [*, +]
end     pop * → output                  [3, 4, 2, *]      [+]
        pop + → output                  [3, 4, 2, *, +]   []

Postfix: "3 4 2 * +"    → evaluates to 11 ✓
```

**Trace through `3 + 4 * 2 - 1` → expected: `3 4 2 * + 1 -`**

```
Token   Action                          Output Queue          op_stack
─────────────────────────────────────────────────────────────────────────────
3       → output                        [3]                   []
+       → push                          [3]                   [+]
4       → output                        [3, 4]                [+]
*       higher than + → push            [3, 4]                [*, +]
2       → output                        [3, 4, 2]             [*, +]
-       prec 1, peek=* prec 2 → pop *   [3, 4, 2, *]          [+]
        prec 1, peek=+ prec 1,
        left-assoc → pop +              [3, 4, 2, *, +]       []
        push -                          [3, 4, 2, *, +]       [-]
1       → output                        [3, 4, 2, *, +, 1]    [-]
end     pop - → output                  [3, 4, 2, *, +, 1, -] []

Postfix: "3 4 2 * + 1 -"  → 3 + 4*2 - 1 = 10 ✓
```

**Trace through `( 3 + 4 ) * 2` → expected: `3 4 + 2 *`**

```
Token   Action                          Output Queue      op_stack
────────────────────────────────────────────────────────────────────────────
(       push (                          []                [(]
3       → output                        [3]               [(]
+       peek=( → push +                 [3]               [+, (]
4       → output                        [3, 4]            [+, (]
)       pop until ( : pop + → output    [3, 4, +]         [(]
        discard (                       [3, 4, +]         []
*       op_stack empty → push *         [3, 4, +]         [*]
2       → output                        [3, 4, +, 2]      [*]
end     pop * → output                  [3, 4, +, 2, *]   []

Postfix: "3 4 + 2 *"   → (3+4)*2 = 14 ✓
Compare: without parentheses: 3+4*2 = 11
Parentheses changed the result.
```

**Implementation:**

```python
def infix_to_postfix(expr):
    """
    Convert an infix expression to postfix using the Shunting-Yard algorithm.
    Tokens must be separated by spaces.
    Supports: +  -  *  /  **  and parentheses.
    O(n) time — each token is pushed and popped at most once.
    O(n) space — op_stack holds at most n operators.
    """
    precedence  = {'+': 1, '-': 1, '*': 2, '/': 2, '**': 3}
    right_assoc = {'**'}    # ** is right-associative; all others are left

    output   = []
    op_stack = Stack()

    for token in expr.split():

        if token not in precedence and token not in ('(', ')'):
            output.append(token)                          # Operand → output directly

        elif token == '(':
            op_stack.push(token)                          # Barrier for sub-expression

        elif token == ')':
            while not op_stack.is_empty() and op_stack.peek() != '(':
                output.append(op_stack.pop())             # Flush until matching (
            op_stack.pop()                                # Discard the '('

        else:                                             # token is an operator
            while (
                not op_stack.is_empty()
                and op_stack.peek() != '('
                and op_stack.peek() in precedence
                and (
                    precedence[op_stack.peek()] > precedence[token]
                    or (
                        precedence[op_stack.peek()] == precedence[token]
                        and token not in right_assoc
                    )
                )
            ):
                output.append(op_stack.pop())

            op_stack.push(token)

    while not op_stack.is_empty():                        # Flush remaining operators
        output.append(op_stack.pop())

    return ' '.join(output)


# Verify
cases = [
    ("3 + 4 * 2",             "3 4 2 * +",       11),
    ("( 3 + 4 ) * 2",         "3 4 + 2 *",       14),
    ("3 + 4 * 2 - 1",         "3 4 2 * + 1 -",   10),
    ("2 ** 3 ** 2",            "2 3 2 ** **",    512),   # Right-assoc: 2**(3**2)=512
    ("( 2 + 3 ) * ( 4 - 1 )", "2 3 + 4 1 - *",   15),
]

print("Infix → Postfix → Result")
for infix, expected_postfix, expected_result in cases:
    postfix = infix_to_postfix(infix)
    result  = evaluate_postfix(postfix)
    status  = "✓" if postfix == expected_postfix and result == expected_result else "✗"
    print(f"  {status}  {infix:30} → {postfix:20} = {result}")
```

### Stage 3: The Complete Infix Evaluator

Combining both stages: convert infix to postfix, then evaluate postfix.

```python
def evaluate_infix(expr):
    """
    Evaluate a fully infix expression with precedence and parentheses.
    O(n) time — two O(n) passes: conversion then evaluation.
    O(n) space — two stacks, each at most O(n).
    """
    postfix = infix_to_postfix(expr)
```

## Synthesis: How the Two Problems Connect

Parenthesis matching and expression evaluation are not independent applications. Expression evaluation **depends** on parenthesis matching.

```
( 3 + 4 ) * 2

    ↓
Infix-to-Postfix scan:

    When ) is encountered, flush operators until ( is found.
    This is exactly the parenthesis-matching pop loop.
    If there is no matching (, the expression is malformed.

    The Shunting-Yard algorithm implicitly validates parentheses
    as a side effect of its main operation.
```

If you add an explicit check — `raise ValueError` when a `)` is found with no `(` on the stack, or when the stack still holds a `(` at the end — you get parenthesis validation embedded inside expression evaluation at zero additional cost.

```python
def infix_to_postfix_validated(expr):
    """
    Infix to postfix with parenthesis validation built in.
    Raises ValueError with a descriptive message on malformed input.
    """
    precedence  = {'+': 1, '-': 1, '*': 2, '/': 2, '**': 3}
    right_assoc = {'**'}
    output      = []
    op_stack    = Stack()

    for token in expr.split():
        if token not in precedence and token not in ('(', ')'):
            output.append(token)

        elif token == '(':
            op_stack.push(token)

        elif token == ')':
            if op_stack.is_empty():
                raise ValueError(f"Unmatched ')' in expression: {expr!r}")
            while not op_stack.is_empty() and op_stack.peek() != '(':
                output.append(op_stack.pop())
            if op_stack.is_empty():
                raise ValueError(f"Unmatched ')' in expression: {expr!r}")
            op_stack.pop()    # Discard '('

        else:
            while (
                not op_stack.is_empty()
                and op_stack.peek() != '('
                and op_stack.peek() in precedence
                and (
                    precedence[op_stack.peek()] > precedence[token]
                    or (
                        precedence[op_stack.peek()] == precedence[token]
                        and token not in right_assoc
                    )
                )
            ):
                output.append(op_stack.pop())
            op_stack.push(token)

    while not op_stack.is_empty():
        op = op_stack.pop()
        if op == '(':
            raise ValueError(f"Unmatched '(' in expression: {expr!r}")
        output.append(op)

    return ' '.join(output)
```

## Consolidated Reference Implementation

```python
class Node:
    def __init__(self, data):
        self.data = data
        self.next = None


class Stack:
    def __init__(self):
        self.top   = None
        self._size = 0

    def push(self, data):
        node      = Node(data)
        node.next = self.top
        self.top  = node
        self._size += 1

    def pop(self):
        if self.is_empty():
            raise IndexError("pop from an empty stack")
        data     = self.top.data
        self.top = self.top.next
        self._size -= 1
        return data

    def peek(self):
        if self.is_empty():
            raise IndexError("peek from an empty stack")
        return self.top.data

    def is_empty(self):
        return self.top is None

    def __len__(self):
        return self._size

    def __repr__(self):
        elements, current = [], self.top
        while current:
            elements.append(repr(current.data))
            current = current.next
        return "Stack(top→bottom): [" + ", ".join(elements) + "]"


# ── PARENTHESIS MATCHING ──────────────────────────────────────────────────────

def is_balanced(expression):
    s        = Stack()
    matching = {')': '(', ']': '[', '}': '{'}
    openers  = set(matching.values())
    closers  = set(matching.keys())
    for ch in expression:
        if ch in openers:
            s.push(ch)
        elif ch in closers:
            if s.is_empty() or s.peek() != matching[ch]:
                return False
            s.pop()
    return s.is_empty()


def validate_brackets(expression):
    s        = Stack()
    matching = {')': '(', ']': '[', '}': '{'}
    openers  = set(matching.values())
    closers  = set(matching.keys())
    for pos, ch in enumerate(expression):
        if ch in openers:
            s.push((ch, pos))
        elif ch in closers:
            if s.is_empty():
                return False, f"Position {pos}: unexpected '{ch}' — no matching opener"
            top_ch, top_pos = s.peek()
            if top_ch != matching[ch]:
                return False, (
                    f"Position {pos}: '{ch}' does not match "
                    f"'{top_ch}' opened at position {top_pos}"
                )
            s.pop()
    if not s.is_empty():
        top_ch, pos = s.pop()
        return False, f"Position {pos}: '{top_ch}' was never closed"
    return True, None


# ── EXPRESSION EVALUATION ─────────────────────────────────────────────────────

def evaluate_postfix(expr):
    s         = Stack()
    operators = {
        '+': lambda a, b: a + b,
        '-': lambda a, b: a - b,
        '*': lambda a, b: a * b,
        '/': lambda a, b: int(a / b),
        '**': lambda a, b: a ** b,
    }
    for token in expr.split():
        if token in operators:
            b = s.pop()
            a = s.pop()
            s.push(operators[token](a, b))
        else:
            s.push(int(token))
    return s.pop()


def infix_to_postfix(expr):
    precedence  = {'+': 1, '-': 1, '*': 2, '/': 2, '**': 3}
    right_assoc = {'**'}
    output      = []
    op_stack    = Stack()
    for token in expr.split():
        if token not in precedence and token not in ('(', ')'):
            output.append(token)
        elif token == '(':
            op_stack.push(token)
        elif token == ')':
            while not op_stack.is_empty() and op_stack.peek() != '(':
                output.append(op_stack.pop())
            op_stack.pop()
        else:
            while (
                not op_stack.is_empty()
                and op_stack.peek() != '('
                and op_stack.peek() in precedence
                and (
                    precedence[op_stack.peek()] > precedence[token]
                    or (
                        precedence[op_stack.peek()] == precedence[token]
                        and token not in right_assoc
                    )
                )
            ):
                output.append(op_stack.pop())
            op_stack.push(token)
    while not op_stack.is_empty():
        output.append(op_stack.pop())
    return ' '.join(output)


def evaluate_infix(expr):
    return evaluate_postfix(infix_to_postfix(expr))
```

## Common Implementation Pitfalls

### Pitfall 1 — Checking Character Count Instead of Sequence

```python
# Wrong — counts match but order is violated
def wrong_balance(s):
    return s.count('(') == s.count(')')

print(wrong_balance(")("))    # True — but the sequence is wrong!
print(wrong_balance("([)]"))  # True — counts match but nesting is crossed
```

Counting is not sufficient. `)(` has equal counts but is invalid. `([)]` has one of each pair but is invalid. Only the stack enforces nesting order.

```python
# Correct — use the stack to enforce sequence
print(is_balanced(")("))      # False ✓
print(is_balanced("([)]"))    # False ✓
```

---

### Pitfall 2 — Forgetting the Empty-Stack Check Before `peek()`

```python
# Wrong — crashes on an extra closer
def broken_balance(expression):
    s = Stack()
    matching = {')': '(', ']': '[', '}': '{'}
    for ch in expression:
        if ch in matching.values():
            s.push(ch)
        elif ch in matching:
            # Missing empty check — IndexError when stack is empty
            if s.peek() != matching[ch]:
                return False
            s.pop()
    return s.is_empty()

broken_balance("}")    # IndexError — stack is empty when } is encountered
```

```python
# Correct — check empty before peek
elif ch in closers:
    if s.is_empty():              # Check first
        return False
    if s.peek() != matching[ch]:
        return False
    s.pop()
```

---

### Pitfall 3 — Wrong Operand Order in Postfix Evaluation

```python
s = Stack()
s.push(10)
s.push(3)

# Wrong — reversed operand order
a = s.pop()    # 3  ← popped first, but this is the RIGHT operand
b = s.pop()    # 10 ← popped second, but this is the LEFT operand
print(a - b)   # 3 - 10 = -7   ✗

# Correct — name them by role, not by pop order
b = s.pop()    # Right operand — pushed last
a = s.pop()    # Left operand  — pushed first
print(a - b)   # 10 - 3 = 7    ✓
```

The mnemonic: **b before a**. Pop `b` (right) first, then `a` (left).

---

### Pitfall 4 — Adding the Parenthesis to the Postfix Output

```python
# Wrong — '(' ends up in the postfix output
def wrong_infix_to_postfix(expr):
    output   = []
    op_stack = Stack()
    for token in expr.split():
        if token == ')':
            while op_stack.peek() != '(':
                output.append(op_stack.pop())
            output.append(op_stack.pop())   # ← appends '(' to output — wrong!
    return ' '.join(output)
```

Parentheses are **structural only**. They control the order operators are flushed, but they never appear in the postfix output. Pop and discard the `(` — never append it.

```python
# Correct
if token == ')':
    while op_stack.peek() != '(':
        output.append(op_stack.pop())
    op_stack.pop()    # ← Discard '(' — do NOT append it
```

---

### Pitfall 5 — Ignoring Associativity for Right-Associative Operators

```python
# Exponentiation is right-associative:
# 2 ** 3 ** 2  means  2 ** (3 ** 2) = 2 ** 9 = 512
# NOT  (2 ** 3) ** 2 = 8 ** 2 = 64

# Wrong — treating ** as left-associative pops it when precedence is equal
# Converts "2 ** 3 ** 2" to "2 3 ** 2 **" → (2**3)**2 = 64  ✗

# Correct — for equal precedence, pop only if left-associative
while (
    not op_stack.is_empty()
    and op_stack.peek() in precedence
    and (
        precedence[op_stack.peek()] > precedence[token]
        or (
            precedence[op_stack.peek()] == precedence[token]
            and token not in right_assoc    # ← This condition is essential
        )
    )
):
    output.append(op_stack.pop())
```

```python
# Verify
print(evaluate_infix("2 ** 3 ** 2"))    # 512 ✓  (right-assoc)
print(2 ** 3 ** 2)                       # 512 ✓  (Python's own result)
```

---

### Pitfall 6 — Not Flushing the Operator Stack at the End

```python
# Wrong — remaining operators are abandoned after the main loop
def incomplete_infix_to_postfix(expr):
    output   = []
    op_stack = Stack()
    for token in expr.split():
        pass   # main loop logic ...
    # Missing: flush the op_stack
    return ' '.join(output)

incomplete_infix_to_postfix("3 + 4")
# After loop: output=['3','4'], op_stack still holds ['+']
# Returns '3 4' — operator lost entirely ✗
```

```python
# Correct — flush what remains after the main loop
while not op_stack.is_empty():
    output.append(op_stack.pop())
# output: ['3', '4', '+'] → '3 4 +' ✓
```

## Linked-List Stack Versus Python's deque

| Property | Linked-list Stack | `collections.deque` |
|---|---|---|
| Push | O(1) always | O(1) always |
| Pop | O(1) always | O(1) always |
| Peek | O(1) — `top.data` | O(1) — `deque[-1]` |
| Memory released on pop | Immediately — node freed | Not immediately — block retained |
| No array pre-allocation | ✓ — one node per element | ✗ — block-allocated internally |
| Practical for these problems | Both work identically | Both work identically |
| Production Python choice | Teaching and custom builds | Preferred for speed |

For parenthesis matching and expression evaluation, both choices produce identical results and identical time complexity. The linked-list stack is used here because it continues directly from the previous topic and makes every operation's O(1) cost explicit and visible.

## Applications in Real Systems

**Code Editors and IDEs**

Every editor that highlights mismatched brackets — VS Code, PyCharm, IntelliJ, Vim — uses a bracket-matching algorithm built on the same LIFO discipline as Part I. The cursor position gives the character index; the stack gives the matching position to highlight.

**Compilers and Interpreters**

CPython does not literally run the Shunting-Yard algorithm — since Python 3.9 it parses source code with a PEG grammar into an abstract syntax tree — but that tree is then compiled into bytecode for a stack-based virtual machine, so arithmetic ends up in exactly the postfix order Stage 2 produces. For `a + b * c`, CPython emits (in order) *load a, load b, load c, multiply, add* — push the operands, apply the operators, precisely the `evaluate_postfix` pattern. The JVM is built the same way for the same reason: postfix order is what a stack-based instruction set naturally wants. Real-world parsers more often use recursive-descent or precedence-climbing techniques — close relatives of Shunting-Yard that solve the same operator-ordering problem — to build the tree that eventually gets compiled down to this stack-oriented form.

**Scientific and Financial Calculators**

Reverse Polish Notation traces back to Jan Łukasiewicz's parenthesis-free Polish (prefix) notation from 1924. The reversed, postfix form was proposed in 1954 and extended for computing use by the Australian logician Charles Hamblin in the mid-1950s. Hewlett-Packard did not invent RPN, but adopted it starting with the HP-9100A desktop calculator (1968) and made it famous with the pocket-sized HP-35 (1972). Users entered expressions in postfix directly — push operands, then operators — and never needed parentheses. The `evaluate_postfix` function from Stage 1 is essentially the algorithm those calculators use internally to resolve what you key in.

**Spreadsheet Formula Parsers**

When a spreadsheet evaluates a formula such as `=SUM(A1*(B2+C3))`, it tokenizes the expression and resolves operator precedence and parenthesis nesting before computing a result — the same class of problem Stage 2 solves. It is also why an unbalanced formula like `=SUM(A1*(B2+C3)` is rejected immediately: the same parenthesis-tracking discipline used in `infix_to_postfix_validated` is what catches the error before any arithmetic is attempted.

**Regular Expression Engines**

A pattern like `(a(b|c)*d)+` contains a group nested inside another group. Parsing nested groups requires the identical discipline as Part I: meeting an unexpected `)`, or reaching the end of the pattern with a group still open, is the same failure mode as an unmatched bracket. Python's `re` module surfaces exactly this as `re.error: missing ), unterminated subpattern` when a group is opened but never closed.

## Topic Summary

| Concept | What It Means |
|---|---|
| LIFO enforces nesting | The most recently opened bracket must be closed first — exactly what a stack provides |
| Opening bracket | Push it — remember it for later matching |
| Closing bracket | Pop and compare — if the types mismatch or the stack is empty, the expression is invalid |
| Empty stack at end | All openers were matched — the expression is valid |
| Postfix notation | Operators follow their operands — no precedence rules needed at evaluation time |
| Postfix evaluation | Scan left to right: push numbers, pop two operands and push result on every operator |
| Pop order in postfix | First pop is the right operand (`b`), second pop is the left operand (`a`) |
| Shunting-Yard | Converts infix to postfix using an operator stack — O(n) time, O(n) space |
| Precedence | Higher-precedence operators bind first — `*` before `+` |
| Left-associativity | Same-precedence operators bind left to right — `a - b - c` = `(a-b)-c` |
| Right-associativity | `**` binds right to left — `a ** b ** c` = `a**(b**c)` |
| Parentheses in Shunting-Yard | Push `(` as a barrier; on `)` flush operators until `(` is found and discard it |
| All core operations | O(1) per token — full conversion and evaluation in O(n) |

The stack's LIFO order is not a coincidence in either of these problems. Nesting structure — in brackets, in expressions, in function calls — has an inherent LIFO shape: the innermost thing must resolve before the outer thing can continue. The stack captures this shape directly, turning problems that look complex into single-pass, O(n) algorithms.
