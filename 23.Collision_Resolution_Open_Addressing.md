# Open Addressing — Linear Probing, Quadratic Probing, Double Hashing

---

## Before We Begin — What Problem Are We Even Solving?

Imagine you arrive at a cinema and your reserved seat — Row 3, Seat 7 — is already taken by someone who sat in the wrong place.

You have two choices:

**Option A:** Call the manager, set up a folding chair in the aisle next to seat 7, and seat everyone who gets displaced there in a little cluster. *(That's Chaining — the previous topic.)*

**Option B:** Keep your ticket, look at the seats around you, and simply sit in the **next available seat** in the same row. You're still in the cinema, still in your row — just shifted a little. *(That's Open Addressing.)*

Open Addressing means: when a collision happens, **don't go outside the array**. Instead, probe — look for another empty slot **within the same array** — and place the entry there.

No linked lists. No extra memory. Everything lives inside the original array.

---

## A Quick Recap — Where We Left Off

In the previous topic, we learned that a **hash table** stores key-value pairs by computing:

```
index = hash(key) % table_size
```

And when two keys produce the same index — a **collision** — Chaining resolved it by attaching a linked list to that slot.

Open Addressing takes a completely different approach:

> *"If slot `i` is taken, I'll look at slot `i+1`. Or `i+4`. Or some other slot — but I'll find one inside the array itself."*

The sequence of slots you examine is called a **probe sequence**. The three major strategies for generating that sequence are:

- **Linear Probing** — check the next slot, then the next, then the next...
- **Quadratic Probing** — check slots at increasing quadratic distances
- **Double Hashing** — use a second hash function to decide the step size

Each strategy is a different answer to the same question: *"When slot `i` is taken, which slot do I try next?"*

---

## The Core Mechanic — What "Probing" Means

Before diving into each strategy, understand the shared mechanic.

Every Open Addressing table has three possible states for each slot:

```
┌──────────┐
│  EMPTY   │  ← Never been used. Searching stops here (key definitely not present).
└──────────┘

┌──────────┐
│ OCCUPIED │  ← Holds a live (key, value) pair.
└──────────┘

┌──────────┐
│  DELETED │  ← Was occupied, now deleted. A "tombstone."
│(tombstone│    Searching must CONTINUE past this — the key we want
│  marker) │    might be further along the probe sequence.
└──────────┘
```

The tombstone is the trickiest concept in Open Addressing and the reason deletion is harder here than in Chaining. We'll come back to it in detail.

---

## Strategy 1 — Linear Probing

### The Idea

*"If slot `i` is taken, try slot `i+1`. If that's taken, try `i+2`. Keep going until you find an empty slot."*

The probe sequence is:

```
i, i+1, i+2, i+3, ...  (all mod table_size)
```

Formally: slot to try on the `k`-th probe = `(hash(key) + k) % size`

### A Concrete Walk-Through

Table size = 7. We insert five keys.

```
hash("Alice")   % 7 = 3
hash("Bob")     % 7 = 0
hash("Charlie") % 7 = 3   ← collision with Alice
hash("Dave")    % 7 = 4   ← collision with Charlie's landing spot
hash("Eve")     % 7 = 0   ← collision with Bob
```

Let's insert them one by one and trace what happens:

**Insert "Alice" → index 3 (empty → place here)**
```
[ _, _, _, Alice, _, _, _ ]
  0  1  2    3   4  5  6
```

**Insert "Bob" → index 0 (empty → place here)**
```
[ Bob, _, _, Alice, _, _, _ ]
```

**Insert "Charlie" → index 3 (TAKEN by Alice)**
```
Try index 3 → occupied
Try index 4 → empty → place Charlie here
[ Bob, _, _, Alice, Charlie, _, _ ]
```

**Insert "Dave" → index 4 (TAKEN by Charlie)**
```
Try index 4 → occupied
Try index 5 → empty → place Dave here
[ Bob, _, _, Alice, Charlie, Dave, _ ]
```

**Insert "Eve" → index 0 (TAKEN by Bob)**
```
Try index 0 → occupied
Try index 1 → empty → place Eve here
[ Bob, Eve, _, Alice, Charlie, Dave, _ ]
```

Final table state:
```
Index:  0     1    2      3        4        5     6
      [ Bob, Eve, None, Alice, Charlie,  Dave, None ]
```

### Searching with Linear Probing

To find "Charlie":

```
Compute hash("Charlie") % 7 = 3
Look at index 3 → "Alice" — not Charlie, keep probing
Look at index 4 → "Charlie" — FOUND! Return value.
```

To confirm "Frank" is not in the table:

```
Compute hash("Frank") % 7 = 5
Look at index 5 → "Dave"   — not Frank, keep probing
Look at index 6 → None     — EMPTY! Stop. "Frank" is not here.
```

The search stops at the first `None` (truly empty slot). If we hit a tombstone, we keep going.

### The Big Problem — Primary Clustering

Linear Probing has a nasty side effect called **primary clustering**.

Because every collision resolves by stepping +1, long consecutive runs of occupied slots build up. And a long run means every new key that hashes *anywhere into that run* makes the run even longer.

```
Before:    [ _, _, _, Alice, Charlie, Dave, _ ]
                         ← cluster of 3 →

After inserting more keys that hash to 3, 4, or 5:
           [ _, _, _, Alice, Charlie, Dave, X, Y, Z ]
                         ← cluster grows to 6 →
```

This is not random scatter — it is a self-reinforcing pile-up. The longer the cluster, the more likely new insertions land inside it, which makes it longer still.

**Primary clustering degrades average search time from O(1) to O(n) in the worst case.**

## Strategy 2 — Quadratic Probing

### The Idea

*"If slot `i` is taken, don't just step by 1 — jump by squares: 1², 2², 3²... This spreads collisions out and breaks up clusters."*

The probe sequence is:

```
i, i+1², i+2², i+3², ...  (all mod table_size)
```

Formally: slot to try on the `k`-th probe = `(hash(key) + k²) % size`

### The Same Walk-Through, with Quadratic Probing

Same keys, same hashes. Table size = 7.

**Insert "Alice" → index 3 (empty → place here)**
```
[ _, _, _, Alice, _, _, _ ]
```

**Insert "Charlie" → index 3 (TAKEN)**
```
k=1: try (3 + 1²) % 7 = 4 → empty → place Charlie here
[ _, _, _, Alice, Charlie, _, _ ]
```

**Insert "Dave" → index 4 (TAKEN)**
```
k=1: try (4 + 1²) % 7 = 5 → empty → place Dave here
[ _, _, _, Alice, Charlie, Dave, _ ]
```

**Insert "Eve" → index 0 (TAKEN by Bob)**
```
k=1: try (0 + 1²) % 7 = 1 → empty → place Eve here
[ Bob, Eve, _, Alice, Charlie, Dave, _ ]
```

Same final positions in this particular example — but with more keys and more collisions, the quadratic jumps scatter entries much more evenly than the linear +1 step.

### Secondary Clustering — A Smaller Problem

Quadratic Probing solves primary clustering, but introduces a milder version called **secondary clustering**:

> Two keys that hash to the *same initial index* will follow the *exact same probe sequence* (i+1, i+4, i+9...) and compete at every step.

They don't collide with the whole neighbourhood like in linear probing — but they still collide with each other. This is less severe, but not zero.

### An Important Limitation — Not All Slots Are Guaranteed to Be Reached

With linear probing, if you probe long enough, you will visit every slot. Guaranteed.

With quadratic probing, you are **not** guaranteed to visit every slot — depending on the table size. If the table is half-full and some probe sequences cycle without covering all slots, an insertion could fail even though empty slots exist.

**Fix: Use a prime table size and keep load factor α < 0.5.** Under these conditions, quadratic probing is guaranteed to find an empty slot within at most `size/2` probes.

## Strategy 3 — Double Hashing

### The Idea

*"If slot `i` is taken, don't use a fixed step — compute the step size using a second, independent hash function. Different keys get different step sizes, so their probe sequences diverge."*

The probe sequence is:

```
i, i + h₂(key), i + 2·h₂(key), i + 3·h₂(key), ...  (all mod table_size)
```

Formally: slot to try on the `k`-th probe = `(h₁(key) + k · h₂(key)) % size`

Where:
- `h₁(key) = hash(key) % size`  — the primary hash (determines the starting slot)
- `h₂(key)` — the secondary hash (determines the step size)

### Choosing h₂ Carefully

The secondary hash function must never return 0 — a step size of 0 means you'd probe the same slot forever.

A commonly used formula:

```python
h2 = lambda key, size: 1 + (hash(key) % (size - 1))
```

This always returns a value between 1 and `size - 1`. It also works best when `size` is prime, which ensures the probe sequence visits all slots before repeating.

### The Same Walk-Through, with Double Hashing

Let's say:
- `h₁(key) = hash(key) % 7`
- `h₂(key) = 1 + (hash(key) % 6)`

For our colliding keys:
```
h₁("Charlie") = 3,  h₂("Charlie") = 4
h₁("Dave")    = 4,  h₂("Dave")    = 2
```

**Insert "Charlie" → index 3 (TAKEN by Alice)**
```
k=1: try (3 + 1·4) % 7 = 0 → occupied by Bob
k=2: try (3 + 2·4) % 7 = 4 → occupied by Charlie... wait
```

*(In a real trace, "Dave" may not yet be inserted — the point is the step size is now unique per key, so "Charlie" and "Dave" follow completely different probe paths even though they started at the same index.)*

**The key insight:**
```
Linear Probing:    "Charlie" and "Dave" both step +1 → compete at every slot
Quadratic Probing: "Charlie" and "Dave" both follow i+1,i+4,i+9 → compete at every step
Double Hashing:    "Charlie" steps by 4 → visits 3, 0, 4, 1, 5...
                   "Dave"    steps by 2 → visits 4, 6, 1, 3, 5...
                   Their paths diverge after the first collision. No clustering.
```

Double Hashing essentially **eliminates both primary and secondary clustering**. Keys spread independently based on their own computed step size.

## The Tombstone Problem — Why Deletion Is Hard

This is the most important concept that separates Open Addressing from Chaining.

In Chaining, deletion is clean: unlink the node, done.

In Open Addressing, you cannot simply blank out a slot when deleting. Here's why:

```
Table after several insertions (Linear Probing):

Index:  0     1      2      3        4      5     6
      [ Bob, Eve,  None, Alice,  Charlie, Dave, None ]

Suppose we search for "Charlie":
  hash("Charlie") % 7 = 3
  index 3 → "Alice" — not Charlie, probe next
  index 4 → "Charlie" — FOUND ✓

Now suppose we DELETE "Bob" at index 0, replacing it with None:

Index:  0     1      2      3        4      5     6
      [None, Eve,  None, Alice,  Charlie, Dave, None ]

Now search for "Eve":
  hash("Eve") % 7 = 0
  index 0 → None — STOP. Search thinks "Eve" is not here.
  But Eve IS at index 1! We just can't reach her.
```

Deleting a live entry and replacing it with `None` **breaks the probe chain** for every key that was placed downstream of it.

### The Fix — Tombstones

Instead of replacing a deleted entry with `None`, replace it with a special **DELETED** marker (tombstone):

```python
DELETED = object()   # A unique sentinel object — not None, not a real key
```

Rules:
- During **search**: treat `DELETED` as "keep probing" (same as OCCUPIED for search purposes).
- During **insertion**: treat `DELETED` as "available — you can place a new entry here."
- During **deletion**: replace the entry with `DELETED`, never with `None`.

```
After correctly deleting "Bob" with a tombstone:

Index:  0          1      2      3        4      5     6
      [DELETED,  Eve,  None, Alice,  Charlie, Dave, None ]

Search for "Eve":
  hash("Eve") % 7 = 0
  index 0 → DELETED — keep probing
  index 1 → "Eve"   — FOUND ✓
```

The probe chain is intact. "Eve" is still reachable.

## Implementation — All Three Strategies in Python

Let's build a clean, complete hash table that supports all three probing strategies.

```python
class OpenAddressHashTable:

    DELETED = object()   # Unique tombstone sentinel

    def __init__(self, size=11, strategy="linear"):
        self.size     = size
        self.strategy = strategy          # "linear", "quadratic", "double"
        self.keys     = [None] * size     # Slot holds the key (or None or DELETED)
        self.values   = [None] * size     # Corresponding values
        self.count    = 0

    # ── Hash Functions ──────────────────────────────────────────────────────

    def _h1(self, key):
        return hash(key) % self.size

    def _h2(self, key):
        # Step size for double hashing — always between 1 and size-1
        return 1 + (hash(key) % (self.size - 1))

    # ── Probe Sequence Generator ─────────────────────────────────────────────

    def _probe(self, key):
        """Yield slot indices to try, in order, for the given key."""
        start = self._h1(key)
        step  = self._h2(key) if self.strategy == "double" else 1

        for k in range(self.size):
            if self.strategy == "linear":
                yield (start + k) % self.size
            elif self.strategy == "quadratic":
                yield (start + k * k) % self.size
            elif self.strategy == "double":
                yield (start + k * step) % self.size

    # ── Insertion ────────────────────────────────────────────────────────────

    def insert(self, key, value):
        first_deleted = None   # Track first tombstone seen (reuse it for insertion)

        for slot in self._probe(key):
            if self.keys[slot] is None:
                # Truly empty — use this slot (or reuse tombstone if we saw one)
                target = first_deleted if first_deleted is not None else slot
                self.keys[target]   = key
                self.values[target] = value
                self.count += 1
                return

            elif self.keys[slot] is self.DELETED:
                # Tombstone — remember it but keep looking (key might exist further along)
                if first_deleted is None:
                    first_deleted = slot

            elif self.keys[slot] == key:
                # Key already exists — update in place
                self.values[slot] = value
                return

        # Table is full — this should not happen with proper load factor management
        raise Exception("Hash table is full")

    # ── Search ───────────────────────────────────────────────────────────────

    def search(self, key):
        for slot in self._probe(key):
            if self.keys[slot] is None:
                return None                    # Truly empty — key not present

            elif self.keys[slot] is self.DELETED:
                continue                       # Tombstone — keep probing

            elif self.keys[slot] == key:
                return self.values[slot]       # Found it

        return None

    # ── Deletion ─────────────────────────────────────────────────────────────

    def delete(self, key):
        for slot in self._probe(key):
            if self.keys[slot] is None:
                return False                   # Key not in table

            elif self.keys[slot] is self.DELETED:
                continue                       # Skip tombstones

            elif self.keys[slot] == key:
                self.keys[slot]   = self.DELETED   # Place tombstone
                self.values[slot] = None
                self.count -= 1
                return True

        return False

    # ── Display ──────────────────────────────────────────────────────────────

    def display(self):
        for i in range(self.size):
            k = self.keys[i]
            if k is None:
                print(f"  [{i}] → EMPTY")
            elif k is self.DELETED:
                print(f"  [{i}] → DELETED (tombstone)")
            else:
                print(f"  [{i}] → ({k!r}: {self.values[i]!r})")

    def load_factor(self):
        return self.count / self.size
```

### Running It

```python
# Test with Linear Probing
ht = OpenAddressHashTable(size=11, strategy="linear")

ht.insert("Alice",   "555-1234")
ht.insert("Bob",     "555-5678")
ht.insert("Charlie", "555-9999")
ht.insert("Dave",    "555-0001")
ht.insert("Eve",     "555-4321")

print("=== Linear Probing Table ===")
ht.display()

print("\nSearch 'Charlie':", ht.search("Charlie"))
print("Search 'Zara':",    ht.search("Zara"))

ht.delete("Bob")
print("\n=== After Deleting 'Bob' ===")
ht.display()

print("\nSearch 'Eve' after deletion:", ht.search("Eve"))
# Eve is still findable — the tombstone at Bob's old slot keeps the probe chain intact
```

## Visualising the Three Probe Sequences

Same starting index. Same collision. Three completely different paths.

```
Table size = 13. Key "X" hashes to index 5. Key "Y" also hashes to index 5.
h₂("Y") = 4 (for double hashing example)

LINEAR PROBING (step = 1):
  "Y" probes:  5 → 6 → 7 → 8 → 9 → 10 → ...
                   ↑ a straight march through the array

QUADRATIC PROBING (step = k²):
  "Y" probes:  5 → 6 → 9 → 14%13=1 → 21%13=8 → ...
                   ↑ increasing jumps, skips over regions

DOUBLE HASHING (step = h₂("Y") = 4):
  "Y" probes:  5 → 9 → 0 → 4 → 8 → 12 → 3 → ...
                   ↑ uniform jumps, uniquely sized per key
```

| Strategy | Step Formula | Cluster Type | Clustering Severity |
|---|---|---|---|
| Linear Probing | `+1` | Primary — long runs | Worst |
| Quadratic Probing | `+k²` | Secondary — same start index | Mild |
| Double Hashing | `+k · h₂(key)` | Nearly none | Best |

## Time Complexity

Let α = n/m = load factor. All three strategies share the same complexity class:

| Operation | Average Case | Worst Case |
|---|---|---|
| Insert | O(1 / (1 − α)) | O(n) |
| Search (hit) | O(1 / (1 − α)) | O(n) |
| Search (miss) | O(1 / (1 − α)²) | O(n) |
| Delete | O(1 / (1 − α)) | O(n) |

The formula `1 / (1 − α)` tells you everything:

```
α = 0.5  → 1 / 0.5  = 2.0    → about 2 probes on average — fast
α = 0.7  → 1 / 0.3  ≈ 3.3    → still reasonable
α = 0.9  → 1 / 0.1  = 10.0   → 10 probes average — slowing badly
α = 0.99 → 1 / 0.01 = 100.0  → essentially O(n)
α = 1.0  → 1 / 0    = ∞      → impossible — table is full
```

**This is why Open Addressing requires α < 1.0 at all times.** The table must always have empty slots, or insertion never terminates.

A typical threshold for resizing is **α = 0.7** (resize at 70% full).

---

## The Load Factor Wall — Open Addressing vs. Chaining

This is the fundamental difference between the two approaches:

```
Chaining:
  α can exceed 1.0 — chains just grow longer
  Performance degrades gracefully
  Table NEVER gets "full" in a strict sense

Open Addressing:
  α MUST stay below 1.0 — there must always be empty slots
  Performance degrades sharply as α → 1.0
  Table becomes completely unusable at α = 1.0
```

```
Performance vs. Load Factor (approximate):

                │ Open Addressing
  Probes        │         ___________∞
  per           │       /
  operation     │     /
                │   /
              3 │ /
              2 │/_____________________________ Chaining (grows linearly)
              1 ├────────────────────────────
                0   0.25  0.5   0.75  1.0
                              α (load factor)
```

Chaining degrades gently. Open Addressing degrades gently up to about 0.7, then plummets.

## Common Mistakes Beginners Make

### Mistake 1 — Deleting with None Instead of a Tombstone

```python
# WRONG — breaks the probe chain
def wrong_delete(table, key):
    slot = find_slot(table, key)
    table[slot] = None       # ← This cuts the chain for anyone probed past here

# CORRECT — preserve the chain
def correct_delete(table, key):
    slot = find_slot(table, key)
    table[slot] = DELETED    # ← A tombstone — search skips it, insertion reuses it
```

This is the most common Open Addressing bug. The symptom is mysterious: some keys become "unfindable" after you delete a seemingly unrelated key.

---

### Mistake 2 — Letting the Table Fill Up

```python
# WRONG — no resize check
ht = OpenAddressHashTable(size=7)
for i in range(7):
    ht.insert(f"key_{i}", i)    # ← Table is now 100% full

ht.insert("one_more", 99)       # ← Infinite loop — no empty slot exists
```

Always resize before the table reaches 70–75% capacity.

---

### Mistake 3 — Using a Non-Prime Table Size with Quadratic Probing

```python
# Can fail — non-prime size means the probe sequence may cycle
# and miss valid empty slots
ht = OpenAddressHashTable(size=8, strategy="quadratic")

# With size=8, the quadratic sequence from index 0:
# 0, 1, 4, 9%8=1, 16%8=0, ...  ← cycles! Only visits 4 distinct slots out of 8
# An insertion can fail even though 4 slots are empty.

# Fix: use a prime size (7, 11, 13, 17, 19, 23...)
ht = OpenAddressHashTable(size=11, strategy="quadratic")
```

Prime-sized tables guarantee that quadratic probing visits at least `size/2` distinct slots.

---

### Mistake 4 — h₂(key) Returning 0 in Double Hashing

```python
# WRONG secondary hash — can return 0
def bad_h2(key, size):
    return hash(key) % size    # ← If this returns 0, step size = 0 → infinite loop

# CORRECT — guarantee step size is between 1 and size-1
def good_h2(key, size):
    return 1 + (hash(key) % (size - 1))   # ← Always ≥ 1
```

A step size of 0 means `(start + k * 0) % size = start` for all `k` — you probe the same slot forever.

---

### Mistake 5 — Searching Past a True None (False "Not Found")

```python
# A None means "this slot was NEVER occupied" — stop searching here.
# A DELETED tombstone means "was occupied, now gone" — keep probing.

# Confusing the two causes you to miss keys that were placed
# further along the probe sequence from a now-deleted slot.
```

This is why the two markers — `None` and `DELETED` — must be distinct objects. They mean completely different things to the search algorithm.

## Comparison — All Three Strategies Side by Side

| Property | Linear Probing | Quadratic Probing | Double Hashing |
|---|---|---|---|
| Probe formula | `(h + k) % m` | `(h + k²) % m` | `(h + k·h₂) % m` |
| Primary clustering | Yes — severe | No | No |
| Secondary clustering | No | Yes — mild | No |
| Cache performance | Best (sequential) | Medium | Worst (scattered) |
| Guaranteed coverage | Yes | Only with prime size & α < 0.5 | Yes (with prime size) |
| Implementation complexity | Simplest | Moderate | Requires second hash fn |
| Best use case | Small tables, cache speed matters | General use | Minimising collisions, large tables |

**Practical rule of thumb:**

- If you want simplicity and your table is small → **Linear Probing**
- If you want a balance of performance and simplicity → **Quadratic Probing**
- If you want the best distribution and can afford two hash functions → **Double Hashing**

## Open Addressing vs. Chaining — The Full Picture

You've now studied both collision strategies. Here's how to think about the choice:

| Aspect | Open Addressing | Chaining |
|---|---|---|
| Memory layout | All data in one array — cache-friendly | Extra nodes scattered on heap — cache-unfriendly |
| Load factor limit | Must stay below 1.0 | Can exceed 1.0 |
| Deletion | Hard — requires tombstones | Easy — just unlink the node |
| Memory overhead | No extra pointers | One `next` pointer per node |
| Worst case | O(n) with high α or bad hash | O(n) with all keys in one bucket |
| Best use case | Known, bounded key sets; cache speed | Dynamic, unpredictable key sets |

---

## Where You'll See This in Real Life

Open Addressing is used whenever memory compactness and cache performance matter more than flexibility:

- **Python `dict` (modern CPython)** — Uses open addressing with a compact representation. Python's dictionary is one of the most carefully optimised open-addressing tables ever built, with custom probe sequences that exploit CPU caches.

- **Python `set`** — Same implementation as `dict` but stores only keys, not values. All collision resolution is open addressing.

- **Google's `absl::flat_hash_map`** — The flagship C++ hash map in Google's Abseil library. Pure open addressing with linear probing. Powers vast amounts of Google's infrastructure.

- **Rust's `HashMap`** — Uses Robin Hood Hashing, a variant of linear probing where richer keys steal slots from poorer ones to equalise probe lengths.

- **C++ `std::unordered_map`** — Typically implemented as chaining, but many modern replacements (like `absl::flat_hash_map`) use open addressing for its cache advantages.

- **DNS resolvers** — Fast, memory-compact caches for domain-to-IP mappings often use open addressing tables with double hashing.

## Summary

| Concept | What It Means |
|---|---|
| Open Addressing | Resolve collisions inside the array — no external lists |
| Probe sequence | The ordered series of slots examined after a collision |
| Linear Probing | Step by +1 each time — simple but causes primary clustering |
| Quadratic Probing | Step by k² each time — breaks primary clusters, mild secondary clusters |
| Double Hashing | Step by `k · h₂(key)` — unique steps per key, near-zero clustering |
| Tombstone (`DELETED`) | A marker for deleted slots — keeps probe chains intact |
| Load factor wall | Performance collapses as α → 1.0; always resize before 0.75 |

## What Comes After This?

You have now studied both major collision resolution families. Here is the complete picture of where these fit in the hash table world:

```
Hash Table Collision Resolution
 │
 ├──► Chaining                         (previous topic)
 │         └── Each slot holds a linked list of nodes
 │
 └──► Open Addressing                  (this topic)
           │
           ├── Linear Probing          step = +1
           ├── Quadratic Probing       step = +k²
           └── Double Hashing         step = +k · h₂(key)

Advanced variants built on these foundations:
 ├── Robin Hood Hashing   (linear probing + fairness balancing)
 ├── Cuckoo Hashing       (two hash functions, entries can be evicted and re-placed)
 └── Hopscotch Hashing    (open addressing in bounded neighbourhoods)
```
