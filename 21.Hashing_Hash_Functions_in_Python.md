# Hashing and Hash Functions in Python

---

## 1. Introduction

The company has grown to 10,000 employees.

HR receives hundreds of queries every day:

- *"Does an employee named Alice work here?"*
- *"What is Bob's department?"*
- *"Is employee ID 4821 still active?"*

The CEO calls a meeting. The CTO presents three options:

**Option A — Unsorted List:** Store all 10,000 employees in a plain list. To find Alice, scan from the beginning. Worst case: 10,000 comparisons. Unacceptable.

**Option B — Binary Search Tree:** Keep employees sorted by name. Find Alice in at most 14 comparisons (log₂ 10,000 ≈ 14). Good — but every new hire requires finding the correct insertion position. And if employees join in alphabetical order, the BST skews into a straight line.

**Option C — Hash Table:** Convert Alice's name into a number using a formula. Use that number as the array index. Go directly to that index. Find Alice in **1 step** — regardless of whether there are 10 employees or 10 million.

Option C is not magic. It is mathematics. That formula — the one that converts a name into an index — is called a **hash function**. And the structure it powers is called a **hash table**.

Before diving in, let us be honest and try every structure you already know on this exact problem — and see precisely where each one breaks.

**Array / Python List** stores employees at indices 0, 1, 2, 3... There is no relationship between an employee's name and their index. Finding Alice means scanning every slot — O(n). Inserting in sorted order to enable binary search costs O(n) per insertion due to shifting.

**Stack** is last in, first out. To check if Alice exists, you pop everyone above her — and destroy the stack in the process. Structurally wrong for lookup.

**Queue** is first in, first out. Alice could be anywhere in the queue. You dequeue everyone ahead of her just to check. Same problem as the stack.

**Singly Linked List** requires walking the chain from the head node. No index, no shortcut, no way to jump. Finding Alice in a list of 10,000 employees is 10,000 pointer dereferences in the worst case.

**Binary Search Tree** gives O(log n) search — much better. But it still requires multiple comparisons and is sensitive to insertion order. It also cannot answer *"does this exact key exist?"* in one step.

**The shared failure of all five:** they require you to *search* for an element. You arrive not knowing where it is and must navigate toward it. None of them can directly compute *where* an element must be from the element itself.

A hash function breaks this pattern entirely. It does not search — it **calculates**. Given an employee name, it computes a precise storage location in O(1) time. The name itself tells you exactly where to look.

## 2. Real-World Applications

Hashing is everywhere — often invisibly.

**Company Employee Database**

HR stores 10,000 employee records. Given any employee ID or name, the system must respond in under a millisecond. No BST, no scan — a hash table maps the ID directly to the employee's record slot.

**Python Dictionaries**

Every Python `dict` is a hash table. When you write `employee["Alice"]`, Python hashes the string `"Alice"`, computes an index, and retrieves the value in O(1). This is why dictionary lookups are always fast regardless of size.

**Password Storage**

When you set a password, the system does not store the password itself. It stores `hash(password)`. When you log in, it hashes your input and compares hashes. The original password never touches the database — even if the database is stolen, the passwords are safe.

**File Integrity Verification**

When you download software, the website shows a hash like `SHA256: a3f9b2...`. After downloading, you hash the file and compare. One changed byte produces a completely different hash — instantly revealing tampering or corruption.

**Blockchain**

Every block in a blockchain contains the hash of the previous block. Altering any historical transaction changes its hash, which changes the next block's hash, which cascades through the entire chain — making tampering computationally detectable.

**Caching in Web Servers**

A web server caches responses using the URL as a hash key. When the same request arrives again, the server hashes the URL, jumps directly to the cached response, and returns it in microseconds — no recomputation needed.

## 3. Key Terminology

| Term | Meaning |
|------|---------|
| **Hash Function** | A formula that converts any key (name, number, string) into a fixed-size integer index |
| **Hash Value / Hash Code** | The integer produced by the hash function for a given key |
| **Hash Table** | An array where elements are stored at positions determined by the hash function |
| **Bucket** | A slot in the hash table — each index is a bucket |
| **Collision** | Two different keys produce the same hash value — they both want the same bucket |
| **Load Factor** | Ratio of stored elements to total table size — `n / m`. High load factor → more collisions |
| **Collision Resolution** | The strategy used when two keys hash to the same index |
| **Chaining** | Each bucket holds a linked list — colliding keys share the same bucket's list |
| **Open Addressing** | On collision, probe for the next empty bucket in the table itself |

## 4. What a Hash Function Does

A hash function takes a **key** — any employee name, ID, or string — and converts it to an **integer index** that fits inside the hash table.

```
Key (Employee Name)          Hash Function              Index
───────────────────    ──────────────────────────    ──────────
"Alice"            →   some formula on characters →     3
"Bob"              →   some formula on characters →     7
"Charlie"          →   some formula on characters →     1
"Diana"            →   some formula on characters →     3   ← collision with Alice!
```

The index must always fall within the table size. If the table has `m` slots, valid indices are `0` to `m-1`. The most common way to ensure this is the **modulo operation**:

```
hash_index = hash_value % m
```

A good hash function satisfies three properties:

**Deterministic** — the same key always produces the same index. `hash("Alice")` must always return `3`, never sometimes `3` and sometimes `6`.

**Uniform Distribution** — keys spread evenly across all buckets. A function that sends 80% of employees to bucket 0 is useless — it recreates the scanning problem.

**Fast to Compute** — the hash must be computed in O(1). If computing the hash takes O(n) time, you have gained nothing over a linear scan.

## 5. Building Hash Functions from Scratch

### 5.1 Division Method — The Foundation

The simplest hash function for integer keys:

```
h(k) = k % m
```

Where `k` is the integer key and `m` is the table size.

**CEO Example — Employee IDs**

The company assigns every employee a unique numeric ID. The CEO wants to store 7 employee records in a table of size `m = 10`.

```
Employee        ID      h(ID) = ID % 10
──────────────────────────────────────
Alice           1234         4
Bob             5678         8
Charlie         9012         2
Diana           3456         6
Eve             7890         0
Frank           2345         5
George          6789         9
```

```
Hash Table (size 10):
Index │ Employee
──────┼──────────────
  0   │ Eve
  1   │ (empty)
  2   │ Charlie
  3   │ (empty)
  4   │ Alice
  5   │ Frank
  6   │ Diana
  7   │ (empty)
  8   │ Bob
  9   │ George
```

To find Alice: compute `1234 % 10 = 4`. Go directly to index 4. One step. Done.

**Choosing `m`:** use a prime number for `m` when possible. Prime sizes distribute keys more uniformly because they share no common factors with typical key patterns. `m = 10` above is for readability — `m = 11` or `m = 13` would distribute better in practice.

**Numerical example:**

```python
keys = [15, 27, 43, 8, 62, 31, 19]
m = 7

for k in keys:
    print(f"  h({k}) = {k} % {m} = {k % m}")
```

```
h(15) = 15 % 7 = 1
h(27) = 27 % 7 = 6
h(43) = 43 % 7 = 1    ← collision with 15!
h(8)  = 8  % 7 = 1    ← collision again!
h(62) = 62 % 7 = 6    ← collision with 27!
h(31) = 31 % 7 = 3
h(19) = 19 % 7 = 5
```

Collisions are normal and expected — they are not a failure of the hash function. They are handled by collision resolution strategies (covered in Section 8).

### 5.2 Multiplication Method

```
h(k) = floor(m × (k × A mod 1))
```

Where `A` is a constant between 0 and 1. The value `A = (√5 - 1) / 2 ≈ 0.6180` (the golden ratio) is widely recommended because it distributes keys very uniformly regardless of table size.

```python
import math

def hash_multiply(k, m, A=0.6180339887):
    return math.floor(m * ((k * A) % 1))

m = 10
keys = [1234, 5678, 9012, 3456, 7890]

for k in keys:
    print(f"  h({k}) = {hash_multiply(k, m)}")
```

```
h(1234) = 1
h(5678) = 5
h(9012) = 7
h(3456) = 3
h(7890) = 8
```

No collisions in this set — the golden ratio does an excellent job of spreading values.

### 5.3 String Hash Function — Polynomial Rolling Hash

For employee names (strings), we cannot directly apply `% m` because names are not numbers. We convert each character to its ASCII value and combine them using a polynomial formula:

```
h(s) = (s[0]×p⁰ + s[1]×p¹ + s[2]×p² + ... + s[n-1]×p^(n-1)) % m
```

Where `p` is a small prime (commonly 31 for lowercase letters) and `m` is the table size.

**Why multiply by powers of `p`?** Position matters. Without it, `"Alice"` and `"eCali"` (same letters, different order) would produce identical hashes — every anagram of an employee's name would collide.

```python
def string_hash(name, m, p=31):
    hash_value = 0
    power = 1
    for char in name.lower():
        hash_value += ord(char) * power
        power *= p
    return hash_value % m

m = 11
employees = ["Alice", "Bob", "Charlie", "Diana", "Eve", "Frank", "George"]

print(f"  Table size: {m}\n")
for name in employees:
    idx = string_hash(name, m)
    print(f"  string_hash('{name}') = {idx}")
```

```
Table size: 11

string_hash('Alice')   = 3
string_hash('Bob')     = 8
string_hash('Charlie') = 7
string_hash('Diana')   = 6
string_hash('Eve')     = 0
string_hash('Frank')   = 9
string_hash('George')  = 2
```

All 7 employees land in different buckets — no collisions for this set with `m = 11`.

**Step-by-step trace for "Bob":**

```
'B' → ord('b') = 98  → 98 × 31⁰ = 98  × 1   =    98
'o' → ord('o') = 111 → 111 × 31¹ = 111 × 31  =  3441
'b' → ord('b') = 98  → 98  × 31² = 98  × 961 = 94178

hash_value = 98 + 3441 + 94178 = 97717
index      = 97717 % 11        = 8
```

### 5.4 Python's Built-in `hash()`

Python provides a built-in `hash()` function that works on any hashable object — strings, integers, tuples.

```python
m = 11
employees = ["Alice", "Bob", "Charlie", "Diana", "Eve", "Frank", "George"]

print("Using Python's built-in hash():\n")
for name in employees:
    idx = hash(name) % m
    print(f"  hash('{name}') % {m} = {idx}")
```

```
Using Python's built-in hash():

hash('Alice')   % 11 = 4
hash('Bob')     % 11 = 7
hash('Charlie') % 11 = 3
hash('Diana')   % 11 = 0
hash('Eve')     % 11 = 9
hash('Frank')   % 11 = 5
hash('George')  % 11 = 6
```

Python's `hash()` is cryptographically randomised per session (hash randomisation) — results may differ each time you run the program. For consistent hashing across sessions, use the custom functions from Sections 5.1–5.3.

## 6. Building a Hash Table — The Employee Directory

Now let us build a complete hash table for the company's employee directory. Each slot stores `(name, department)` pairs. We use chaining to handle collisions (each bucket is a list).

```python
class EmployeeHashTable:
    """
    Hash table for the CEO's employee directory.
    Keys   = employee names (strings)
    Values = department names (strings)
    Uses chaining for collision resolution.
    """

    def __init__(self, size=11):
        self.size  = size
        self.table = [[] for _ in range(size)]    # Each bucket is an empty list

    def _hash(self, name):
        """Polynomial rolling hash for employee names."""
        hash_value = 0
        power = 1
        for char in name.lower():
            hash_value += ord(char) * power
            power *= 31
        return hash_value % self.size

    def insert(self, name, department):
        """Hire an employee — store name → department mapping."""
        idx = self._hash(name)
        bucket = self.table[idx]

        for i, (k, v) in enumerate(bucket):
            if k == name:
                bucket[i] = (name, department)    # Update existing employee
                print(f"  Updated '{name}' → '{department}' at index {idx}")
                return

        bucket.append((name, department))          # New employee
        print(f"  Inserted '{name}' → '{department}' at index {idx}")

    def search(self, name):
        """Find an employee's department — O(1) average."""
        idx = self._hash(name)
        for k, v in self.table[idx]:
            if k == name:
                return v
        return None                                 # Employee not found

    def delete(self, name):
        """Employee resigned — remove from directory."""
        idx = self._hash(name)
        bucket = self.table[idx]
        for i, (k, v) in enumerate(bucket):
            if k == name:
                bucket.pop(i)
                print(f"  Removed '{name}' from index {idx}")
                return
        print(f"  '{name}' not found — cannot remove")

    def display(self):
        """Show the entire hash table."""
        print(f"\n  Hash Table (size={self.size}):")
        print(f"  {'Index':<8} {'Bucket Contents'}")
        print(f"  {'─'*40}")
        for i, bucket in enumerate(self.table):
            contents = bucket if bucket else "(empty)"
            print(f"  {i:<8} {contents}")
        print()
```

## 8. Collisions — When Two Employees Want the Same Desk

A collision happens when two different keys hash to the same index. This is not a bug — it is mathematically inevitable for any hash function when the number of possible keys is larger than the table size.

**The Birthday Problem:** In a company of just 23 employees, there is a 50% chance that two employees share the same birthday. The same probabilistic logic applies to hash collisions — with a table of size `m`, collisions become likely once you store roughly `√m` elements.

### 8.1 Chaining — Each Desk Has a Filing Stack

In chaining, each bucket holds a **linked list** (or Python list) of all elements that hash to that index.

```
Index 3 has a collision between Alice and Heidi
(both string_hash to index 3 for some m):

Index │ Bucket
──────┼───────────────────────────────
  3   │ [('Alice','Engineering'), ('Heidi','Legal')]
  8   │ [('Bob','Sales')]
  7   │ [('Charlie','HR')]
```

To search for Heidi: compute hash → go to index 3 → scan the short list → found. Average case is still O(1) if the hash function distributes well and the load factor is low.

**Numerical chaining example:**

```python
keys = [15, 27, 43, 8, 62, 31, 19]
m = 7

table = [[] for _ in range(m)]
for k in keys:
    idx = k % m
    table[idx].append(k)

print("Chaining result:\n")
for i, bucket in enumerate(table):
    print(f"  Index {i}: {bucket if bucket else '(empty)'}")
```

```
Chaining result:

  Index 0: (empty)
  Index 1: [15, 43, 8]    ← three-way collision
  Index 2: (empty)
  Index 3: [31]
  Index 4: (empty)
  Index 5: [19]
  Index 6: [27, 62]       ← two-way collision
```

### 8.2 Open Addressing — Find the Next Empty Desk

In open addressing, all elements are stored directly in the table array itself — no linked lists. When a collision occurs, the algorithm probes for the next available slot.

**Linear Probing:** on collision at index `i`, try `i+1`, `i+2`, `i+3`... until an empty slot is found.

```
h(k) = (original_hash + probe_number) % m
```

**CEO Example — Linear Probing:**

```
Table size m = 7
Insert IDs: 50, 700, 76, 85, 92, 73, 101

h(50)  = 50  % 7 = 1  → slot 1 empty → place at 1
h(700) = 700 % 7 = 0  → slot 0 empty → place at 0
h(76)  = 76  % 7 = 6  → slot 6 empty → place at 6
h(85)  = 85  % 7 = 1  → slot 1 TAKEN → probe slot 2 → empty → place at 2
h(92)  = 92  % 7 = 1  → slot 1 TAKEN → probe slot 2 TAKEN → probe slot 3 → place at 3
h(73)  = 73  % 7 = 3  → slot 3 TAKEN → probe slot 4 → empty → place at 4
h(101) = 101 % 7 = 3  → slot 3 TAKEN → probe 4 TAKEN → probe 5 → place at 5

Final table:
Index │  0   │  1   │  2   │  3   │  4   │  5   │  6
──────┼──────┼──────┼──────┼──────┼──────┼──────┼──────
Value │ 700  │  50  │  85  │  92  │  73  │ 101  │  76
```

**Quadratic Probing:** on collision at index `i`, try `i+1²`, `i+2²`, `i+3²`... Reduces **primary clustering** — the tendency of linear probing to form long runs of filled slots.

```
h(k, probe) = (original_hash + probe²) % m
```

**Double Hashing:** use a second hash function to determine the probe step size. This provides the most uniform probing and virtually eliminates clustering:

```
h(k, probe) = (h1(k) + probe × h2(k)) % m
```

## 9. Load Factor — When to Resize the Table

The **load factor** `α = n / m` measures how full the hash table is. `n` = number of stored elements, `m` = table size.

```
α = 0.1  → table is 10% full  → very few collisions, lots of wasted space
α = 0.5  → table is 50% full  → good balance
α = 0.7  → table is 70% full  → collisions becoming frequent
α = 1.0  → table is 100% full → severe collisions (chaining only — open addressing breaks)
```

**Rule of thumb:** keep `α < 0.7` for open addressing, `α < 1.0` for chaining.

When the load factor exceeds the threshold, **rehashing** is triggered:

1. Create a new table of roughly double the size (next prime after `2m`)
2. Re-insert every existing element using the new table size
3. Discard the old table

Python's `dict` automatically rehashes when the load factor reaches approximately `0.66`.

**Numerical example:**

```python
employees_stored = 7
table_sizes = [7, 10, 11, 13]

print("Load Factor Analysis:\n")
for m in table_sizes:
    alpha = employees_stored / m
    status = "⚠ consider resizing" if alpha > 0.7 else "✓ acceptable"
    print(f"  n={employees_stored}, m={m}  →  α = {alpha:.2f}  {status}")
```

```
Load Factor Analysis:

  n=7, m=7   →  α = 1.00  ⚠ consider resizing
  n=7, m=10  →  α = 0.70  ⚠ consider resizing
  n=7, m=11  →  α = 0.64  ✓ acceptable
  n=7, m=13  →  α = 0.54  ✓ acceptable
```

This is why we chose `m = 11` for the CEO's directory with 7 employees — it keeps the load factor comfortably below 0.7.

## 11. Python's `dict` — A Hash Table You Use Every Day

Every Python dictionary is a hash table. Understanding hashing explains why dicts behave the way they do.

```python
# This is a hash table — you have been using one all along
employee_dept = {}

employee_dept["Alice"]   = "Engineering"    # insert → hash("Alice") → index → store
employee_dept["Bob"]     = "Sales"
employee_dept["Charlie"] = "HR"

# O(1) lookup — hash("Alice") → index → retrieve
print(employee_dept["Alice"])               # Engineering

# O(1) membership test
print("Diana" in employee_dept)             # False

# O(1) update
employee_dept["Alice"] = "Product"          # hash("Alice") → same index → overwrite

# Demonstrate hash values
print("\nHash values (session-specific):\n")
for name in ["Alice", "Bob", "Charlie"]:
    print(f"  hash('{name}') = {hash(name)}")
    print(f"  index in dict of size 8 = {hash(name) % 8}\n")
```

**Why dict keys must be immutable:** hashing requires that the key's hash value never changes after insertion. If a key could change (like a list), its hash would change, and the table would lose track of it — you would insert at one index and find nothing when you search. This is why `dict` keys must be strings, numbers, or tuples — all immutable.

```python
# Valid dict keys (immutable — hashable)
d = {}
d["Alice"]        = "Engineering"   # string ✓
d[1234]           = "ID-based"      # integer ✓
d[(50, "Sales")]  = "dept-loc"      # tuple ✓

# Invalid dict key (mutable — unhashable)
d[["Alice", 1234]] = "data"         # TypeError: unhashable type: 'list'
```

        bucket = self.table[idx]
        for i, (k, v) in enumerate(bucket):
            if k == name:
                bucket[i] = (name, dept)
                return
        bucket.append((name, dept))

    def search(self, name):
        for k, v in self.table[self._hash(name)]:
            if k == name:
                return v
        return None

    def delete(self, name):
        idx    = self._hash(name)
        bucket = self.table[idx]
        for i, (k, v) in enumerate(bucket):
            if k == name:
                bucket.pop(i)
                return True
        return False

    def display(self):
        print(f"\n  Hash Table (size={self.size}):")
        for i, bucket in enumerate(self.table):
            print(f"  [{i:>2}]  {bucket if bucket else '(empty)'}")
        print()

## 13. Time Complexity

| Operation | Average Case | Worst Case | Notes |
|-----------|-------------|------------|-------|
| Insert | O(1) | O(n) | Worst case: all keys collide into one bucket |
| Search | O(1) | O(n) | Worst case: entire chain must be scanned |
| Delete | O(1) | O(n) | Same as search |
| Rehash | O(n) | O(n) | Re-insert all n elements into new table |
| `hash()` compute | O(1) integers | O(L) strings | L = length of string |

The average O(1) holds when: (1) the hash function distributes keys uniformly, and (2) the load factor is kept below ~0.7.

## 14. Common Mistakes

**Mistake 1 — Choosing a poor table size**

```python
# Bad — m=10 shares factor 2 and 5 with many key patterns
# Even-numbered keys always hash to even indices — half the table wasted
table_size = 10

# Good — prime numbers distribute more uniformly
table_size = 11    # or 13, 17, 19, 23...
```

**Mistake 2 — Using a mutable object as a hash key**

```python
# Wrong — lists are mutable, their hash would change if modified
d = {}
d[["Alice", 1234]] = "Engineering"   # TypeError: unhashable type: 'list'

# Correct — use a tuple (immutable)
d[("Alice", 1234)] = "Engineering"   # ✓
```

**Mistake 3 — Ignoring the load factor until it is too late**

```python
# Wrong — inserting indefinitely into a fixed-size table
# Load factor reaches 1.0 → every insertion causes a long collision chain
# Average search degrades from O(1) to O(n)

# Correct — monitor load factor and rehash when α > 0.7
if len(self.elements) / self.size > 0.7:
    self._rehash()
```

**Mistake 4 — Treating hash equality as key equality**

```python
# Wrong — two different keys CAN have the same hash (collision)
# Always verify the actual key after hashing
idx = hash(name) % m
if table[idx] == name:     # Wrong — table[idx] might be a DIFFERENT name
    return True

# Correct — check the actual key stored at that index
for stored_key, value in table[idx]:
    if stored_key == name:     # Explicit key comparison
        return value
```

## 16. Summary

| Concept | Meaning |
|---------|---------|
| Hash function | Converts any key into a fixed-range integer index — O(1) |
| Division method | `h(k) = k % m` — use prime `m` for best distribution |
| Multiplication method | `h(k) = floor(m × (k×A mod 1))` — golden ratio A distributes beautifully |
| Polynomial rolling hash | For strings — position-sensitive, uses ASCII × powers of prime |
| Collision | Two keys produce the same index — normal and expected |
| Chaining | Each bucket holds a list of all colliding elements |
| Open addressing | On collision, probe for the next empty slot in the table |
| Load factor α | `n/m` — keep below 0.7 for open addressing |
| Rehashing | Double table size and re-insert all elements when α exceeds threshold |
| Python `dict` | A hash table — every key lookup is O(1) because of hashing |
| Immutable keys | Keys must be immutable because their hash must never change after insertion |

A hash function is the only data structure mechanism that makes the cost of finding something **independent of how many things you are storing**. Ten employees or ten million — finding Alice takes the same one step. That is not an approximation or an average — it is the direct consequence of computing a location rather than searching for it.
