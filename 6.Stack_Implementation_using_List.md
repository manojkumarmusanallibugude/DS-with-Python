# Stack — Linked List Implementation

---

## The Limit of the Array Approach

In the previous topic, we built a stack backed by a Python list. It worked. Push was O(1) amortised. Pop was O(1). For most workloads, it is perfectly adequate.

But it carries one fundamental assumption: **you know, approximately, how large the stack will grow**.

A Python list allocates memory in chunks and doubles its capacity when it runs out. This is efficient in practice, but the underlying array always occupies a contiguous block of memory. When the list doubles, it must allocate a new, larger block and copy everything over. During that copy, both the old block and the new block exist simultaneously.

More importantly, you cannot set a hard upper bound without writing extra logic. You either over-allocate and waste memory, or under-allocate and resize.

The linked list takes the opposite philosophy. **Memory is allocated one node at a time, exactly when needed, and released immediately when a node is removed.** There is no pre-allocated block, no doubling, no copying. The stack grows and shrinks with no overhead beyond the node itself.

This is the case for a linked-list-backed stack: precise, on-demand memory allocation with no wasted space and no resize events.

---

## How It Works Conceptually

A stack follows **LIFO — Last In, First Out**. The last element pushed is the first element popped.

In a linked list, the natural point of O(1) insertion *and* O(1) removal is the **head**. You do not need a tail reference for a stack. Every operation — push and pop — happens at the front.

```
Push 10:         Push 20:         Push 30:         Pop:

  top              top              top              top
   │                │                │                │
   ▼                ▼                ▼                ▼
[10│None]       [20│ ──►]        [30│ ──►]        [20│ ──►]
                [10│None]        [20│ ──►]        [10│None]
                                 [10│None]
```

Each node holds its value and a pointer to the node below it in the stack. The `top` pointer always refers to the most recently pushed node. When you pop, `top` moves down to the next node.

No shifting. No resizing. Just pointer updates.

---

## Building the Node

Every node in the linked list needs two things: the data it holds, and a reference to the next node.

```python
class Node:
    def __init__(self, data):
        self.data = data
        self.next = None    # Points to the node below in the stack
```

This is the atom. The stack is built entirely from chains of these.

---

## The Stack Class

```python
class Stack:
    def __init__(self):
        self.top = None     # Empty stack: top points to nothing
        self.size = 0       # Track the number of elements
```

`top` is the only reference the stack needs. It always points to the most recently pushed node. An empty stack has `top = None`.

---

## Push — Adding to the Top

Pushing is inserting a new node at the head of the linked list.

```python
def push(self, data):
    node = Node(data)   # Create the new node
    node.next = self.top  # New node points down to the current top
    self.top = node       # top now points to the new node
    self.size += 1
```

**What happens step by step:**

```
Before push(30):                After push(30):

  top                             top
   │                               │
   ▼                               ▼
[20│ ──►]                      [30│ ──►]
[10│None]                      [20│ ──►]
                                [10│None]
```

1. A new node containing 30 is created.
2. Its `next` pointer is set to the current top (node 20).
3. `top` is updated to point to the new node (node 30).

**Time: O(1).** No traversal. No resizing. Three pointer operations.

---

## Pop — Removing from the Top

Popping is removing the head node and returning its data.

```python
def pop(self):
    if self.is_empty():
        raise IndexError("pop from empty stack")
    data = self.top.data      # Store the value before removing
    self.top = self.top.next  # top moves down to the next node
    self.size -= 1
    return data
```

**What happens step by step:**

```
Before pop():                   After pop():

  top                             top
   │                               │
   ▼                               ▼
[30│ ──►]   ← removed          [20│ ──►]
[20│ ──►]                      [10│None]
[10│None]
```

1. The value at `top` (30) is saved.
2. `top` moves to `top.next` (node 20).
3. The old top node is no longer referenced — Python's garbage collector reclaims it.

**Time: O(1).** The node is freed the moment it is removed, with no deferred cleanup.

---

## Peek — Reading Without Removing

Sometimes you need to see what is on top without taking it off.

```python
def peek(self):
    if self.is_empty():
        raise IndexError("peek from empty stack")
    return self.top.data
```

This simply reads `top.data`. The structure is not modified.

**Time: O(1).**

---

## IsEmpty and Size

```python
def is_empty(self):
    return self.top is None

def __len__(self):
    return self.size
```

Both are O(1). `is_empty` checks whether `top` is `None`. `size` is maintained as a running count so you never need to traverse the list to count nodes.

## Complete Implementation

```python
class Node:
    def __init__(self, data):
        self.data = data
        self.next = None


class Stack:
    def __init__(self):
        self.top = None
        self.size = 0

    def push(self, data):
        """Add an element to the top. O(1)."""
        node = Node(data)
        node.next = self.top
        self.top = node
        self.size += 1

    def pop(self):
        """Remove and return the top element. O(1)."""
        if self.is_empty():
            raise IndexError("pop from empty stack")
        data = self.top.data
        self.top = self.top.next
        self.size -= 1
        return data

    def peek(self):
        """Return the top element without removing it. O(1)."""
        if self.is_empty():
            raise IndexError("peek from empty stack")
        return self.top.data

    def is_empty(self):
        """Return True if the stack contains no elements. O(1)."""
        return self.top is None

    def __len__(self):
        """Return the number of elements in the stack. O(1)."""
        return self.size

    def __repr__(self):
        """Display the stack from top to bottom."""
        elements = []
        current = self.top
        while current:
            elements.append(str(current.data))
            current = current.next
        return "Stack (top → bottom): [" + ", ".join(elements) + "]"
```

## Practical Patterns

### Pattern 1 — Balanced Parentheses

Every opening bracket must be closed by a matching bracket in the correct order.

```python
def is_balanced(expression):
    s = Stack()
    pairs = {')': '(', ']': '[', '}': '{'}

    for char in expression:
        if char in '([{':
            s.push(char)
        elif char in ')]}':
            if s.is_empty() or s.pop() != pairs[char]:
                return False

    return s.is_empty()


print(is_balanced("({[]})"))    # True
print(is_balanced("({[})"))     # False — mismatched
print(is_balanced("((())"))     # False — unclosed
```

The stack holds all open brackets seen so far. When a closing bracket appears, the most recent open bracket must match it. This is inherently LIFO — the last opened must be the first closed.

---

### Pattern 2 — Reversing a Sequence

Pushing every element of a sequence onto a stack and popping them all out reverses the order.

```python
def reverse_string(s):
    stack = Stack()
    for char in s:
        stack.push(char)

    result = []
    while not stack.is_empty():
        result.append(stack.pop())

    return "".join(result)


print(reverse_string("linked"))    # "deknil"
```

This works because LIFO naturally inverts the order of arrival. The first character pushed is the last popped.

---

### Pattern 3 — Undo History

Every action is pushed onto the stack. Undoing pops the last action and reverses it.

```python
class TextEditor:
    def __init__(self):
        self.text = ""
        self.history = Stack()

    def type(self, chars):
        self.history.push(("type", chars))
        self.text += chars

    def undo(self):
        if self.history.is_empty():
            return
        action, data = self.history.pop()
        if action == "type":
            self.text = self.text[:-len(data)]

    def __repr__(self):
        return f'"{self.text}"'


editor = TextEditor()
editor.type("Hello")
editor.type(", world")
print(editor)          # "Hello, world"

editor.undo()
print(editor)          # "Hello"

editor.undo()
print(editor)          # ""
```

The undo stack holds actions in chronological order. Undoing always reverses the most recent action — the definition of LIFO.

---

### Pattern 4 — Postfix Expression Evaluation

Postfix notation (also called Reverse Polish Notation) eliminates the need for parentheses by placing operators after their operands. Evaluating it is a natural fit for a stack.

```python
def evaluate_postfix(expression):
    s = Stack()
    tokens = expression.split()

    for token in tokens:
        if token.lstrip('-').isdigit():
            s.push(int(token))
        else:
            b = s.pop()    # Second operand (pushed first)
            a = s.pop()    # First operand (pushed second)
            if   token == '+': s.push(a + b)
            elif token == '-': s.push(a - b)
            elif token == '*': s.push(a * b)
            elif token == '/': s.push(int(a / b))

    return s.pop()


print(evaluate_postfix("3 4 + 2 *"))      # (3+4)*2 = 14
print(evaluate_postfix("5 1 2 + 4 * + 3 -"))  # 5+((1+2)*4)-3 = 14
```

Each operand is pushed. When an operator appears, exactly two operands are popped, the result is computed, and pushed back. The final value left on the stack is the answer.

## Linked List Stack vs Array Stack

| Property | Array-backed Stack (`list`) | Linked List Stack |
|---|---|---|
| Push | O(1) amortised | O(1) always |
| Pop | O(1) | O(1) |
| Peek | O(1) | O(1) |
| Memory allocation | Pre-allocated block, resizes by doubling | One node per element, on demand |
| Memory overhead per element | Low (just the value) | Higher (value + `next` pointer) |
| Max size | Unbounded (resizes automatically) | Unbounded (limited only by available memory) |
| Memory wasted | Up to 2× capacity on resize | None — each node freed immediately on pop |
| Index access | O(1) | Not applicable |

**When to prefer the linked list implementation:**

- When the maximum stack depth is unpredictable and you want no resize events.
- When every pop should immediately free memory.
- When you are building the stack as a teaching exercise or as part of a larger custom data structure.

**When to prefer the array implementation:**

- In almost all practical Python applications — the Python `list` is highly optimised and the overhead of object allocation per node adds up.
- When memory per element matters and you want minimal overhead.

## Common Mistakes

### Mistake 1 — Popping from an Empty Stack

```python
s = Stack()
s.push(1)
s.pop()
s.pop()    # Raises IndexError — stack is already empty
```

Always check `is_empty()` before calling `pop()` if the stack might be empty, or use a try/except block.

```python
try:
    value = s.pop()
except IndexError:
    print("Stack is empty")
```

---

### Mistake 2 — Confusing Pop Order

When two values are popped for a binary operation, **order matters**.

```python
s.push(10)
s.push(3)

b = s.pop()    # b = 3  (last in — first out)
a = s.pop()    # a = 10

result = a - b    # 10 - 3 = 7    ✓
```

Reversing the assignment gives `3 - 10 = -7`, which is wrong. Always pop the second operand first, then the first operand.

---

### Mistake 3 — Forgetting to Update `top`

A common mistake when implementing manually is updating the node's pointer but forgetting to update `top`.

```python
# Wrong — top never changes
def push(self, data):
    node = Node(data)
    node.next = self.top    # correct so far
    # forgot: self.top = node
```

After this, every push creates a node that nothing references. The old `top` still points to the old node. Every pop returns the same stale value.

---

### Mistake 4 — Traversing to Find Size

If you do not maintain a `size` counter, finding the length requires traversal:

```python
# Avoid this — O(n)
def length(self):
    count = 0
    current = self.top
    while current:
        count += 1
        current = current.next
    return count
```

Maintain `self.size` as a field instead. Increment on push, decrement on pop. Length is then O(1).

## Where This Pattern Appears

**Call Stack in Programming Languages**

When a function calls another function, the runtime pushes a frame containing the local variables, parameters, and return address onto a stack. When the function returns, the frame is popped. This is the call stack — a literal linked stack of frames that the language runtime manages. Stack overflow occurs when this stack grows deeper than the allotted memory.

**Browser History Navigation**

Each visited page is pushed onto a back-stack. Pressing Back pops from it and pushes onto a forward-stack. Navigating to a new page clears the forward-stack.

**Expression Parsers and Compilers**

Compilers use stacks to parse nested expressions, evaluate operator precedence, convert between infix and postfix notation, and track scopes. Every function body, every set of braces, every level of nesting corresponds to a push/pop cycle.

**Depth-First Search**

DFS on a graph can be implemented with an explicit stack instead of recursion. Vertices are pushed when discovered and popped when fully explored. The iterative version using a stack mirrors exactly what the call stack does implicitly in the recursive version.

## Summary

| Concept | What It Means |
|---|---|
| LIFO | Last In, First Out — the defining property of a stack |
| `top` pointer | Always refers to the most recently pushed node |
| Push | Create a new node; point it to current `top`; update `top` |
| Pop | Save `top.data`; move `top` to `top.next`; return saved value |
| Peek | Read `top.data` without modifying the structure |
| Memory | Each node allocated on push, freed on pop — no pre-allocation |
| All core operations | O(1) — no traversal required for any of them |

The linked list stack removes the only assumption the array stack made: that you have some idea of the maximum size in advance. By allocating one node per element, it adapts precisely to the workload — never holding more memory than the current stack depth demands.
