# Queue — Linked List Implementation

---

## The Limit of the `deque` Approach

In the previous topic, we built a queue using `collections.deque`. Enqueue was O(1). Dequeue was O(1). The implementation was concise and practical. For the vast majority of use cases, it is the right choice.

But it rests on one hidden assumption: **memory is managed in fixed-size blocks allocated by Python's runtime, and you have no direct control over how that memory is claimed or released**.

A `deque` maintains a doubly linked list of internal blocks. When a block fills up, a new one is allocated. When a block empties out, it is eventually released — but on the runtime's schedule, not yours. You cannot observe the allocation boundary. You cannot enforce an exact memory budget. The structure manages itself and keeps its internals opaque.

More critically, `deque` is indivisible. It is a self-contained object. You cannot embed it as a sub-structure inside a larger data structure without wrapping it. You cannot expose its nodes as first-class elements. You cannot extend its behaviour at the node level.

The linked list takes a different position. **Memory is requested exactly once per element, at the moment it is enqueued. It is released exactly once per element, at the moment it is dequeued.** The queue's memory footprint at any instant is proportional to exactly the number of elements it currently holds — no more, no less.

This is the case for a linked-list-backed queue: two pointers, one counter, one node per element. No blocks, no internal arrays, no capacity to manage.

---

## Rethinking the Queue as a Chain

In the `deque`-based queue, elements live inside fixed-size memory blocks managed by Python. Enqueue and dequeue are fast because Python handles the bookkeeping internally.

In a linked queue, elements are **individual nodes scattered in memory**, each connected to the next one toward the rear by a pointer. The queue maintains two references: one to the front node (for dequeuing) and one to the rear node (for enqueuing).

```
deque-based queue:                   Linked-list-based queue:

  Internal blocks (opaque):           Nodes linked by pointers:

  ┌──────────────┐                    front                  rear
  │ 10 │ 20 │ 30 │──► ...              │                       │
  └──────────────┘                     ▼                       ▼
                                   ┌──────────┐           ┌──────────┐
                                   │ 10 │  ───┼──►  ...──►│ 40 │None │
                                   └──────────┘           └──────────┘
```

Both represent the same queue — 10 at the front, 40 at the rear. The difference is structural: one relies on Python's internal block allocator; the other exposes every node as an explicit Python object you own.

The key insight is that **only two nodes ever matter at a time**. Enqueue touches only the rear. Dequeue touches only the front. The middle of the chain is never visited during normal operation.

---

## The Node

Each element in the queue lives in a node with two fields.

```python
class Node:
    def __init__(self, data):
        self.data = data    # The value stored at this position
        self.next = None    # Reference to the next node toward the rear
```

The `next` field points **toward the rear** — away from the front, toward newer elements. The front node's `next` points to the second element, and so on until the rear node, whose `next` is `None`.

---

## The Queue Class

```python
class Queue:
    def __init__(self):
        self.front = None   # Points to the node to be dequeued next; None means empty
        self.rear = None    # Points to the node most recently enqueued
        self._size = 0      # Maintained explicitly to keep len() at O(1)
```

That is the entire state. Two references and one counter. No array. No capacity. No index.

The need for **two** pointers — not one — is what distinguishes a linked queue from a linked stack. A linked stack only ever touches the head. A linked queue touches both ends, so both ends must be tracked.

---

## Enqueue — Inserting at the Rear

Enqueuing is appending a node to the tail of the linked chain.

```python
def enqueue(self, data):
    """Add an element to the rear of the queue. O(1)."""
    node = Node(data)           # Step 1: Allocate a new node
    if self.rear is None:       # Step 2: If queue is empty, both pointers go here
        self.front = node
        self.rear = node
    else:
        self.rear.next = node   # Step 3: Link the current rear to the new node
        self.rear = node        # Step 4: The new node becomes the rear
    self._size += 1
```

**Trace through enqueue(40) onto a queue already holding [10, 20, 30]:**

```
Step 1 — Create the new node:

    new_node: [40 │ None]

Step 2 — Not empty, so link rear.next to the new node:

    front                              rear
      │                                 │
      ▼                                 ▼
    [10 │ ──►] ──► [20 │ ──►] ──► [30 │ ──►] ──► [40 │ None]
                                                    ▲
                                               new_node

Step 3 — Move rear to the new node:

    front                                         rear
      │                                             │
      ▼                                             ▼
    [10 │ ──►] ──► [20 │ ──►] ──► [30 │ ──►] ──► [40 │ None]
```

Four operations at most. No traversal. No reallocation. **Time: O(1) — always.**

## Dequeue — Removing from the Front

Dequeuing is detaching the head node and returning its value.

```python
def dequeue(self):
    """Remove and return the front element. Raises IndexError if empty. O(1)."""
    if self.is_empty():
        raise IndexError("dequeue from an empty queue")
    data = self.front.data          # Step 1: Save the value
    self.front = self.front.next    # Step 2: Advance front to the next node
    if self.front is None:          # Step 3: If queue is now empty, clear rear too
        self.rear = None
    self._size -= 1
    return data                     # Step 4: Return the saved value
```

**Trace through dequeue() on a queue holding [10, 20, 30, 40]:**

```
Step 1 — Save the value at front:

    saved = 10

    front                                         rear
      │                                             │
      ▼                                             ▼
    [10 │ ──►] ──► [20 │ ──►] ──► [30 │ ──►] ──► [40 │ None]

Step 2 — Advance front to front.next:

                   front                          rear
                     │                              │
                     ▼                              ▼
    [10 │ ──►] ──► [20 │ ──►] ──► [30 │ ──►] ──► [40 │ None]
     ▲
     └── No references remain. Garbage collected.

Step 3 — front is not None, so rear stays put.

Step 4 — Return 10.
```

The dequeued node is immediately eligible for garbage collection because nothing references it anymore. **Time: O(1).**

**Special case — dequeuing the last element:**

```
Before: queue holds only [99]

    front   rear
      │       │
      ▼       ▼
    [99 │ None]

Step 1 — saved = 99
Step 2 — front = front.next → front = None
Step 3 — front is None → rear = None  ← critical: rear must also be cleared

After: front = None, rear = None  → queue is empty
```

Failing to clear `rear` when the last node is dequeued leaves a dangling pointer. The next enqueue would attempt to link via `self.rear.next` on a node that no longer represents a valid position in the queue.

## Peek — Reading the Front

```python
def front_peek(self):
    """Return the front element without removing it. Raises IndexError if empty. O(1)."""
    if self.is_empty():
        raise IndexError("front of an empty queue")
    return self.front.data

def rear_peek(self):
    """Return the rear element without removing it. Raises IndexError if empty. O(1)."""
    if self.is_empty():
        raise IndexError("rear of an empty queue")
    return self.rear.data
```

Both `front.data` and `rear.data` are directly accessible. No traversal. **Time: O(1).**

## Supporting Methods

```python
def is_empty(self):
    """Return True if the queue has no elements. O(1)."""
    return self.front is None

def __len__(self):
    """Return the number of elements in the queue. O(1)."""
    return self._size

def __repr__(self):
    """Return a readable string showing the queue from front to rear. O(n)."""
    elements = []
    current = self.front
    while current is not None:
        elements.append(repr(current.data))
        current = current.next
    return "Queue(front → rear): [" + ", ".join(elements) + "]"
```

`__len__` is O(1) because `_size` is kept current by enqueue and dequeue. Traversing the chain every time `len()` is called would make it O(n) — an unnecessary cost for such a routine query.

`is_empty` checks `self.front is None` rather than `self._size == 0`. Both are equivalent, but the pointer check is marginally more direct and avoids a subtle bug class: if `_size` were ever miscounted, `front is None` would still give the truthful answer.

## Complete Implementation

```python
class Node:
    def __init__(self, data):
        self.data = data
        self.next = None


class Queue:
    def __init__(self):
        self.front = None
        self.rear = None
        self._size = 0

    def enqueue(self, data):
        """Add an element to the rear. O(1)."""
        node = Node(data)
        if self.rear is None:
            self.front = node
            self.rear = node
        else:
            self.rear.next = node
            self.rear = node
        self._size += 1

    def dequeue(self):
        """Remove and return the front element. Raises IndexError if empty. O(1)."""
        if self.is_empty():
            raise IndexError("dequeue from an empty queue")
        data = self.front.data
        self.front = self.front.next
        if self.front is None:
            self.rear = None
        self._size -= 1
        return data

    def front_peek(self):
        """Return the front element without removing it. Raises IndexError if empty. O(1)."""
        if self.is_empty():
            raise IndexError("front of an empty queue")
        return self.front.data

    def rear_peek(self):
        """Return the rear element without removing it. Raises IndexError if empty. O(1)."""
        if self.is_empty():
            raise IndexError("rear of an empty queue")
        return self.rear.data

    def is_empty(self):
        """Return True if the queue contains no elements. O(1)."""
        return self.front is None

    def __len__(self):
        """Return the number of elements. O(1)."""
        return self._size

    def __repr__(self):
        """Display the queue from front to rear. O(n)."""
        elements = []
        current = self.front
        while current is not None:
            elements.append(repr(current.data))
            current = current.next
        return "Queue(front → rear): [" + ", ".join(elements) + "]"
```

## Practical Patterns

### Pattern 1 — Breadth-First Search (BFS)

BFS explores a graph layer by layer. The queue guarantees that every node at distance d from the source is fully processed before any node at distance d + 1. Replacing the queue with a stack gives DFS — the data structure determines the traversal order.

```python
def bfs(graph, start):
    """Level-order traversal of a graph using a linked-list queue."""
    q = Queue()
    visited = set()

    q.enqueue(start)
    visited.add(start)

    order = []
    while not q.is_empty():
        vertex = q.dequeue()
        order.append(vertex)
        for neighbour in graph[vertex]:
            if neighbour not in visited:
                visited.add(neighbour)
                q.enqueue(neighbour)

    return order


graph = {
    "A": ["B", "C"],
    "B": ["A", "D", "E"],
    "C": ["A", "F"],
    "D": ["B"],
    "E": ["B"],
    "F": ["C"],
}

print(bfs(graph, "A"))    # ['A', 'B', 'C', 'D', 'E', 'F']
```

The queue holds the frontier — every node discovered but not yet expanded. Nodes leave the queue in the exact order they entered, which is what forces level-by-level progression.

---

### Pattern 2 — Level-Order Binary Tree Traversal

Level-order traversal visits every node on one level before moving to the next. The queue drives this naturally: enqueue children left-to-right; they will be dequeued left-to-right on the next level.

```python
class TreeNode:
    def __init__(self, val):
        self.val = val
        self.left = None
        self.right = None


def level_order(root):
    """Return values grouped by level, using a linked-list queue."""
    if root is None:
        return []

    q = Queue()
    q.enqueue(root)
    result = []

    while not q.is_empty():
        level_size = len(q)    # Nodes on the current level
        level = []

        for _ in range(level_size):
            node = q.dequeue()
            level.append(node.val)
            if node.left:
                q.enqueue(node.left)
            if node.right:
                q.enqueue(node.right)

        result.append(level)

    return result


#         1
#        / \
#       2   3
#      / \   \
#     4   5   6

root = TreeNode(1)
root.left  = TreeNode(2)
root.right = TreeNode(3)
root.left.left  = TreeNode(4)
root.left.right = TreeNode(5)
root.right.right = TreeNode(6)

print(level_order(root))
# [[1], [2, 3], [4, 5, 6]]
```

Capturing `level_size = len(q)` before the inner loop is the key move. It fixes the boundary between the current level's nodes (already in the queue) and the next level's children (about to be enqueued). Without it, you cannot tell where one level ends and the next begins.

### Pattern 3 — Hot Potato Simulation

In the hot potato game, players pass an object around a circle. When the music stops after a random count, the player holding it is eliminated. This repeats until one player remains. A queue models the circle perfectly: each pass is a dequeue-then-enqueue; elimination is a plain dequeue.

```python
import random

def hot_potato(players, max_passes):
    """
    Simulate hot potato elimination.
    Each round: pass the potato a random number of times (1 to max_passes),
    then eliminate the current holder.
    """
    q = Queue()
    for player in players:
        q.enqueue(player)

    print(f"Players: {players}\n")

    round_num = 1
    while len(q) > 1:
        passes = random.randint(1, max_passes)

        # Pass the potato 'passes' times around the circle
        for _ in range(passes):
            q.enqueue(q.dequeue())    # Move front player to the rear

        eliminated = q.dequeue()      # Current front is holding the potato
        print(f"Round {round_num}: {eliminated} is eliminated "
              f"(after {passes} passes)")
        round_num += 1

    winner = q.dequeue()
    print(f"\nWinner: {winner}")
    return winner


random.seed(42)
hot_potato(["Alice", "Bob", "Carol", "Dave", "Eve"], max_passes=8)
```

```
Players: ['Alice', 'Bob', 'Carol', 'Dave', 'Eve']

Round 1: Carol is eliminated (after 3 passes)
Round 2: Alice is eliminated (after 7 passes)
Round 3: Eve is eliminated (after 2 passes)
Round 4: Dave is eliminated (after 5 passes)

Winner: Bob
```

The pattern `q.enqueue(q.dequeue())` rotates the entire queue by one position in O(1) — one dequeue from the front, one enqueue to the rear. No index arithmetic, no slicing, no shifting.

### Pattern 4 — Josephus Problem

The Josephus problem is a counting elimination: n people stand in a circle; every k-th person is eliminated until one remains. The queue formulation is identical to hot potato, but with a fixed step count.

```python
def josephus(n, k):
    """
    Find the position (1-indexed) of the last survivor when every k-th
    person is eliminated from a circle of n people.
    """
    q = Queue()
    for i in range(1, n + 1):
        q.enqueue(i)

    print(f"Circle of {n}, eliminate every {k}th person:\n")

    step = 1
    while len(q) > 1:
        # Rotate k-1 times to bring the k-th person to the front
        for _ in range(k - 1):
            q.enqueue(q.dequeue())

        eliminated = q.dequeue()
        print(f"  Step {step:2d}: eliminated person {eliminated:2d}  "
              f"(remaining: {len(q)})")
        step += 1

    survivor = q.dequeue()
    print(f"\nSurvivor: person {survivor}")
    return survivor


josephus(n=7, k=3)
```

```
Circle of 7, eliminate every 3rd person:

  Step  1: eliminated person  3  (remaining: 6)
  Step  2: eliminated person  6  (remaining: 5)
  Step  3: eliminated person  2  (remaining: 4)
  Step  4: eliminated person  7  (remaining: 3)
  Step  5: eliminated person  5  (remaining: 2)
  Step  6: eliminated person  1  (remaining: 1)

Survivor: person 4
```

Each rotation of `k - 1` steps costs O(k) time. With n eliminations total, the overall complexity is O(nk). This is the direct simulation; mathematical closed-form solutions exist for the pure count, but the queue version models the physical process exactly.

### Pattern 5 — Multi-Source BFS (Distance from Multiple Sources)

Some problems require finding the shortest distance from any of several sources simultaneously — for example, the nearest exit in a maze, or the nearest land cell in a grid of water. Multi-source BFS seeds the queue with all sources at once and expands outward together.

```python
def nearest_exit(maze, entrances):
    """
    Find the shortest distance from any entrance to any empty cell ('.')
    that is on the boundary of the maze. '+' marks walls.

    maze: list of list of characters
    entrances: list of (row, col) pairs — all seeded at distance 0
    Returns: minimum steps to the nearest exit, or -1 if unreachable.
    """
    rows, cols = len(maze), len(maze[0])
    q = Queue()
    visited = set()

    # Seed all entrances simultaneously — each starts at distance 0
    for r, c in entrances:
        q.enqueue((r, c, 0))
        visited.add((r, c))

    directions = [(0, 1), (0, -1), (1, 0), (-1, 0)]

    while not q.is_empty():
        r, c, dist = q.dequeue()

        for dr, dc in directions:
            nr, nc = r + dr, c + dc

            if (nr, nc) in visited:
                continue
            if not (0 <= nr < rows and 0 <= nc < cols):
                continue
            if maze[nr][nc] == '+':
                continue

            # A boundary empty cell that is not an entrance is an exit
            if (nr == 0 or nr == rows - 1 or nc == 0 or nc == cols - 1):
                if (nr, nc) not in {(r, c) for r, c in entrances}:
                    return dist + 1

            visited.add((nr, nc))
            q.enqueue((nr, nc, dist + 1))

    return -1


maze = [
    ['+', '+', '.', '+'],
    ['.', '.', '.', '+'],
    ['+', '+', '+', '.'],
]
entrances = [(1, 2)]

print(nearest_exit(maze, entrances))    # 1
```

Multi-source BFS is the same algorithm as single-source BFS. The only difference is the initialisation: instead of one starting node, the queue is pre-loaded with all sources. The wavefront expands from all of them at once, so the first time any boundary cell is reached, it is guaranteed to be the closest one from any source.

## Linked List Queue vs `deque`-Based Queue

| Property | `deque`-based | Linked List (`Node` chain) |
|---|---|---|
| Enqueue | O(1) | O(1) |
| Dequeue | O(1) | O(1) |
| Peek front | O(1) | O(1) |
| Peek rear | O(1) | O(1) |
| Memory per element | Amortised — block-allocated internally | One `Node` object, allocated on enqueue |
| Memory released on dequeue | Deferred — block freed only when fully empty | Yes — node is immediately freed |
| Unused capacity | Some — partially filled blocks | None |
| Index access | O(1) | Not applicable |
| Node visibility | Internal — not accessible | Full — each node is a plain Python object |
| Embeddable in other structures | Only as a wrapper | Directly — nodes can carry extra fields |
| Practical default in Python | Preferred | Teaching and custom structures |

**Choose the linked list queue when:**
- Memory must be reclaimed immediately on dequeue.
- You are building a larger data structure (graph node, tree, LRU cache) that embeds a queue internally and needs direct access to nodes.
- You want the educational clarity of explicit pointers and explicit ownership.

**Choose the `deque`-based queue when:**
- You are writing production Python code and simplicity matters.
- Throughput is high — `deque` is implemented in C and is faster in practice than a pure-Python linked list.
- You want the standard library's optimised internals without maintenance overhead.

## Common Mistakes

### Mistake 1 — Forgetting to Update `rear` on the First Enqueue

```python
# Wrong — rear is never set for an empty queue
def enqueue(self, data):
    node = Node(data)
    if self.rear is not None:
        self.rear.next = node
        self.rear = node
    # Missing the else branch: if rear is None, both front and rear must be set
```

After this, `front` is never assigned when enqueuing into an empty queue. The first dequeue returns `None` or raises `AttributeError` rather than returning the enqueued value.

---

### Mistake 2 — Forgetting to Clear `rear` When the Last Node Is Dequeued

```python
# Wrong — rear is left pointing to a freed node
def dequeue(self):
    data = self.front.data
    self.front = self.front.next
    # Missing: if self.front is None: self.rear = None
    self._size -= 1
    return data
```

After the last element is dequeued, `front` becomes `None` (correct) but `rear` still points to the old node (incorrect). The next enqueue executes `self.rear.next = node` on this stale reference, silently corrupting the chain. The queue appears to hold one element, but `front` is `None` and `rear` is an orphan.

Always pair the `front` update with a `rear` cleanup:

```python
self.front = self.front.next
if self.front is None:
    self.rear = None
```

---

### Mistake 3 — Enqueuing by Updating `front` Instead of `rear`

```python
# Wrong — inserts at the front, making this a stack, not a queue
def enqueue(self, data):
    node = Node(data)
    node.next = self.front    # ← prepending, not appending
    self.front = node
```

Prepending gives LIFO (stack) behaviour. Appending to `rear` gives FIFO (queue) behaviour. The two operations are mirror images; mixing them destroys the ordering guarantee.

---

### Mistake 4 — Computing Size by Traversal

```python
# Avoid — O(n) every call
def __len__(self):
    count = 0
    node = self.front
    while node:
        count += 1
        node = node.next
    return count
```

Maintain a `_size` counter instead. Increment in `enqueue`, decrement in `dequeue`. Length becomes O(1) with no traversal cost. This matters especially in BFS loops where `len(q)` is called once per level to fix the level boundary.

---

### Mistake 5 — Dequeuing Without an Empty Check

```python
q = Queue()
q.enqueue(1)
q.dequeue()
q.dequeue()    # AttributeError: 'NoneType' object has no attribute 'data'
```

When `front` is `None`, accessing `self.front.data` raises `AttributeError`, not `IndexError`. Always guard dequeue calls:

```python
if not q.is_empty():
    value = q.dequeue()
```

Or handle the exception explicitly if the guard clutters the call site:

```python
try:
    value = q.dequeue()
except IndexError:
    value = None
```

---

### Mistake 6 — Confusing Which End Is Front and Which Is Rear

In the linked list queue, the chain flows **front → rear**. Enqueue appends to the rear. Dequeue removes from the front.

```
Correct mental model:

  front                              rear
    │                                 │
    ▼                                 ▼
  [10 │ ──►] ──► [20 │ ──►] ──► [30 │ None]

  dequeue() removes 10  ← from front
  enqueue(40) appends  40 → to rear
```

A common error is reversing this — enqueuing at the front (making it a stack) or dequeuing from the rear (making it LIFO). The mnemonic: elements **enter** at the rear and **exit** at the front, just like a physical queue.

## Where This Pattern Appears

**Operating System Process Scheduling**

The kernel's run queue is a linked list of process control blocks. Each block is a node. Scheduling a process detaches its node from the front in O(1). Adding a newly ready process appends its node to the rear in O(1). The linked structure allows the scheduler to also splice, reorder, or remove nodes from arbitrary positions when priorities change — something a `deque` cannot do without rebuilding itself.

**Network Packet Buffers**

High-performance network drivers maintain packet queues as linked lists of buffer descriptors. Each descriptor node points to the packet payload. When a packet arrives, a descriptor is allocated and appended to the rear. When the NIC is ready to transmit, the front descriptor is consumed and its memory returned to a free pool immediately. Direct control over per-packet allocation and deallocation is essential at the throughput rates involved.

**LRU Cache (Least Recently Used)**

An LRU cache evicts the least recently used item when capacity is exceeded. The standard implementation combines a hash map with a doubly linked list. The list maintains access order: the most recently used node is moved to the front; the least recently used node sits at the rear and is evicted when needed. The queue structure is embedded inside the cache itself — the nodes are first-class objects that both the hash map and the list share by reference, something impossible with an opaque `deque`.

**Producer–Consumer Pipelines with Backpressure**

In systems where producers and consumers operate at different speeds, a linked queue between them absorbs bursts naturally: each produced item allocates one node; each consumed item frees one node. Memory grows and shrinks in exact proportion to the current backlog. If the system imposes a memory limit, the node count serves directly as a backpressure signal — no separate accounting is needed.

## Summary

| Concept | What It Means |
|---|---|
| FIFO | First In, First Out — the defining rule of a queue |
| `front` pointer | Always references the node to be dequeued next |
| `rear` pointer | Always references the most recently enqueued node |
| Enqueue | New node; link `rear.next` to it; move `rear` to new node |
| Dequeue | Save `front.data`; advance `front` to `front.next`; if now `None`, clear `rear` |
| Empty check | `front is None` — both pointers are `None` when queue is empty |
| Node freed on dequeue | No deferred cleanup; memory returns at the exact moment of removal |
| All core operations | O(1) — no traversal, no reallocation |
| Two pointers required | Unlike a stack (one pointer), a queue needs `front` and `rear` to avoid O(n) enqueue |

The linked list queue is the direct translation of the abstract queue concept into explicit pointer logic. Two references, one counter, one node per element. No capacity, no index, no array. A chain that grows at the rear and shrinks from the front — with each end touched independently, in constant time, regardless of how many elements sit between them.
