# Circular Queue — Array-Based Implementation

---

## The Problem with a Simple Array Queue

The queues we built so far — list-based, `deque`-based, and linked-list-based — all grow and shrink dynamically. Memory is requested when elements arrive and released when they leave. For most applications, this is exactly right.

But a different class of problems exists where **the queue size is known in advance and fixed**. Ring buffers in audio drivers. Packet queues in network interfaces. Sensor pipelines in embedded systems. Task queues with a hard slot limit. In all of these, the maximum number of simultaneously live elements is bounded and known at initialisation time. Dynamic allocation introduces overhead — allocation calls, garbage collection pressure, heap fragmentation — that these environments cannot afford.

The natural response is: allocate a fixed array of capacity k once, and reuse it forever. The queue lives entirely inside this array. No allocation happens during normal operation. No memory is released until the queue itself is destroyed.

The challenge is that a naive fixed-array queue wastes its own memory. Watch what happens when you use a plain array as a queue with a fixed size:

```
Initial array of capacity 5 — all slots empty:

 Index:   0     1     2     3     4
        ┌─────┬─────┬─────┬─────┬─────┐
        │     │     │     │     │     │
        └─────┴─────┴─────┴─────┴─────┘
          front = 0, rear = 0

Enqueue A, B, C:

 Index:   0     1     2     3     4
        ┌─────┬─────┬─────┬─────┬─────┐
        │  A  │  B  │  C  │     │     │
        └─────┴─────┴─────┴─────┴─────┘
          front = 0, rear = 3

Dequeue A, B:

 Index:   0     1     2     3     4
        ┌─────┬─────┬─────┬─────┬─────┐
        │ --- │ --- │  C  │     │     │
        └─────┴─────┴─────┴─────┴─────┘
          front = 2, rear = 3

Enqueue D, E, F:

 Index:   0     1     2     3     4
        ┌─────┬─────┬─────┬─────┬─────┐
        │ --- │ --- │  C  │  D  │  E  │
        └─────┴─────┴─────┴─────┴─────┘
          front = 2, rear = 5

rear has reached the end of the array.
But slots 0 and 1 are empty!
The naive queue declares itself FULL — even though only 3 of 5 slots are used.
Enqueueing F would fail, despite available capacity.
```

The slots at indices 0 and 1 are wasted forever. As the queue operates, the `front` pointer marches right and the `rear` pointer marches right. Both escape off the end of the array. The memory to the left of `front` is permanently stranded.

This is called **array drift**, and it is the fundamental defect of the linear fixed-array queue.

---

## The Circular Queue — Wrapping the Array

The fix is to treat the array as if its last slot connects back to its first slot. When `rear` reaches the end of the array, the next enqueue wraps it back to index 0. When `front` reaches the end, the next dequeue wraps it to index 0. The array is logically circular.

```
Same array, treated as a ring:

         0
       ┌───┐
     4 │   │ 1
       │   │
     3 │   │ 2
       └───┘

After enqueue A, B, C and dequeue A, B, then enqueue D, E, F:

         0
       ┌─F─┐
     4 E   D 1
       │   │
     3 │   C 2
       └───┘

front = 2 (C)
rear  = 1 (after F, wraps back)
size  = 4

Slots 0 and 1 are now reachable again.
The array is never stranded.
```

The wrap is implemented with a single operation: the **modulo operator**.

```python
rear = (rear + 1) % capacity
```

When `rear` is at index 4 and capacity is 5:

```
(4 + 1) % 5 = 0   → wraps to index 0
```

When `front` is at index 4:

```
(4 + 1) % 5 = 0   → wraps to index 0
```

No special-case branching. One arithmetic expression handles all cases.

## The Circular Queue Class

```python
class CircularQueue:
    def __init__(self, capacity):
        self._capacity = capacity
        self._queue = [None] * capacity   # Fixed array allocated once
        self._front = 0                   # Index of the next element to dequeue
        self._rear = 0                    # Index where the next enqueue will write
        self._size = 0                    # Number of elements currently stored
```

Five fields. One fixed array. No dynamic allocation after `__init__`.

`_front` and `_rear` start at 0. `_size` starts at 0. As elements flow in and out, `_front` and `_rear` chase each other around the array, always separated by exactly `_size` positions.

## Enqueue — Writing at `_rear`

```python
def enqueue(self, data):
    """Add an element at the rear. Raises OverflowError if full. O(1)."""
    if self.is_full():
        raise OverflowError("enqueue on a full circular queue")
    self._queue[self._rear] = data          # Write at the current rear position
    self._rear = (self._rear + 1) % self._capacity   # Advance rear, wrapping if needed
    self._size += 1
```

**Trace through enqueue(D) onto a queue holding [C] with capacity 5, front=2, rear=3:**

```
Step 1 — Write D at index rear (3):

 Index:   0     1     2     3     4
        ┌─────┬─────┬─────┬─────┬─────┐
        │     │     │  C  │  D  │     │
        └─────┴─────┴─────┴─────┴─────┘
                      ▲      ▲
                    front   (just written)

Step 2 — Advance rear: (3 + 1) % 5 = 4:

        rear now = 4, front = 2, size = 2
```

**Trace through enqueue(F) after the array holds [_, _, C, D, E], rear=4:**

```
Step 1 — Write F at index rear (4):

 Index:   0     1     2     3     4
        ┌─────┬─────┬─────┬─────┬─────┐
        │     │     │  C  │  D  │  F  │
        └─────┴─────┴─────┴─────┴─────┘

Step 2 — Advance rear: (4 + 1) % 5 = 0  ← WRAP:

        rear now = 0, front = 2, size = 3

Next enqueue will write at index 0 — the previously stranded slot.
```

## Dequeue — Reading from `_front`

```python
def dequeue(self):
    """Remove and return the front element. Raises IndexError if empty. O(1)."""
    if self.is_empty():
        raise IndexError("dequeue from an empty circular queue")
    data = self._queue[self._front]              # Read the front element
    self._queue[self._front] = None              # Clear the slot (optional but clean)
    self._front = (self._front + 1) % self._capacity  # Advance front, wrapping if needed
    self._size -= 1
    return data
```

**Trace through dequeue() on [_, _, C, D, F], front=2, rear=0:**

```
Step 1 — Read value at index front (2): saved = C

Step 2 — Clear slot 2:

 Index:   0     1     2     3     4
        ┌─────┬─────┬─────┬─────┬─────┐
        │     │     │ --- │  D  │  F  │
        └─────┴─────┴─────┴─────┴─────┘

Step 3 — Advance front: (2 + 1) % 5 = 3:

        front now = 3, rear = 0, size = 2

Step 4 — Return C.
```

**Trace through dequeue() after front wraps to index 0:**

```
State: front=4, rear=2, size=3 → [G, H, _, _, F]

Step 1 — Read value at index 4: saved = F
Step 2 — Clear slot 4.
Step 3 — Advance front: (4 + 1) % 5 = 0  ← WRAP

        front now = 0 — continues reading G next.
```

## Full, Empty, and the Capacity Ambiguity

A classic trap: when `_front == _rear`, the queue is either **empty** or **full**. Both states produce the same pointer relationship. A separate `_size` counter resolves this unambiguously.

```
Empty: _front = _rear = 2, _size = 0

 Index:   0     1     2     3     4
        ┌─────┬─────┬─────┬─────┬─────┐
        │ --- │ --- │     │     │     │
        └─────┴─────┴─────┴─────┴─────┘
                      ▲
                front = rear = 2

Full: _front = _rear = 2, _size = 5

 Index:   0     1     2     3     4
        ┌─────┬─────┬─────┬─────┬─────┐
        │  E  │  F  │  A  │  B  │  C  │  (D was dequeued, E, F wrapped around)
        └─────┴─────┴─────┴─────┴─────┘
                      ▲
                front = rear = 2

Both look identical from the pointers alone.
_size = 0 → empty. _size = 5 → full. _size decides.
```

```python
def is_empty(self):
    """Return True if the queue has no elements. O(1)."""
    return self._size == 0

def is_full(self):
    """Return True if the queue is at capacity. O(1)."""
    return self._size == self._capacity
```

An alternative to `_size` is reserving one slot as a sentinel — never filling the array completely, so `(rear + 1) % capacity == front` means full and `front == rear` means empty. This wastes one slot but avoids maintaining the counter. The `_size` approach wastes no capacity and is less error-prone.

## Peek — Reading Without Removing

```python
def front_peek(self):
    """Return the front element without removing it. Raises IndexError if empty. O(1)."""
    if self.is_empty():
        raise IndexError("front of an empty circular queue")
    return self._queue[self._front]

def rear_peek(self):
    """Return the rear element without removing it. Raises IndexError if empty. O(1)."""
    if self.is_empty():
        raise IndexError("rear of an empty circular queue")
    return self._queue[(self._rear - 1) % self._capacity]
```

`rear_peek` uses `(self._rear - 1) % self._capacity` because `_rear` always points to the **next empty slot**, not the last filled slot. Stepping back by one (with modulo wrap for index 0) gives the most recently enqueued element.

## Supporting Methods

```python
def __len__(self):
    """Return the number of elements. O(1)."""
    return self._size

def __repr__(self):
    """Display elements in logical order from front to rear. O(n)."""
    if self.is_empty():
        return "CircularQueue(capacity={}, size=0): []".format(self._capacity)
    elements = []
    for i in range(self._size):
        idx = (self._front + i) % self._capacity
        elements.append(repr(self._queue[idx]))
    return "CircularQueue(capacity={}, size={}): [{}]".format(
        self._capacity, self._size, ", ".join(elements)
    )
```

`__repr__` reconstructs the logical order by walking from `_front`, stepping modulo capacity. The underlying array may be split across the wrap boundary — for example, the logical sequence [C, D, E, A, B] might sit at indices [2, 3, 4, 0, 1] in the array. The loop makes this transparent to the caller.

## Complete Implementation

```python
class CircularQueue:
    def __init__(self, capacity):
        """Initialise a circular queue of fixed capacity. O(n) to allocate array."""
        if capacity <= 0:
            raise ValueError("capacity must be a positive integer")
        self._capacity = capacity
        self._queue = [None] * capacity
        self._front = 0
        self._rear = 0
        self._size = 0

    # ── Core operations ──────────────────────────────────────────────────────

    def enqueue(self, data):
        """Add an element at the rear. Raises OverflowError if full. O(1)."""
        if self.is_full():
            raise OverflowError("enqueue on a full circular queue")
        self._queue[self._rear] = data
        self._rear = (self._rear + 1) % self._capacity
        self._size += 1

    def dequeue(self):
        """Remove and return the front element. Raises IndexError if empty. O(1)."""
        if self.is_empty():
            raise IndexError("dequeue from an empty circular queue")
        data = self._queue[self._front]
        self._queue[self._front] = None
        self._front = (self._front + 1) % self._capacity
        self._size -= 1
        return data

    def front_peek(self):
        """Return the front element without removing it. Raises IndexError if empty. O(1)."""
        if self.is_empty():
            raise IndexError("front of an empty circular queue")
        return self._queue[self._front]

    def rear_peek(self):
        """Return the rear element without removing it. Raises IndexError if empty. O(1)."""
        if self.is_empty():
            raise IndexError("rear of an empty circular queue")
        return self._queue[(self._rear - 1) % self._capacity]

    # ── State queries ─────────────────────────────────────────────────────────

    def is_empty(self):
        """Return True if the queue has no elements. O(1)."""
        return self._size == 0

    def is_full(self):
        """Return True if the queue is at capacity. O(1)."""
        return self._size == self._capacity

    def __len__(self):
        """Return the number of elements currently stored. O(1)."""
        return self._size

    # ── Display ───────────────────────────────────────────────────────────────

    def __repr__(self):
        """Display elements in logical order from front to rear. O(n)."""
        if self.is_empty():
            return "CircularQueue(capacity={}, size=0): []".format(self._capacity)
        elements = []
        for i in range(self._size):
            idx = (self._front + i) % self._capacity
            elements.append(repr(self._queue[idx]))
        return "CircularQueue(capacity={}, size={}): [{}]".format(
            self._capacity, self._size, ", ".join(elements)
        )
```

```python
cq = CircularQueue(5)

print(cq.is_empty())     # True
print(cq.is_full())      # False

cq.enqueue(10)
cq.enqueue(20)
cq.enqueue(30)

print(cq.dequeue())      # 20

cq.enqueue(40)
cq.enqueue(50)
cq.enqueue(60)
cq.enqueue(70)           # Slots freed by the two dequeues are now reused
print(cq)                # CircularQueue(capacity=5, size=5): [30, 40, 50, 60, 70]
print(cq.is_full())      # True

    cq.enqueue(99)       # OverflowError: enqueue on a full circular queue

print(cq.dequeue())      # 40
cq.enqueue(80)
cq.enqueue(90)
print(cq)                # CircularQueue(capacity=5, size=5): [50, 60, 70, 80, 90]

# Drain the queue
while not cq.is_empty():
    print(cq.dequeue(), end=" ")
# 50 60 70 80 90

print(cq.is_empty())     # True
```

## Practical Patterns

### Pattern 1 — Ring Buffer for Audio Streaming

An audio driver maintains a ring buffer between the thread that fills audio samples and the thread that feeds them to the hardware. The producer writes samples at the rear; the hardware consumer reads from the front. Because the buffer is fixed-size and pre-allocated, there are no allocation stalls mid-stream.

```python
class AudioRingBuffer:
    """
    Fixed-size ring buffer for audio samples.
    Producer calls write(); consumer calls read().
    """
    def __init__(self, capacity):
        self._buf = CircularQueue(capacity)

    def write(self, sample):
        """Producer: write one audio sample. Returns False if buffer is full."""
        if self._buf.is_full():
            return False      # Signal backpressure — producer must wait
        self._buf.enqueue(sample)
        return True

    def read(self):
        """Consumer: read one audio sample. Returns None if buffer is empty."""
        if self._buf.is_empty():
            return None       # Underrun — consumer must wait
        return self._buf.dequeue()

    def fill_level(self):
        """Return the number of samples currently buffered."""
        return len(self._buf)

    def capacity(self):
        return self._buf._capacity


# Simulate a 48 kHz audio stream with a 16-sample buffer
buffer = AudioRingBuffer(capacity=16)

# Producer fills 10 samples
for i in range(10):
    buffer.write(i * 0.1)    # Samples: 0.0, 0.1, 0.2, ...

print(f"Buffer level: {buffer.fill_level()} / {buffer.capacity()}")   # 10 / 16

# Consumer reads 6 samples
for _ in range(6):
    print(f"Played: {buffer.read():.1f}")

print(f"Buffer level after playback: {buffer.fill_level()}")          # 4
```

The buffer never grows. The capacity is chosen to tolerate jitter between producer and consumer without dropping samples.

### Pattern 2 — CPU Round-Robin Scheduler

A round-robin scheduler gives each process a fixed time slice in cyclic order. Processes that are not done are re-enqueued. Completed ones are dropped. The circular queue is ideal: the number of concurrent processes is bounded, allocation per-cycle is zero.

```python
def round_robin(processes, time_slice, capacity=20):
    """
    Simulate round-robin CPU scheduling with a circular queue.
    processes: list of (name, burst_time) tuples
    time_slice: CPU units per turn
    """
    cq = CircularQueue(capacity)
    for name, burst in processes:
        cq.enqueue([name, burst])

    time_elapsed = 0
    print(f"{'Time':>6}  {'Process':<14}  Result")
    print("─" * 38)

    while not cq.is_empty():
        name, remaining = cq.dequeue()
        run = min(remaining, time_slice)
        time_elapsed += run
        remaining -= run

        if remaining > 0:
            cq.enqueue([name, remaining])       # Back to the rear
            result = f"{remaining} units left"
        else:
            result = "✓ DONE"

        print(f"{time_elapsed:>6}  {name:<14}  {result}")

    print(f"\nTotal time: {time_elapsed}")


processes = [
    ("Web-Server",  12),
    ("DB-Query",     5),
    ("Compiler",    18),
    ("Logger",       3),
]
round_robin(processes, time_slice=4)
```

```
  Time  Process         Result
──────────────────────────────────────
     4  Web-Server      8 units left
     8  DB-Query        1 units left
    12  Compiler        14 units left
    15  Logger          ✓ DONE
    19  Web-Server      4 units left
    20  DB-Query        ✓ DONE
    24  Compiler        10 units left
    28  Web-Server      ✓ DONE
    32  Compiler        6 units left
    36  Compiler        2 units left
    38  Compiler        ✓ DONE

Total time: 38
```

The capacity bound reflects the maximum number of simultaneously runnable processes — a known quantity in most operating environments.

### Pattern 3 — Sliding Window Log with Bounded Memory

A monitoring system records the last N events. Older events are automatically overwritten as new ones arrive. This is a classic **overwrite-on-full** circular buffer — a minor policy variation on the standard circular queue.

```python
class SlidingLog:
    """
    Keeps the most recent `capacity` events.
    When full, the oldest event is silently overwritten.
    """
    def __init__(self, capacity):
        self._capacity = capacity
        self._log = [None] * capacity
        self._head = 0      # Next write position
        self._size = 0

    def record(self, event):
        """Record an event; overwrites the oldest when full."""
        self._log[self._head] = event
        self._head = (self._head + 1) % self._capacity
        if self._size < self._capacity:
            self._size += 1

    def recent(self):
        """Return all recorded events in chronological order."""
        start = (self._head - self._size) % self._capacity
        return [self._log[(start + i) % self._capacity]
                for i in range(self._size)]


log = SlidingLog(capacity=5)

events = [
    "User logged in",
    "Page /home loaded",
    "API call /search",
    "Page /product/42 loaded",
    "User added to cart",
    "Checkout initiated",
    "Payment processed",
]

for ev in events:
    log.record(ev)
    print(f"Recorded: '{ev}'")
    print(f"  Recent: {log.recent()}\n")
```

```
Recorded: 'User logged in'
  Recent: ['User logged in']

Recorded: 'Page /home loaded'
  Recent: ['User logged in', 'Page /home loaded']

...

Recorded: 'Checkout initiated'
  Recent: ['API call /search', 'Page /product/42 loaded',
            'User added to cart', 'Checkout initiated']
            # 'User logged in' and 'Page /home loaded' have been overwritten

Recorded: 'Payment processed'
  Recent: ['Page /product/42 loaded', 'User added to cart',
            'Checkout initiated', 'Payment processed']
```

Memory is permanently bounded. No matter how many events arrive, the log uses exactly `capacity * sizeof(event)` bytes.

### Pattern 4 — Hot Potato with Fixed Capacity

The hot potato game in a circular queue is more natural here than in any previous implementation: the queue physically **is** a ring, not just a chain that wraps abstractly.

```python
import random

def hot_potato(players, max_passes, seed=None):
    """
    Eliminate players one at a time by passing the potato around.
    The circular queue's bounded size matches the fixed player count exactly.
    """
    if seed is not None:
        random.seed(seed)

    cq = CircularQueue(len(players))
    for p in players:
        cq.enqueue(p)

    print(f"Starting players: {players}\n")
    round_num = 1

    while len(cq) > 1:
        passes = random.randint(1, max_passes)
        for _ in range(passes):
            cq.enqueue(cq.dequeue())        # Rotate: front goes to rear
        eliminated = cq.dequeue()
        print(f"Round {round_num:2d} ({passes:2d} passes): {eliminated} eliminated"
              f"  →  remaining: {len(cq)}")
        round_num += 1

    print(f"\nWinner: {cq.dequeue()}")


hot_potato(
    ["Alice", "Bob", "Carol", "Dave", "Eve", "Frank"],
    max_passes=10,
    seed=7
)
```

```
Starting players: ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank']

Round  1 ( 8 passes): Dave eliminated     →  remaining: 5
Round  2 ( 3 passes): Alice eliminated    →  remaining: 4
Round  3 ( 7 passes): Frank eliminated    →  remaining: 3
Round  4 ( 2 passes): Eve eliminated      →  remaining: 2
Round  5 ( 9 passes): Carol eliminated    →  remaining: 1

Winner: Bob
```

### Pattern 5 — Batch Task Processor with Backpressure

A bounded circular queue between a producer and consumer enforces backpressure naturally. When the queue is full, the producer must wait. When it is empty, the consumer must wait. No additional mechanism is needed — the queue's fullness IS the backpressure signal.

```python
import time

def simulate_pipeline(capacity, num_tasks):
    """
    Simulate a bounded producer-consumer pipeline.
    Producer generates tasks; consumer processes them.
    When the queue is full, the producer pauses (backpressure).
    """
    queue = CircularQueue(capacity)
    produced = 0
    consumed = 0

    print(f"Pipeline: capacity={capacity}, tasks={num_tasks}\n")
    print(f"{'Action':<30} {'Queue Size':>12} {'Status'}")
    print("─" * 56)

    while consumed < num_tasks:
        # Producer: try to add a task
        if produced < num_tasks and not queue.is_full():
            task_id = produced + 1
            queue.enqueue(f"Task-{task_id:03d}")
            produced += 1
            print(f"  Produced Task-{task_id:03d}             "
                  f"{len(queue):>6}/{capacity}   {'FULL' if queue.is_full() else ''}")

        # Consumer: process one task if available
        if not queue.is_empty():
            task = queue.dequeue()
            consumed += 1
            print(f"  Consumed {task:<20} "
                  f"{len(queue):>6}/{capacity}")

    print(f"\nAll {num_tasks} tasks processed.")


simulate_pipeline(capacity=4, num_tasks=9)
```

```
Pipeline: capacity=4, tasks=9

Action                         Queue Size  Status
────────────────────────────────────────────────────────
  Produced Task-001                  1/4
  Consumed Task-001                  0/4
  Produced Task-002                  1/4
  Consumed Task-002                  0/4
  Produced Task-003                  1/4
  ...
```

The circular queue holds in-flight tasks without unbounded memory growth. In production systems, this pattern prevents a fast producer from exhausting memory when the consumer is slow.

## Circular Queue vs Linear Queue vs Linked List Queue

| Property | Linear Array Queue | Linked List Queue | Circular Queue |
|---|---|---|---|
| Memory layout | Contiguous array | Scattered nodes | Contiguous array |
| Allocation after init | Array grows (Python list) | One node per enqueue | None |
| Memory freed on dequeue | Deferred (list shrinks lazily) | Immediately per node | Not applicable (pre-allocated) |
| Max capacity | Unbounded | Unbounded | Fixed at init |
| Slot reuse | No — array drifts right | N/A | Yes — wraps around |
| `enqueue` | O(1) amortised | O(1) | O(1) |
| `dequeue` | O(n) for plain list; O(1) for deque | O(1) | O(1) |
| `is_full` check | Not applicable | Not applicable | O(1) — required |
| Cache behaviour | Excellent | Poor (pointer chasing) | Excellent |
| Ideal use case | General-purpose, dynamic | Custom structures, embedded nodes | Fixed-size buffers, real-time systems |

The circular queue is not universally superior to the linked list queue. Choose it when:
- Capacity is known and bounded upfront.
- Allocation overhead during operation is unacceptable.
- Cache locality matters — the fixed array gives predictable access patterns.

Choose the linked list queue when:
- Capacity is unpredictable.
- Memory must be reclaimed immediately on dequeue.
- Nodes carry additional fields used by a larger structure.

## Common Mistakes

### Mistake 1 — Using `_rear` Directly as the Last Element Index

```python
# Wrong — _rear points to the NEXT write position, not the last element
def rear_peek(self):
    return self._queue[self._rear]    # Returns None (the next empty slot)

# Correct — step back by one, with wrap
def rear_peek(self):
    return self._queue[(self._rear - 1) % self._capacity]
```

`_rear` is always one step ahead of the most recently written slot. Direct access reads an empty (or stale) slot. Subtracting 1 with modulo is the correct idiom.

---

### Mistake 2 — Detecting Full/Empty from Pointer Equality Alone

```python
# Wrong — cannot distinguish full from empty
def is_empty(self):
    return self._front == self._rear    # True when full AND when empty

def is_full(self):
    return self._front == self._rear    # Same expression — meaningless
```

Pointers converge for both states. Always maintain `_size` (or a reserved sentinel slot) to resolve the ambiguity.

---

### Mistake 3 — Forgetting Modulo on Front or Rear Advancement

```python
# Wrong — _front marches past the end of the array
def dequeue(self):
    data = self._queue[self._front]
    self._front += 1          # No modulo → IndexError when _front >= _capacity
    self._size -= 1
    return data

# Correct
    self._front = (self._front + 1) % self._capacity
```

The entire point of a circular queue is the wrap. Omitting modulo from either advancement reverts to a drifting linear queue that raises `IndexError` on overflow.

---

### Mistake 4 — Enqueuing into a Full Queue Without Checking

```python
cq = CircularQueue(3)
cq.enqueue("A")
cq.enqueue("B")
cq.enqueue("C")
cq.enqueue("D")    # OverflowError if guarded; silent corruption if not

# Silent corruption (no guard):
# _rear wraps to 0 and overwrites "A" while _size becomes 4
# but _capacity is 3 — _size now lies about the queue's true state
```

The circular queue cannot grow. Enqueuing into a full queue overwrites the front element, corrupting the FIFO order silently. Always check `is_full()` before enqueue, or deliberately choose the overwrite policy (as in `SlidingLog`) and document it explicitly.

---

### Mistake 5 — Off-by-One in `__repr__` Traversal

```python
# Wrong — traverses capacity slots, not size slots
def __repr__(self):
    elements = []
    for i in range(self._capacity):          # ← should be self._size
        idx = (self._front + i) % self._capacity
        elements.append(repr(self._queue[idx]))
    return repr(elements)
```

When the queue is partially filled, this reads `None` values from empty slots and includes them in the output. Iterate over `range(self._size)` to read only live elements.

---

### Mistake 6 — Negative Index from `_rear - 1` Without Modulo

```python
# Fragile — fails when _rear == 0
def rear_peek(self):
    return self._queue[self._rear - 1]   # Returns self._queue[-1] in Python

# Python actually allows negative list indices, so this accidentally "works"
# for Python lists — but it reads the last physical slot (index capacity-1),
# which may not be the logical rear element if _rear == 0 and capacity-1
# is not the most recently written position.

# Correct — always use modulo
def rear_peek(self):
    return self._queue[(self._rear - 1) % self._capacity]
```

Python's negative indexing makes `self._queue[-1]` valid but semantically wrong in this context. Modulo guarantees the correct physical index regardless of the pointer value.

## Full Reference

```python
# Instantiation
cq = CircularQueue(capacity)     # Fixed capacity — cannot change after creation

# Core operations — all O(1)
cq.enqueue(x)        # Add x to the rear; raises OverflowError if full
cq.dequeue()         # Remove and return the front element; raises IndexError if empty
cq.front_peek()      # Read front element without removing; raises IndexError if empty
cq.rear_peek()       # Read rear element without removing; raises IndexError if empty

# State queries — all O(1)
cq.is_empty()        # True if size == 0
cq.is_full()         # True if size == capacity
len(cq)              # Number of elements currently stored

# Display — O(n), logical order front to rear
print(cq)            # CircularQueue(capacity=k, size=n): [front, ..., rear]

# Key invariants always maintained:
#   0 <= _front < capacity
#   0 <= _rear  < capacity
#   0 <= _size  <= capacity
#   _rear = (_front + _size) % capacity
```

## Where This Pattern Appears

**Embedded and Real-Time Systems**

Microcontrollers with kilobytes of RAM cannot afford heap allocation during operation. Circular buffers are the standard data structure for UART receive/transmit, SPI transfers, I2C message queues, and ADC sample pipelines. The fixed array is placed in static memory at compile time. Enqueue and dequeue are interrupt-safe when combined with atomic index updates.

**Audio and Video Processing**

Every digital audio workstation, codec, and streaming media player uses ring buffers between their I/O threads and processing threads. The buffer must be large enough to absorb scheduling jitter (the OS pausing the audio thread) without causing an underrun (silence) or overflow (dropped samples). The size is tuned at startup; it never changes during playback.

**Network Interface Cards**

NIC drivers maintain descriptor rings — circular queues of DMA buffer descriptors. The kernel adds descriptors at the producer end; the hardware consumes them at the consumer end. Both ends advance independently using head and tail pointers stored in NIC registers. The Linux `e1000` and `ixgbe` drivers are concrete examples, each implementing descriptor rings as circular queues of fixed depth.

**Operating System Kernel IPC**

Pipe and FIFO implementations in POSIX kernels use a fixed circular buffer in kernel memory. When a process writes to a pipe, bytes enter at the write end; when another process reads, bytes leave at the read end. The buffer size (typically 64 KB on Linux) is fixed. Writing blocks when full; reading blocks when empty. The circular queue is the direct implementation of this mechanism.

**Database Write-Ahead Logs**

Some database engines use a circular buffer as the in-memory segment of the write-ahead log. New log records are appended at the rear. The checkpoint thread consumes from the front, persisting records to disk. The circular buffer decouples transaction throughput from disk write latency without unbounded memory growth.

## Summary

| Concept | What It Means |
|---|---|
| Array drift | Linear fixed-array queues strand memory to the left of `_front` permanently |
| Circular wrap | `(index + 1) % capacity` turns a linear array into a ring |
| `_front` | Index of the next element to be dequeued |
| `_rear` | Index where the next enqueue will write (one past the last element) |
| `_size` | Required to distinguish empty (`_size == 0`) from full (`_size == capacity`) |
| `is_full()` | Unique to circular queues — not a concept in dynamic queues |
| All core operations | O(1) — one arithmetic step plus one array access |
| Zero allocation after init | The entire lifetime of the queue uses the array allocated in `__init__` |
| Overwrite variant | Set `_size` tracking aside and allow rear to overwrite front — models sliding logs and ring buffers |
| Primary use case | Bounded, real-time, or memory-constrained environments where dynamic allocation is expensive or forbidden |

The circular queue solves exactly one problem — array drift — and it solves it completely, with one arithmetic operation. Every slot in the array is available to every element that will ever pass through the queue. Memory does not accumulate. Pointers do not escape. The queue stays in place while the data flows through it.
