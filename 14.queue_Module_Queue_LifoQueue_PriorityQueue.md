# queue Module — `Queue`, `LifoQueue`, `PriorityQueue`

---

## Before We Begin — What Problem Are We Even Solving?

Imagine you are building a web server that handles incoming requests from multiple browser tabs simultaneously.

Each tab fires a request at the exact same moment. Your server has only one CPU thread available. You cannot process all requests at once — you must decide: *which one goes first?*

Now someone uploads a large file in one tab. In another tab, your boss is waiting for a simple login response. Should both requests wait in the same line? Should the boss's login jump the queue?

You have three different scheduling problems:

- **Fair queue** — requests served in the order they arrived (first come, first served)
- **Stack-based reversal** — last request added is processed first (LIFO — useful for undo chains, backtracking)
- **Priority queue** — most important request is always served first, regardless of arrival order

Now multiply this by the fact that your server runs **multiple threads simultaneously**, each pulling requests from the same queue. Suddenly, order and safety both matter.

You need a data structure that:
1. Handles all three scheduling strategies
2. Is **thread-safe by design** — no data corruption when threads read/write simultaneously
3. Blocks a thread automatically when the queue is empty — no busy-waiting in loops

That is exactly what Python's **`queue` module** provides.

---

## The Core Idea — Three Classes, Three Scheduling Disciplines

Python's `queue` module provides three classes, each implementing a different ordering strategy:

```
queue.Queue          → FIFO  (First In, First Out)  — normal queue
queue.LifoQueue      → LIFO  (Last In, First Out)   — stack behaviour
queue.PriorityQueue  → Priority-ordered              — smallest item first
```

All three share **the exact same interface** — `.put()`, `.get()`, `.empty()`, `.qsize()`, `.task_done()`, `.join()`. The only difference is the **ordering** of what `.get()` returns.

```
queue.Queue (FIFO):

  put(10) → put(20) → put(30)

    ┌──────────────────────────┐
    │  10  │  20  │  30       │
    └──────────────────────────┘
    get() → 10   (oldest first)


queue.LifoQueue (LIFO):

  put(10) → put(20) → put(30)

    ┌──────────────────────────┐
    │  10  │  20  │  30       │
    └──────────────────────────┘
    get() → 30   (newest first)


queue.PriorityQueue (Min-Heap):

  put(50) → put(10) → put(30)

    ┌──────────────────────────┐
    │  10  │  50  │  30       │  (heap-ordered internally)
    └──────────────────────────┘
    get() → 10   (smallest first)
```

---

## Why Does This Matter? The Real-World Motivation

You already know `collections.deque`. Why learn `queue`?

| Feature | `collections.deque` | `queue.Queue` / `LifoQueue` / `PriorityQueue` |
|---|---|---|
| Thread-safe | **No** — requires manual locking | **Yes — built-in locks** |
| Blocking `.get()` | No — raises `IndexError` immediately | **Yes — waits until item available** |
| Blocking `.put()` with `maxsize` | No | **Yes — waits until space available** |
| Priority ordering | No | **Yes — `PriorityQueue`** |
| LIFO ordering | Manual | **Yes — `LifoQueue`** |
| `task_done()` / `.join()` | No | **Yes — track work completion** |
| Use case | Single-threaded algorithms | **Multi-threaded producer-consumer** |

The critical difference: **`deque` is for algorithms; `queue` is for threads.**

When two threads simultaneously call `deque.appendleft()` and `deque.pop()`, you get a **race condition** — unpredictable crashes or silent data corruption. The `queue` module solves this with an internal `threading.Lock` that you never have to manage yourself.

Real-world uses:
- **Web server request handling** — thread pool pulls tasks from `Queue`
- **Download managers** — multiple downloader threads share a `Queue` of URLs
- **Undo/Redo systems** — `LifoQueue` reverses operations in order
- **Task schedulers** — `PriorityQueue` ensures high-priority jobs run first
- **Log processing pipelines** — producer threads write logs; consumer threads process them
- **Build systems** — tasks with dependencies ordered by priority

## `queue.Queue` — FIFO Queue

### What It Does

`Queue` implements a standard **first-in, first-out** queue. Items come out in exactly the order they went in. This is the workhorse of producer-consumer patterns.

### Creating and Basic Usage

```python
import queue

q = queue.Queue()           # Unbounded FIFO queue
q = queue.Queue(maxsize=5)  # Bounded — blocks when full

q.put(10)     # Add item — blocks if full (when maxsize set)
q.put(20)
q.put(30)

print(q.get())    # 10 — oldest item first
print(q.get())    # 20
print(q.get())    # 30
```

### ASCII Trace — FIFO Ordering

```
State after put(10), put(20), put(30):

    FRONT                         REAR
      │                            │
      ▼                            ▼
  ┌───────┬───────┬───────┐
  │  10   │  20   │  30   │     ← items enter from the rear
  └───────┴───────┴───────┘
      ↑
  get() returns 10 — the FRONT item

After get():
  ┌───────┬───────┐
  │  20   │  30   │
  └───────┴───────┘
      ↑
  get() returns 20 next
```

### Blocking Behaviour — The Key Feature

```python
import queue
import threading

q = queue.Queue()

def consumer():
    print("Consumer waiting...")
    item = q.get()    # BLOCKS HERE until something is available
    print(f"Consumer got: {item}")
    q.task_done()

t = threading.Thread(target=consumer)
t.start()

import time
time.sleep(2)         # Consumer is blocked for 2 seconds
q.put("hello")        # Consumer unblocks and gets "hello"

t.join()
```

```
Output:
  Consumer waiting...
  (2 second pause)
  Consumer got: hello
```

This blocking behaviour eliminates the need for `while not queue.empty(): time.sleep(0.01)` busy-wait loops. The thread sleeps at the OS level and wakes only when data arrives.

### Non-Blocking and Timeout Variants

```python
import queue

q = queue.Queue()

# Non-blocking put — raises queue.Full immediately if full
try:
    q.put("item", block=False)
except queue.Full:
    print("Queue is full")

# Put with timeout — raises queue.Full after 3 seconds if still full
try:
    q.put("item", timeout=3)
except queue.Full:
    print("Timed out waiting to put")

# Non-blocking get — raises queue.Empty immediately if empty
try:
    item = q.get(block=False)
except queue.Empty:
    print("Nothing to get")

# Get with timeout — raises queue.Empty after 2 seconds
try:
    item = q.get(timeout=2)
except queue.Empty:
    print("Timed out waiting for item")
```

### `task_done()` and `.join()` — Tracking Completion

This is what makes `Queue` different from a raw deque for real work pipelines.

```python
import queue
import threading

q = queue.Queue()

def worker():
    while True:
        item = q.get()
        if item is None:        # Sentinel — signal to stop
            break
        print(f"Processing: {item}")
        q.task_done()           # Signal that this item is fully processed

# Start 3 worker threads
threads = [threading.Thread(target=worker) for _ in range(3)]
for t in threads:
    t.start()

# Add work
for task in ["A", "B", "C", "D", "E"]:
    q.put(task)

q.join()    # BLOCKS until every put() item has had task_done() called

# Send stop signals to workers
for _ in threads:
    q.put(None)
for t in threads:
    t.join()

print("All work complete.")
```

```
How task_done() / join() works internally:

  put("A")  → internal counter: 1
  put("B")  → internal counter: 2
  put("C")  → internal counter: 3

  get() + task_done()  → counter: 2
  get() + task_done()  → counter: 1
  get() + task_done()  → counter: 0  ← q.join() unblocks here
```

> **Rule:** Every `put()` must be matched with exactly one `task_done()` call. Forgetting `task_done()` causes `q.join()` to block forever.

## `queue.LifoQueue` — LIFO (Stack) Queue

### What It Does

`LifoQueue` gives you a **thread-safe stack**. The last item added is the first item returned. It is literally a stack wrapped in thread-safety locks.

### Creating and Basic Usage

```python
import queue

lq = queue.LifoQueue()
lq = queue.LifoQueue(maxsize=5)    # Bounded variant

lq.put(10)
lq.put(20)
lq.put(30)

print(lq.get())    # 30 — most recently added
print(lq.get())    # 20
print(lq.get())    # 10
```

### ASCII Trace — LIFO Ordering

```
After put(10), put(20), put(30):

    TOP (most recent)
      │
      ▼
  ┌───────┐
  │  30   │  ← get() returns this first
  ├───────┤
  │  20   │
  ├───────┤
  │  10   │  ← put() first, get() last
  └───────┘
    BOTTOM

Step-by-step:

  put(10):   [ 10 ]
  put(20):   [ 10, 20 ]
  put(30):   [ 10, 20, 30 ]
  get() → 30:  [ 10, 20 ]
  get() → 20:  [ 10 ]
  get() → 10:  [ ]
```

### LifoQueue vs deque as a Stack

```python
# LifoQueue — thread-safe, blocks on get() when empty
import queue
lq = queue.LifoQueue()
lq.put(1)
lq.put(2)
print(lq.get())    # 2

# deque as stack — NOT thread-safe, raises IndexError when empty
from collections import deque
dq = deque()
dq.append(1)
dq.append(2)
print(dq.pop())    # 2
```

Use `LifoQueue` when multiple threads share a stack. Use `deque` when you're working in a single thread and need maximum speed.

### Real-World Use: Thread-Safe Undo System

```python
import queue
import threading

undo_stack = queue.LifoQueue()

def perform_action(action):
    print(f"Doing: {action}")
    undo_stack.put(action)

def undo():
    if not undo_stack.empty():
        action = undo_stack.get()
        print(f"Undoing: {action}")
        undo_stack.task_done()

perform_action("Type 'Hello'")
perform_action("Bold text")
perform_action("Insert image")

undo()    # Undoing: Insert image
undo()    # Undoing: Bold text
undo()    # Undoing: Type 'Hello'
```

## `queue.PriorityQueue` — Priority-Ordered Queue

### What It Does

`PriorityQueue` always returns the **smallest item** first, regardless of insertion order. Internally it uses a **min-heap** (same as `heapq`), but wrapped in thread-safety locks.

### Creating and Basic Usage

```python
import queue

pq = queue.PriorityQueue()

pq.put(50)    # Priority 50 — low urgency
pq.put(10)    # Priority 10 — high urgency
pq.put(30)    # Priority 30 — medium urgency

print(pq.get())    # 10 — smallest value, highest priority
print(pq.get())    # 30
print(pq.get())    # 50
```

### ASCII Trace — Priority Ordering

```
After put(50), put(10), put(30):

Internal min-heap structure:

         10          ← always at the top (smallest)
        /  \
       50    30

get() → 10    (heap reorganises after removal)

         30
        /
       50

get() → 30

         50

get() → 50
```

The heap ensures every `get()` finds the minimum in **O(log n)** time, and every `put()` inserts in **O(log n)** time.

### Using Tuples for Priority + Data

Since `PriorityQueue` orders by the smallest item, the standard pattern is to use **(priority, data)** tuples:

```python
import queue

pq = queue.PriorityQueue()

pq.put((3, "Low priority task"))
pq.put((1, "URGENT: server is down"))
pq.put((2, "Medium: deploy update"))

while not pq.empty():
    priority, task = pq.get()
    print(f"[Priority {priority}] {task}")
```

```
Output:
  [Priority 1] URGENT: server is down
  [Priority 2] Medium: deploy update
  [Priority 3] Low priority task
```

### Priority With Custom Objects

If you use custom objects, Python compares tuples element by element. If two tasks have the same priority number, Python tries to compare the data objects — which may fail if they don't support `<`. The safe solution is to add a **tiebreaker counter**:

```python
import queue
import itertools

pq = queue.PriorityQueue()
counter = itertools.count()    # Unique sequence number — never equal

class Task:
    def __init__(self, name, priority):
        self.name = name
        self.priority = priority

def enqueue_task(task):
    seq = next(counter)           # Unique tiebreaker
    pq.put((task.priority, seq, task))    # (priority, seq, data)

enqueue_task(Task("Deploy DB migration", priority=1))
enqueue_task(Task("Send alert email",    priority=1))   # Same priority — tiebreaker decides order
enqueue_task(Task("Generate report",     priority=3))

while not pq.empty():
    priority, seq, task = pq.get()
    print(f"[P{priority}] {task.name}")
```

```
Output:
  [P1] Deploy DB migration   ← arrived first (seq=0) — tiebreaker keeps FIFO within same priority
  [P1] Send alert email      ← arrived second (seq=1)
  [P3] Generate report
```

### Step-by-Step Trace — Heap Insertions

```
Start: empty heap []

put((3, "Low")):
  Heap: [(3, "Low")]

put((1, "URGENT")):
  Insert at end: [(3, "Low"), (1, "URGENT")]
  Bubble up:     [(1, "URGENT"), (3, "Low")]    ← 1 < 3, swap
                   ↑
              now at root (smallest)

put((2, "Medium")):
  Insert at end: [(1, "URGENT"), (3, "Low"), (2, "Medium")]
  Bubble up:     (2 > 1, no swap needed — already in place)

get() → (1, "URGENT"):
  Remove root.
  Move last to root: [(2, "Medium"), (3, "Low")]
  Sift down:         2 < 3, no swap needed.

get() → (2, "Medium"):
  Remove root.
  Heap: [(3, "Low")]

get() → (3, "Low"):
  Remove root.
  Heap: []
```

## All Three Classes — Side-by-Side Comparison

```python
import queue

# FIFO — order preserved
q = queue.Queue()
for item in [10, 20, 30]:
    q.put(item)
print("Queue (FIFO):", [q.get() for _ in range(3)])
# → [10, 20, 30]

# LIFO — reversed order
lq = queue.LifoQueue()
for item in [10, 20, 30]:
    lq.put(item)
print("LifoQueue (LIFO):", [lq.get() for _ in range(3)])
# → [30, 20, 10]

# Priority — sorted by value
pq = queue.PriorityQueue()
for item in [30, 10, 20]:
    pq.put(item)
print("PriorityQueue:", [pq.get() for _ in range(3)])
# → [10, 20, 30]
```

```
Visual Summary:

  Input order:   10 → 20 → 30

  Queue:         get() → 10, 20, 30     (same order)
  LifoQueue:     get() → 30, 20, 10     (reversed)
  PriorityQueue: get() → smallest first (sorted ascending)
```

## The Complete Interface — All Methods

All three classes share the same API:

```python
import queue

q = queue.Queue(maxsize=0)    # maxsize=0 means unlimited

# Adding items
q.put(item)                         # Add item; blocks if full
q.put(item, block=False)            # Raises queue.Full immediately if full
q.put(item, timeout=3)              # Raises queue.Full after 3 seconds
q.put_nowait(item)                  # Shorthand for put(item, block=False)

# Removing items
item = q.get()                      # Remove item; blocks if empty
item = q.get(block=False)           # Raises queue.Empty immediately if empty
item = q.get(timeout=2)             # Raises queue.Empty after 2 seconds
item = q.get_nowait()               # Shorthand for get(block=False)

# Checking state
q.empty()                           # True if no items (unreliable in threads)
q.full()                            # True if at maxsize (unreliable in threads)
q.qsize()                           # Approximate item count (unreliable in threads)

# Work tracking
q.task_done()                       # Signal one item fully processed
q.join()                            # Block until all put() items have task_done()
```

> **Warning on `empty()`, `full()`, `qsize()`:** In a multi-threaded context, these can be stale by the time you act on them. Between checking `empty()` and calling `get()`, another thread may have consumed the last item. Always use `get(timeout=...)` with `except queue.Empty` instead of `if not q.empty(): q.get()`.

## Complete Runnable Programs

### Program 1 — Producer-Consumer with `Queue`

```python
import queue
import threading
import time
import random

def producer(q, num_items):
    for i in range(1, num_items + 1):
        item = f"Task-{i}"
        q.put(item)
        print(f"[Producer] Added {item}  | Queue size: {q.qsize()}")
        time.sleep(random.uniform(0.1, 0.3))
    # Send sentinel values to stop each consumer
    for _ in range(3):
        q.put(None)

def consumer(q, name):
    while True:
        item = q.get()
        if item is None:
            print(f"[{name}] Received stop signal. Exiting.")
            q.task_done()
            break
        print(f"[{name}] Processing {item}")
        time.sleep(random.uniform(0.2, 0.5))    # Simulate work
        q.task_done()
        print(f"[{name}] Done with {item}")

def main():
    task_queue = queue.Queue(maxsize=5)

    prod = threading.Thread(target=producer, args=(task_queue, 8))
    consumers = [
        threading.Thread(target=consumer, args=(task_queue, f"Worker-{i}"))
        for i in range(1, 4)
    ]

    for c in consumers:
        c.start()
    prod.start()

    prod.join()
    task_queue.join()    # Wait until all tasks are processed

    for c in consumers:
        c.join()

    print("\nAll tasks complete.")

if __name__ == "__main__":
    main()
```

```
Sample output (thread order varies):

  [Producer] Added Task-1  | Queue size: 1
  [Worker-1] Processing Task-1
  [Producer] Added Task-2  | Queue size: 1
  [Worker-2] Processing Task-2
  [Worker-1] Done with Task-1
  [Producer] Added Task-3  | Queue size: 1
  ...
  All tasks complete.
```

### Program 2 — Priority Task Scheduler with `PriorityQueue`

```python
import queue
import threading
import itertools
import time

counter = itertools.count()

class Job:
    def __init__(self, name, priority):
        self.name = name
        self.priority = priority

    def __repr__(self):
        return f"Job({self.name!r}, priority={self.priority})"

def scheduler(pq):
    print("Scheduler started. Waiting for jobs...")
    while True:
        try:
            priority, seq, job = pq.get(timeout=3)
        except queue.Empty:
            print("No more jobs. Scheduler shutting down.")
            break
        print(f"Running [{priority}] {job.name}")
        time.sleep(0.2)    # Simulate execution
        pq.task_done()

def submit_job(pq, job):
    seq = next(counter)
    pq.put((job.priority, seq, job))
    print(f"Submitted: [{job.priority}] {job.name}")

def main():
    pq = queue.PriorityQueue()

    scheduler_thread = threading.Thread(target=scheduler, args=(pq,))
    scheduler_thread.start()

    time.sleep(0.1)    # Let scheduler start

    submit_job(pq, Job("Send weekly digest",   priority=3))
    submit_job(pq, Job("CRITICAL: DB backup",  priority=1))
    submit_job(pq, Job("Deploy hotfix",        priority=1))
    submit_job(pq, Job("Generate reports",     priority=2))
    submit_job(pq, Job("Clean temp files",     priority=5))

    scheduler_thread.join()
    print("\nAll jobs executed.")

if __name__ == "__main__":
    main()
```

### Program 3 — Thread-Safe Undo/Redo with `LifoQueue`

```python
import queue
import threading

class Editor:
    def __init__(self):
        self.content = ""
        self.undo_stack = queue.LifoQueue()
        self.lock = threading.Lock()

    def type_text(self, text):
        with self.lock:
            self.undo_stack.put(("type", text))
            self.content += text
            print(f"Typed: {text!r}  | Content: {self.content!r}")

    def delete_last(self, n):
        with self.lock:
            deleted = self.content[-n:]
            self.undo_stack.put(("delete", deleted))
            self.content = self.content[:-n]
            print(f"Deleted {n} chars   | Content: {self.content!r}")

    def undo(self):
        if self.undo_stack.empty():
            print("Nothing to undo.")
            return
        action, data = self.undo_stack.get()
        with self.lock:
            if action == "type":
                self.content = self.content[: -len(data)]
            elif action == "delete":
                self.content += data
        print(f"Undid {action!r}: {data!r} | Content: {self.content!r}")
        self.undo_stack.task_done()

def main():
    ed = Editor()
    ed.type_text("Hello")
    ed.type_text(", World")
    ed.delete_last(6)     # Deletes ", World"
    ed.type_text("!")
    print("---")
    ed.undo()    # Undo type "!"
    ed.undo()    # Undo delete
    ed.undo()    # Undo type ", World"
    ed.undo()    # Undo type "Hello"
    ed.undo()    # Nothing to undo

if __name__ == "__main__":
    main()
```

```
Output:

  Typed: 'Hello'          | Content: 'Hello'
  Typed: ', World'        | Content: 'Hello, World'
  Deleted 6 chars         | Content: 'Hello'
  Typed: '!'              | Content: 'Hello!'
  ---
  Undid 'type': '!'       | Content: 'Hello'
  Undid 'delete': ', World' | Content: 'Hello, World'
  Undid 'type': ', World' | Content: 'Hello'
  Undid 'type': 'Hello'   | Content: ''
  Nothing to undo.
```

## Common Mistakes and How to Avoid Them

### Mistake 1 — Using `queue.empty()` as a Guard Before `queue.get()`

```python
# Wrong — race condition: another thread may consume the item between
#         the empty() check and the get() call
if not q.empty():
    item = q.get()    # May raise queue.Empty if another thread just got it

# Correct — use get() with timeout or block=False and catch the exception
try:
    item = q.get(timeout=1)
except queue.Empty:
    item = None    # Handle empty queue here
```

`empty()`, `full()`, and `qsize()` are inherently unreliable in multi-threaded code. They reflect the queue state at one moment — which can change before you act on it. Always use `get()` with exception handling.

---

### Mistake 2 — Forgetting `task_done()` When Using `join()`

```python
import queue

q = queue.Queue()
q.put("work")

item = q.get()
print(f"Got: {item}")
# q.task_done()  ← MISSING

q.join()    # HANGS FOREVER — internal counter never reaches zero
```

```python
# Correct
item = q.get()
print(f"Got: {item}")
q.task_done()    # Must be called exactly once per get()
q.join()         # Now unblocks correctly
```

Every `put()` increments an internal counter. Every `task_done()` decrements it. `join()` blocks until that counter reaches zero. One missing `task_done()` means `join()` waits forever.

### Mistake 3 — Comparing `queue.Queue` with `collections.deque` for Thread Safety

```python
# Wrong — deque is NOT thread-safe
from collections import deque
import threading

shared = deque()

def worker():
    for i in range(1000):
        shared.append(i)         # Race condition — two threads appending simultaneously
        if shared:
            shared.popleft()     # May crash or corrupt data

threads = [threading.Thread(target=worker) for _ in range(5)]
for t in threads:
    t.start()
for t in threads:
    t.join()
```

```python
# Correct — use queue.Queue for shared, multi-threaded access
import queue
import threading

shared = queue.Queue()

def worker():
    for i in range(1000):
        shared.put(i)
        try:
            shared.get_nowait()
        except queue.Empty:
            pass

threads = [threading.Thread(target=worker) for _ in range(5)]
for t in threads:
    t.start()
for t in threads:
    t.join()
```

### Mistake 4 — Putting Non-Comparable Objects Into `PriorityQueue` Without a Tiebreaker

```python
import queue

pq = queue.PriorityQueue()

pq.put((1, {"name": "Task A"}))   # Priority 1
pq.put((1, {"name": "Task B"}))   # Priority 1 — SAME PRIORITY

pq.get()
pq.get()    # TypeError: '<' not supported between instances of 'dict' and 'dict'
```

When two items have the same priority, Python tries to compare the data itself. Dicts, objects, and most custom types don't support `<`. The fix is a unique tiebreaker:

```python
import queue
import itertools

pq = queue.PriorityQueue()
counter = itertools.count()

pq.put((1, next(counter), {"name": "Task A"}))    # (priority, seq, data)
pq.put((1, next(counter), {"name": "Task B"}))    # Same priority — seq breaks the tie

priority, seq, data = pq.get()
print(data)    # {'name': 'Task A'} — seq=0 wins over seq=1
```

### Mistake 5 — Using `queue.Queue` in `asyncio` Code

```python
# Wrong — queue.Queue.get() BLOCKS the thread, which freezes the asyncio event loop
import asyncio
import queue

q = queue.Queue()

async def consumer():
    item = q.get()    # This blocks the ENTIRE event loop — no other coroutines run
    print(item)
```

```python
# Correct — use asyncio.Queue for async code
import asyncio

async def producer(q):
    await q.put("hello")

async def consumer(q):
    item = await q.get()    # Yields control — other coroutines can run
    print(item)

async def main():
    q = asyncio.Queue()
    await asyncio.gather(producer(q), consumer(q))

asyncio.run(main())
```

The rule: **`queue.Queue` is for `threading`; `asyncio.Queue` is for `asyncio`.** Mixing them defeats the purpose of both.

### Mistake 6 — Treating `maxsize=0` as Zero Capacity

```python
import queue

q = queue.Queue(maxsize=0)    # NOT a zero-capacity queue!
q.put(1)
q.put(2)
q.put(3)
print(q.qsize())    # 3 — it accepted everything
```

`maxsize=0` (the default) means **unlimited capacity**. To block producers when the queue reaches a certain size, use `maxsize=N` where `N > 0`:

```python
q = queue.Queue(maxsize=5)    # Blocks put() when 5 items are already inside
```

## The Complete `queue` Module Reference

```python
import queue

# --- Queue (FIFO) ---
q = queue.Queue(maxsize=0)     # maxsize=0: unlimited
q.put(item)                    # Add; blocks if full
q.put(item, block=False)       # Raises queue.Full immediately if full
q.put(item, timeout=n)         # Raises queue.Full after n seconds
q.put_nowait(item)             # Same as put(block=False)

item = q.get()                 # Remove; blocks if empty
item = q.get(block=False)      # Raises queue.Empty immediately
item = q.get(timeout=n)        # Raises queue.Empty after n seconds
item = q.get_nowait()          # Same as get(block=False)

q.task_done()                  # Signal one item fully processed
q.join()                       # Block until all task_done() calls received

q.empty()                      # True if no items (unreliable in threads)
q.full()                       # True if at maxsize (unreliable in threads)
q.qsize()                      # Approximate count (unreliable in threads)

# --- LifoQueue (LIFO / Stack) ---
lq = queue.LifoQueue(maxsize=0)
# Same interface as Queue — get() returns newest item first

# --- PriorityQueue (Min-heap) ---
pq = queue.PriorityQueue(maxsize=0)
# Same interface as Queue — get() returns smallest item first
# Use (priority, tiebreaker, data) tuples to avoid comparison errors

# --- Exceptions ---
queue.Empty    # Raised by get(block=False) or get(timeout=...) when empty
queue.Full     # Raised by put(block=False) or put(timeout=...) when full
```

## Summary

| Concept | What It Means |
|---|---|
| `queue.Queue` | FIFO — items come out in order they went in |
| `queue.LifoQueue` | LIFO — last item in is first item out (stack) |
| `queue.PriorityQueue` | Min-heap — smallest item always comes out first |
| Thread-safe | All three have built-in locks — safe for multiple threads |
| `put()` | Add item; blocks if queue is full (when `maxsize > 0`) |
| `get()` | Remove item; blocks if queue is empty — no busy-waiting |
| `task_done()` | Signal one unit of work is complete |
| `join()` | Block until every `put()` has a matching `task_done()` |
| `queue.Empty` | Exception from `get(block=False)` or `get(timeout=n)` |
| `queue.Full` | Exception from `put(block=False)` or `put(timeout=n)` |
| `empty()` / `qsize()` | Unreliable in threads — use `get()` with exception handling |
| vs `collections.deque` | `deque` = speed for algorithms; `queue` = safety for threads |
| vs `asyncio.Queue` | `queue` = for `threading`; `asyncio.Queue` = for `async/await` |
| `(priority, seq, data)` tuple | The standard `PriorityQueue` pattern — avoids comparison errors |

The `queue` module is where data structures meet concurrency. A `deque` lets you build a fast queue; a `Queue` lets you build a *safe* one. Once you understand the difference between FIFO ordering, LIFO ordering, and priority ordering — and once you feel what blocking `get()` eliminates — you will reach for `queue.Queue` instinctively every time you write code that involves threads processing shared work.

A `deque` is a conveyor belt. A `queue.Queue` is that same belt with a safety guard, an emergency stop, and a supervisor keeping track of every item that was loaded.
