# AVL Tree — Self-Balancing BST with Rotations in Python

---

## 1. Introduction

You learned that a BST inserted with sorted data `[10, 20, 30, 40, 50]` becomes a straight line — a degenerate tree with height n−1. Every operation degrades from O(log n) to O(n). The BST's greatest strength collapses into its worst weakness.

In 1962, two Soviet mathematicians — **Adelson-Velsky** and **Landis** — published a solution. They asked a single question:

> *What if every time the tree became unbalanced, it fixed itself automatically?*

The result was the **AVL Tree** — the world's first self-balancing binary search tree. Named after its inventors, it remains one of the most elegant algorithms in computer science.

An AVL Tree is a BST with one additional guarantee:

> **At every single node, the height of the left subtree and the height of the right subtree differ by at most 1.**

This guarantee is called the **AVL Property**. When it is violated, the tree performs a **rotation** — a local restructuring that restores balance without breaking the BST ordering.

---

## 2. Real-World Applications

**Database Indexes (MySQL, PostgreSQL)**
Every time you run `SELECT * FROM orders WHERE id = 12345`, the database engine navigates a B-Tree (a generalised AVL Tree). Without balancing, every insert of a new order could degrade search performance. AVL-style balancing keeps queries at O(log n) regardless of insertion order.

**Java's `TreeMap` and `TreeSet`**
These use a Red-Black Tree (a close cousin of the AVL Tree) to guarantee O(log n) for put, get, and remove. Your Android app, your Spring Boot backend, your Minecraft plugin — all use AVL-style self-balancing.

**Memory Allocators**
The Linux kernel's CFS (Completely Fair Scheduler) stores runnable processes in a Red-Black Tree sorted by their virtual runtime. Adding and removing a process (millions of times per second) must stay O(log n). Balancing makes that possible.

**In-Memory Caches**
LRU caches often combine a hash map with a balanced BST to support O(log n) expiry operations sorted by access time.

## 3. Key Terminology

| Term | Meaning |
|------|---------|
| **Balance Factor** | `height(left) − height(right)` at a given node. Valid values: −1, 0, +1 |
| **Unbalanced Node** | A node where `|balance_factor| > 1` |
| **Rotation** | A local pointer restructuring that lowers the height of a subtree while preserving BST order |
| **Left Rotation** | Pivots a node downward-left; used when the right subtree is too tall |
| **Right Rotation** | Pivots a node downward-right; used when the left subtree is too tall |
| **Left-Right (LR) Rotation** | A left rotation on the child, then a right rotation on the parent |
| **Right-Left (RL) Rotation** | A right rotation on the child, then a left rotation on the parent |
| **Height (AVL)** | Stored in each node for O(1) lookup; updated on every insert |

---

## 4. The Balance Factor in Detail

Every AVL node stores its **height** (not depth — height is measured from below). The balance factor is computed from the children's heights.

```
balance_factor(node) = height(node.left) − height(node.right)
```

By convention:
- `height(None)` = −1 (empty subtree)
- A **leaf node** has height 0 (both children are None, so 1 + max(−1, −1) = 0)

```
         [50]   height=2, BF = height([30]) − height([70]) = 1 − 0 = 1  
        /    \
      [30]  [70]  [30]: BF = 0 − (−1) = 1    [70]: BF = −1 − (−1) = 0 
      /
    [20]    [20]: BF = (−1) − (−1) = 0 
```

Balance factors of **−1, 0, +1** are all valid. Any node reaching **−2 or +2** triggers a rotation.

## 5. The Four Rotation Cases

There are four ways a subtree can become unbalanced. Each has exactly one rotation fix.

The **shape** of the imbalance determines which rotation to apply.

```
Case 1 (LL): Left-heavy, and the left child is left-heavy  → Right Rotation
Case 2 (RR): Right-heavy, and the right child is right-heavy → Left Rotation
Case 3 (LR): Left-heavy, and the left child is right-heavy  → Left Rotate child, then Right Rotate node
Case 4 (RL): Right-heavy, and the right child is left-heavy → Right Rotate child, then Left Rotate node
```

---

### Case 1: LL Imbalance → Right Rotation

**When it occurs:** You insert into the left subtree of the left child, making the node left-heavy with BF = +2.

```
Before:           After Right Rotation on [30]:

    [30]  BF=+2         [20]
    /                  /    \
  [20]  BF=+1        [10]  [30]
  /
[10]
```

**The mechanic:** The left child `[20]` rises to take the unbalanced node's `[30]` position. The unbalanced node becomes the right child of the new root. Any right subtree of `[20]` becomes the left child of `[30]` (it is between them in BST order, so it still fits).

```python
def _rotate_right(self, z):
    y     = z.left          # y is the new root of this subtree
    T3    = y.right         # T3 will move to z's left

    # Perform rotation
    y.right = z             # z drops down to become y's right child
    z.left  = T3            # T3 moves to z's left (BST order preserved)

    # Update heights — z first (it is now lower), then y
    z.height = 1 + max(self._get_height(z.left),
                       self._get_height(z.right))
    y.height = 1 + max(self._get_height(y.left),
                       self._get_height(y.right))

    return y                # y is the new root of this subtree
```

---

### Case 2: RR Imbalance → Left Rotation

**When it occurs:** You insert into the right subtree of the right child, making the node right-heavy with BF = −2.

```
Before:           After Left Rotation on [10]:

[10]  BF=−2               [20]
   \                      /    \
  [20]  BF=−1           [10]  [30]
      \
      [30]
```

**The mechanic:** The mirror image of the right rotation. The right child rises; the unbalanced node drops to the left.

```python
def _rotate_left(self, z):
    y     = z.right         # y is the new root of this subtree
    T2    = y.left          # T2 will move to z's right

    # Perform rotation
    y.left  = z             # z drops down to become y's left child
    z.right = T2            # T2 moves to z's right (BST order preserved)

    # Update heights — z first, then y
    z.height = 1 + max(self._get_height(z.left),
                       self._get_height(z.right))
    y.height = 1 + max(self._get_height(y.left),
                       self._get_height(y.right))

    return y                # y is the new root of this subtree
```

---

### Case 3: LR Imbalance → Left-Right Rotation

**When it occurs:** The node is left-heavy (BF = +2), but the left child is right-heavy (BF = −1). A single right rotation would not fix it because the problematic node is in a "bent" shape.

```
Before:              After Left Rotate [20]:     After Right Rotate [30]:

    [30]  BF=+2            [30]  BF=+2                [25]
    /                      /                          /    \
  [20]  BF=−1           [25]  BF=+1                [20]  [30]
     \                  /
     [25]            [20]
```

**Two-step fix:** First rotate the left child left (straighten the bend), then rotate the node right (standard LL fix).

```python
# In the insert rebalancing logic:
# if BF > 1 and data > node.left.data:   ← LR case
node.left = self._rotate_left(node.left)
return self._rotate_right(node)
```

---

### Case 4: RL Imbalance → Right-Left Rotation

**When it occurs:** The node is right-heavy (BF = −2), but the right child is left-heavy (BF = +1). The mirror of LR.

```
Before:              After Right Rotate [30]:    After Left Rotate [10]:

[10]  BF=−2               [10]  BF=−2                [20]
   \                          \                       /    \
  [30]  BF=+1               [20]  BF=−1            [10]  [30]
  /                              \
[20]                             [30]
```

**Two-step fix:** First rotate the right child right (straighten the bend), then rotate the node left (standard RR fix).

```python
# if BF < -1 and data < node.right.data:   ← RL case
node.right = self._rotate_right(node.right)
return self._rotate_left(node)
```

## 6. The Four Cases — Side-by-Side Reference

```
Imbalance    BF at Node    BF at Child    Fix
──────────────────────────────────────────────────────────
LL           +2            +1 or 0        Right Rotate(node)
RR           -2            -1 or 0        Left Rotate(node)
LR           +2            -1             Left Rotate(child), Right Rotate(node)
RL           -2            +1             Right Rotate(child), Left Rotate(node)
```

Memory trick: **The name describes the shape of the imbalance, not the fix.**
- **LL** = Left-Left problem → fix with a Right rotation (push the tall side down)
- **RR** = Right-Right problem → fix with a Left rotation
- **LR** = Left-Right zigzag → straighten first, then fix
- **RL** = Right-Left zigzag → straighten first, then fix

## 7. The AVL Node Class

The AVL Node stores one extra field compared to a plain BST node: **height**. This allows balance factor computation in O(1) instead of O(n).

```python
class AVLNode:
    def __init__(self, data):
        self.data   = data
        self.left   = None
        self.right  = None
        self.height = 0     # New leaf always starts at height 0
```

## 8. Complete AVL Tree Implementation

```python
class AVLNode:
    def __init__(self, data):
        self.data   = data
        self.left   = None
        self.right  = None
        self.height = 0

    def __repr__(self):
        return f"AVLNode({self.data}, h={self.height})"


class AVLTree:
    def __init__(self):
        self.root = None

    # ── Height Helper ────────────────────────────────────────
    def _get_height(self, node):
        """Returns stored height; -1 for None (empty subtree)."""
        return node.height if node else -1

    # ── Balance Factor Helper ────────────────────────────────
    def _get_balance(self, node):
        """Returns left_height - right_height."""
        if node is None:
            return 0
        return self._get_height(node.left) - self._get_height(node.right)

    # ── Update Height Helper ─────────────────────────────────
    def _update_height(self, node):
        """Recalculates and stores height from children."""
        node.height = 1 + max(self._get_height(node.left),
                               self._get_height(node.right))

    # ── Rotations ────────────────────────────────────────────
    def _rotate_right(self, z):
        """
        Right rotation around z.

             z                 y
            / \               / \
           y   T4    →      T1   z
          / \                   / \
        T1   T3               T3   T4
        """
        y  = z.left
        T3 = y.right

        y.right = z
        z.left  = T3

        self._update_height(z)   # z is now lower — update first
        self._update_height(y)   # y is now higher — update second

        return y                 # new subtree root

    def _rotate_left(self, z):
        """
        Left rotation around z.

          z                    y
         / \                  / \
        T1   y       →       z   T4
            / \             / \
           T2  T4          T1  T2
        """
        y  = z.right
        T2 = y.left

        y.left  = z
        z.right = T2

        self._update_height(z)
        self._update_height(y)

        return y

    # ── Insertion ────────────────────────────────────────────
    def insert(self, data):
        self.root = self._insert_recursive(self.root, data)

    def _insert_recursive(self, node, data):
        # ── Step 1: Standard BST insertion ──────────────────
        if node is None:
            return AVLNode(data)

        if data < node.data:
            node.left  = self._insert_recursive(node.left,  data)
        elif data > node.data:
            node.right = self._insert_recursive(node.right, data)
        else:
            return node    # Duplicates ignored

        # ── Step 2: Update height of current node ───────────
        self._update_height(node)

        # ── Step 3: Get balance factor ───────────────────────
        balance = self._get_balance(node)

        # ── Step 4: Rebalance if needed ──────────────────────

        # Case 1 — LL: Left-Left
        if balance > 1 and data < node.left.data:
            return self._rotate_right(node)

        # Case 2 — RR: Right-Right
        if balance < -1 and data > node.right.data:
            return self._rotate_left(node)

        # Case 3 — LR: Left-Right
        if balance > 1 and data > node.left.data:
            node.left = self._rotate_left(node.left)
            return self._rotate_right(node)

        # Case 4 — RL: Right-Left
        if balance < -1 and data < node.right.data:
            node.right = self._rotate_right(node.right)
            return self._rotate_left(node)

        return node    # Already balanced — return unchanged

    # ── Search ───────────────────────────────────────────────
    def search(self, data):
        return self._search(self.root, data)

    def _search(self, node, data):
        if node is None:
            return False
        if data == node.data:
            return True
        elif data < node.data:
            return self._search(node.left, data)
        else:
            return self._search(node.right, data)

    # ── Height and Balance ───────────────────────────────────
    def height(self):
        return self._get_height(self.root)

    def balance_factor_root(self):
        return self._get_balance(self.root)

    # ── Inorder Traversal ────────────────────────────────────
    def inorder(self, node=None, _first=True):
        if _first:
            node = self.root
        if node is None:
            return
        self.inorder(node.left,  _first=False)
        print(node.data, end="  ")
        self.inorder(node.right, _first=False)

    # ── Level-Order with Heights (for debugging) ─────────────
    def print_tree_info(self, node=None, _first=True):
        """Prints each node with its balance factor — useful for debugging."""
        if _first:
            node = self.root
        if node is None:
            return
        bf = self._get_balance(node)
        print(f"  Node {node.data:>3}  height={node.height}  BF={bf:+d}")
        self.print_tree_info(node.left,  _first=False)
        self.print_tree_info(node.right, _first=False)
```

## 11. Time and Space Complexity

| Operation | AVL Tree | Plain BST (avg) | Plain BST (worst) |
|-----------|----------|-----------------|-------------------|
| **Insert** | O(log n) | O(log n) | O(n) |
| **Search** | O(log n) | O(log n) | O(n) |
| **Height** | O(1) — stored | O(n) | O(n) |
| **Rotation** | O(1) — local only | — | — |
| **Space** | O(n) + 1 int per node | O(n) | O(n) |

**Why is rotation O(1)?**
A rotation only reassigns a handful of pointers — at most 5 pointer changes regardless of how large the tree is. No nodes are moved in memory. It is one of the cheapest operations in all of computer science.

**Why is height O(1) in AVL?**
Every AVL node stores its own height. You read `node.height` directly — no traversal needed.

**The cost of self-balancing:**
AVL Trees guarantee O(log n) at all times, but each insert does up to 2 rotations (in practice, usually 0 or 1). There is a constant-factor overhead compared to a plain BST, which is why Red-Black Trees (slightly fewer rotations on insert) are preferred in write-heavy systems like Linux's scheduler.

## 12. Why Rotations Preserve BST Order

This is the crucial insight. A rotation physically moves nodes but **never violates the BST property**.

```
Right Rotation of z:

      z                 y
     / \               / \
    y   T4    →      T1   z
   / \                   / \
  T1  T3               T3  T4
```

Before the rotation:
- All nodes in T1 < y < T3 < z < T4  (BST property)

After the rotation:
- T1 < y                 (T1 is still y's left subtree)
- y  < z                 (y is still less than z)
- T3 < z                 (T3, which was y's right and is between y and z, moves to z's left)
- z  < T4                (T4 is still z's right subtree)

The inorder sequence is **identical** before and after. The rotation is invisible to anyone reading the tree in sorted order — it only changes the shape, never the order.

## 13. Common Mistakes

**Mistake 1 — Updating heights in the wrong order**

```python
# Wrong: y's height is computed before z's is updated
self._update_height(y)   # y depends on z.height, but z hasn't been updated yet
self._update_height(z)

# Correct: update the lower node (z) first, then the higher node (y)
self._update_height(z)
self._update_height(y)
```

After a rotation, `z` is now *below* `y`. So `z`'s height must be recalculated first, since `y`'s height depends on it.

**Mistake 2 — Forgetting to return the new subtree root**

```python
# Wrong: the parent's pointer still points to z, which is now the wrong root
def _rotate_right(self, z):
    y = z.left
    ...
    # Missing: return y

# Correct
def _rotate_right(self, z):
    y = z.right
    ...
    return y    # Parent must now point to y
```

The recursive insert method does `node.left = self._insert_recursive(node.left, data)`. This re-links the parent to whatever `_insert_recursive` returns. If your rotation forgets to `return y`, the parent keeps pointing to the old (now lower) node.

**Mistake 3 — Checking balance before updating height**

```python
# Wrong: balance is checked on stale heights
balance = self._get_balance(node)   # node.height not yet updated
self._update_height(node)

# Correct: update height first, then check balance
self._update_height(node)
balance = self._get_balance(node)
```

**Mistake 4 — Confusing LL/RR with the rotation direction**

LL imbalance (left-heavy, left child is left-heavy) is fixed with a **Right** rotation. The names describe the problem, not the solution. When in doubt: push the tall side down.

**Mistake 5 — Applying a single rotation to an LR or RL case**

```
    [30]  BF=+2        Applying a single right rotation gives:
    /
  [10]  BF=−1              [10]   ← Wrong! Still unbalanced
      \                   /    \
      [20]              ???    [30]
                               /
                             [20]
```

LR and RL cases require two rotations because the imbalance is "bent". A single rotation straightens the problem into a different imbalance. The second rotation then fixes it.

## 14. AVL vs Plain BST — The Height Guarantee

For n nodes:

| Tree Type | Best Height | Worst Height |
|-----------|-------------|--------------|
| Plain BST | ⌊log₂ n⌋ | n − 1 |
| AVL Tree  | ⌊log₂ n⌋ | 1.44 × log₂ n |

The AVL worst case (1.44 × log₂ n) is a mathematical theorem. No AVL Tree of n nodes can ever exceed this height. For 1,000,000 nodes:

- Plain BST worst case: **999,999 steps** (sorted insertion)
- AVL Tree worst case: **29 steps** (1.44 × log₂(1,000,000) ≈ 29)

That guarantee — not average performance, but a hard upper bound — is what makes AVL Trees suitable for production systems.

```
 │      └── Looser balancing (height ≤ 2 × log n instead of 1.44).
 │          Fewer rotations on insert/delete.
 │          Used in: Java TreeMap, C++ std::map, Linux CFS scheduler.
 │
 ├──► B-Tree / B+ Tree
 │      └── Generalised balanced tree for disk storage.
 │          Each node holds many keys (not just 2 children).
 │          Used in: MySQL InnoDB, PostgreSQL, SQLite, NTFS, ext4.
 │
 └──► Treap / Skip List
        └── Randomised alternatives to AVL that achieve O(log n)
            expected without deterministic rotations.
            Used in: Redis sorted sets (skip list), Lua tables.
```

## 16. Summary

| Concept | Key Point |
|---------|-----------|
| **AVL Property** | At every node, `|height(left) − height(right)| ≤ 1` |
| **Balance Factor** | `height(left) − height(right)`; valid range −1 to +1 |
| **Trigger** | Any insert that makes `|BF| = 2` at any ancestor |
| **LL Case** | BF = +2, left child BF = +1 → Right Rotate |
| **RR Case** | BF = −2, right child BF = −1 → Left Rotate |
| **LR Case** | BF = +2, left child BF = −1 → Left Rotate child, Right Rotate node |
| **RL Case** | BF = −2, right child BF = +1 → Right Rotate child, Left Rotate node |
| **Rotation cost** | O(1) — only pointer reassignments |
| **Height update order** | Always update the lower node (z) before the higher node (y) |
| **Return value** | Rotations must `return y` so the parent reconnects correctly |
| **Height guarantee** | At most 1.44 × log₂(n) — a hard mathematical bound |
| **vs Plain BST** | Guaranteed O(log n); plain BST degrades to O(n) on sorted input |

The rotation is not magic — it is geometry. A tree that leans too far one way can be straightened by pivoting one node up and one node down. The BST order is preserved because the *relative* position of every subtree remains valid. Rotation changes the shape without changing the meaning.

Once you can visualise a rotation as simply *lifting one node and lowering another*, AVL Trees stop being intimidating and start being elegant.
