# Collision Resolution — Chaining Using Lists

---

## Before We Begin — What Problem Are We Even Solving?

Imagine you move into a new apartment building. The building has 7 mailboxes in the lobby, numbered 0 through 6. Every resident is assigned a mailbox based on their apartment number.

Now imagine two residents — Alice (Apt 201) and Bob (Apt 801) — both get assigned to **mailbox 1** because of how the assignment formula works.

What do you do?

**Option A:** Tell Bob he can't have a mailbox. *(Terrible — data loss.)*

**Option B:** Find Bob a different, empty mailbox. *(Works, but complicated to track.)*

**Option C:** Put a small folder inside mailbox 1 that holds multiple letters. Alice's mail goes in the folder. Bob's mail goes in the same folder. Anyone looking for mail just checks the folder. *(Simple, flexible, works.)*

**Option C is Chaining.**

This is exactly what happens inside a hash table when two keys hash to the same index. Instead of panicking or finding another slot, we simply attach a linked list to that slot and let all colliding entries live there together.

---

## A Quick Refresher — What Is a Hash Table?

A **hash table** is a data structure that lets you store and retrieve values by key — like a super-fast dictionary.

```python
# This is a dictionary (hash table under the hood):
phone_book = {}
phone_book["Alice"] = "555-1234"
phone_book["Bob"]   = "555-5678"

print(phone_book["Alice"])   # Output: 555-1234
```

Internally, when you write `phone_book["Alice"]`, Python:

1. Runs `"Alice"` through a **hash function** → gets a number, say `52374`
2. Computes `52374 % table_size` → gets an index, say `3`
3. Stores `"555-1234"` at index `3` of an internal array

```
Internal Array:
┌───┬────────────┐
│ 0 │   None     │
│ 1 │   None     │
│ 2 │   None     │
│ 3 │ "555-1234" │   ← "Alice" hashed here
│ 4 │   None     │
│ 5 │ "555-5678" │   ← "Bob" hashed here
│ 6 │   None     │
└───┴────────────┘
```

But what happens when **two different keys hash to the same index**? That's a **collision** — and it is not a bug. It is mathematically guaranteed to happen. You cannot avoid it, you can only **handle** it gracefully.

---

## What Is a Collision?

A **collision** occurs when two different keys produce the same array index after hashing.

```
hash("Alice") % 7  →  index 3
hash("Charlie") % 7  →  index 3   ← COLLISION!
```

Both "Alice" and "Charlie" want to live at index 3. The array only has one slot there.

**Why does this happen?**

Because a hash function maps a theoretically **unlimited** set of keys (any string, number, or object) into a **limited** array of slots (say, 7 or 100 or 1000). By the **Pigeonhole Principle** — if you have more pigeons than holes, some holes must hold more than one pigeon. Collisions aren't a failure. They're a reality to design around.

---

## The Solution — Chaining with a Linked List

Here's the insight: instead of storing a single value at each array index, store the **head of a linked list**.

If only one key hashes to an index → the list has one node.
If two keys collide at the same index → the list has two nodes.
If ten keys collide → the list has ten nodes.

The array never fills up. Collisions just make the lists longer.

```
Hash Table with Chaining (size = 5):

Index 0:  → None

Index 1:  → [key="Alice", val="555-1234"] → [key="Charlie", val="555-9999"] → None
                ↑ first inserted               ↑ collision! added to chain

Index 2:  → [key="Bob", val="555-5678"] → None

Index 3:  → None

Index 4:  → [key="Dave", val="555-0001"] → [key="Eve", val="555-4321"] → [key="Frank", val="555-8888"] → None
```

Each chain is simply a linked list of Nodes. And you already know what a Node is:

```python
class Node:
    def __init__(self, key, value):
        self.key   = key     # The dictionary key  (e.g. "Alice")
        self.value = value   # The stored value    (e.g. "555-1234")
        self.next  = None    # Pointer to the next node in the chain

    def __repr__(self):
        return f"Node({self.key!r}: {self.value!r})"
```

This is the **exact same Node** from the previous topic — with one small upgrade: it stores a `key` alongside the `value`, because we need to identify which entry is which when we traverse the chain.

## Building the Hash Table — Step by Step

### Step 1 — The Empty Table

```python
class HashTableChaining:
    def __init__(self, size=7):
        self.size  = size
        self.table = [None] * self.size   # Array of None — no chains yet
```

Right now, the table looks like this:

```
table = [None, None, None, None, None, None, None]
          0     1     2     3     4     5     6
```

Every slot is `None` — meaning "this bucket has no chain yet."

---

### Step 2 — The Hash Function

```python
    def _hash(self, key):
        return hash(key) % self.size
```

`hash(key)` is Python's built-in hash — it turns any key into a large integer.
`% self.size` maps it into a valid array index (0 to size−1).

```python
ht = HashTableChaining(size=7)
print(ht._hash("Alice"))    # e.g. 3
print(ht._hash("Bob"))      # e.g. 5
print(ht._hash("Charlie"))  # e.g. 3  ← same as Alice: collision!
```

---

### Step 3 — Insertion

When inserting `(key, value)`:

1. Compute the index.
2. Create a new Node.
3. Prepend it to the chain at that index. *(Prepending is O(1) — no traversal needed.)*

```python
    def insert(self, key, value):
        index    = self._hash(key)           # Step 1: find the bucket
        new_node = Node(key, value)          # Step 2: create the node
        new_node.next  = self.table[index]   # Step 3a: new node points to existing chain
        self.table[index] = new_node         # Step 3b: new node becomes the new head
```

Let's trace what happens when we insert three entries, two of which collide:

```python
ht.insert("Alice",   "555-1234")   # hashes to index 3
ht.insert("Bob",     "555-5678")   # hashes to index 5
ht.insert("Charlie", "555-9999")   # hashes to index 3 → COLLISION
```

**After inserting "Alice":**
```
table[3] → [Alice: 555-1234] → None
```

**After inserting "Charlie":**
```
table[3] → [Charlie: 555-9999] → [Alice: 555-1234] → None
             ↑ new head, prepended in front
```

Charlie is prepended — the newest arrival sits at the front. Alice is still perfectly safe behind it.

---

### Step 4 — Search / Lookup

When searching for a key:

1. Compute the index.
2. Walk the chain at that index, node by node.
3. At each node, compare its `key` to the target.
4. Return the value if matched, or `None` if the end of the chain is reached.

```python
    def search(self, key):
        index   = self._hash(key)    # Go to the right bucket
        current = self.table[index]  # Start at the head of the chain

        while current is not None:
            if current.key == key:       # Found it!
                return current.value
            current = current.next       # Move to the next node

        return None                      # Key not in table
```

This is exactly the traversal from the Node topic — `while current is not None`, follow `.next`.

**Why do we check `current.key == key` and not just trust the index?**

Because *multiple keys can share the same index*. The index tells you *which bucket* to look in, but the key comparison tells you *which node* in that bucket is the one you want.

---

### Step 5 — Deletion

Deleting a node from a chain is standard linked list deletion:

1. Traverse the chain.
2. When you find the matching key, unlink its node by redirecting the previous node's `.next` pointer.

```python
    def delete(self, key):
        index = self._hash(key)
        prev    = None
        current = self.table[index]

        while current is not None:
            if current.key == key:
                if prev is None:
                    # Deleting the head of the chain
                    self.table[index] = current.next
                else:
                    # Bypassing the current node
                    prev.next = current.next
                return True          # Deletion successful
            prev    = current
            current = current.next

        return False                 # Key not found
```

```
Before deleting "Alice" from: [Charlie] → [Alice] → None

After deleting "Alice":        [Charlie] → None
                                    ↑ Charlie's .next now points to None
```

Notice: **no shifting of array elements**. No rebuilding. Just a pointer redirect. This is the same power the Node class gave us — O(1) unlinking.

## A Complete Working Example

Let's put it all together and watch the table evolve in real time.

```python
class Node:
    def __init__(self, key, value):
        self.key   = key
        self.value = value
        self.next  = None

    def __repr__(self):
        return f"({self.key!r}: {self.value!r})"


class HashTableChaining:
    def __init__(self, size=7):
        self.size  = size
        self.table = [None] * self.size

    def _hash(self, key):
        return hash(key) % self.size

    def insert(self, key, value):
        index          = self._hash(key)
        new_node       = Node(key, value)
        new_node.next  = self.table[index]
        self.table[index] = new_node

    def search(self, key):
        index   = self._hash(key)
        current = self.table[index]
        while current:
            if current.key == key:
                return current.value
            current = current.next
        return None

    def delete(self, key):
        index   = self._hash(key)
        prev    = None
        current = self.table[index]
        while current:
            if current.key == key:
                if prev is None:
                    self.table[index] = current.next
                else:
                    prev.next = current.next
                return True
            prev    = current
            current = current.next
        return False

    def display(self):
        for i, head in enumerate(self.table):
            chain = []
            node  = head
            while node:
                chain.append(str(node))
                node = node.next
            arrow_chain = " → ".join(chain) if chain else "None"
            print(f"  [{i}] → {arrow_chain}")


# --- Run it ---
ht = HashTableChaining(size=7)

ht.insert("Alice",   "555-1234")
ht.insert("Bob",     "555-5678")
ht.insert("Charlie", "555-9999")
ht.insert("Dave",    "555-0001")
ht.insert("Eve",     "555-4321")

print("=== Table State ===")
ht.display()

print("\nSearch 'Charlie':", ht.search("Charlie"))
print("Search 'Zara':",    ht.search("Zara"))

ht.delete("Charlie")
print("\n=== After Deleting 'Charlie' ===")
ht.display()
```

**Example Output:**
```
=== Table State ===
  [0] → None
  [1] → ('Eve': '555-4321') → None
  [2] → ('Bob': '555-5678') → None
  [3] → ('Charlie': '555-9999') → ('Alice': '555-1234') → None
  [4] → ('Dave': '555-0001') → None
  [5] → None
  [6] → None

Search 'Charlie': 555-9999
Search 'Zara':    None

=== After Deleting 'Charlie' ===
  [3] → ('Alice': '555-1234') → None
```

Index 3 had a chain of two. After deleting "Charlie", Alice remains untouched. The pointer redirect takes care of everything.

## Visualising What Happens in Memory

This is what chaining looks like in memory — contrast it with a plain array:

```
Plain Array (no collision handling):
┌─────────┬──────────┬──────────┬──────────┐
│  idx 0  │  idx 1   │  idx 2   │  idx 3   │
│  "cat"  │   ???    │  "bird"  │  "fish"  │   ← "dog" can't fit — no room!
└─────────┴──────────┴──────────┴──────────┘

Hash Table with Chaining:
┌─────────┐
│  idx 0  │ → None
├─────────┤
│  idx 1  │ → [key="cat", val=1] → [key="dog", val=2] → None
├─────────┤                             ↑ collision solved — both coexist
│  idx 2  │ → [key="bird", val=3] → None
├─────────┤
│  idx 3  │ → [key="fish", val=4] → None
└─────────┘
```

The array slots don't hold the data directly — they hold the **heads of linked lists**. The Nodes live elsewhere in memory, chained together by their `.next` pointers.

## Time Complexity — How Fast Is This?

Let `n` = total number of entries, `m` = number of slots in the array.

Define **load factor** α = n / m — the average number of entries per bucket.

| Operation | Average Case | Worst Case |
|-----------|-------------|------------|
| Insert    | O(1)        | O(1) (prepend at head) |
| Search    | O(1 + α)    | O(n) |
| Delete    | O(1 + α)    | O(n) |

- **Average case** assumes keys spread evenly across buckets (good hash function).
- **O(1 + α)**: the `1` is for hashing, the `α` is for traversing the average-length chain.
- **Worst case** O(n): all `n` keys hash to the same index — a single chain of length `n`. This should not happen with a well-chosen hash function.

**The practical takeaway:** as long as α stays small (below 1.0), every operation is effectively O(1).

---

## The Load Factor — Your Performance Dial

The **load factor** α = n / m is the single dial that controls performance.

```
α = 3 / 7 ≈ 0.43    → excellent — short chains, fast lookups
α = 7 / 7 = 1.00    → good — average chain length ≈ 1
α = 14 / 7 = 2.00   → degrading — chains growing to length 2–4
α = 70 / 7 = 10.0   → terrible — effectively a linear search
```

### Resizing the Table

When α exceeds a threshold (commonly 0.75), the table **resizes itself**:

1. Allocate a new array, typically double the size.
2. Re-hash every existing `(key, value)` pair into the new array.
3. The chains in the new, larger array are shorter — performance is restored.

```python
    def _resize(self):
        old_table  = self.table
        self.size  = self.size * 2       # Double the size
        self.table = [None] * self.size  # Fresh empty array
        # Re-insert every entry from the old table
        for head in old_table:
            node = head
            while node is not None:
                self.insert(node.key, node.value)
                node = node.next
```

Resizing costs O(n) — but it happens rarely. The amortized cost per insertion remains O(1).

## Common Mistakes Beginners Make

### Mistake 1 — Forgetting to Check the Key Inside the Chain

```python
# WRONG — only checks the index, not the key
def bad_search(table, key):
    index = hash(key) % len(table)
    if table[index] is not None:
        return table[index].value   # ← returns whatever is at the head!
                                    # Could be a completely different key!

# CORRECT — walk the chain and match the key
def good_search(table, key):
    index   = hash(key) % len(table)
    current = table[index]
    while current:
        if current.key == key:      # ← must verify the key
            return current.value
        current = current.next
    return None
```

Two different keys can share an index. The index gets you to the right **bucket**. The key comparison gets you to the right **entry**.

---

### Mistake 2 — Inserting Duplicates Without Checking

```python
ht.insert("Alice", "555-1234")
ht.insert("Alice", "555-9999")   # ← Should UPDATE, not create a second node!
```

Without a duplicate check, you end up with two Nodes carrying `key="Alice"` in the same chain. Searching will always find the first one and never see the updated value.

**Fix:** Before prepending, walk the chain and update if the key already exists.

```python
    def insert(self, key, value):
        index   = self._hash(key)
        current = self.table[index]
        # Check if key already exists — update in place
        while current:
            if current.key == key:
                current.value = value   # Update, don't duplicate
                return
            current = current.next
        # Key not found — prepend a new node
        new_node       = Node(key, value)
        new_node.next  = self.table[index]
        self.table[index] = new_node
```

---

### Mistake 3 — Confusing the Index with the Key

```python
# WRONG mental model:
# "If table[3] has a node, the key must be 3."

# CORRECT mental model:
# "table[3] is a bucket. Any key whose hash % size == 3 lives here.
#  The actual key is stored inside the node's .key attribute."
```

The index is just a **routing address** to the right bucket. The key is the real identifier, stored inside the Node.

---

### Mistake 4 — Allowing the Load Factor to Grow Unchecked

```python
# This table will degrade to O(n) per operation if you never resize it
ht = HashTableChaining(size=7)

for i in range(10000):
    ht.insert(f"user_{i}", i)   # α = 10000 / 7 ≈ 1428 — catastrophic performance
```

Always track the number of entries and resize when α exceeds your threshold.

## Why This Works — The Deeper Insight

In the Node topic, we saw that a linked list can be stored in **non-contiguous memory** — each node can sit anywhere on the heap, connected only by pointers.

Chaining exploits this exact property.

The hash table's array must be contiguous (that's what gives you O(1) index access). But once you're at the right bucket, you *don't need contiguous memory anymore*. The chain of Nodes that handles the collision can scatter freely across the heap.

```
Contiguous (the array — fast O(1) access by index):
┌────┬────┬────┬────┬────┬────┬────┐
│ *  │ *  │None│ *  │None│ *  │None│    * = pointer to a Node
└─┼──┴─┼──┴────┴─┼──┴────┴─┼──┴────┘
  │    │          │          │
  ↓    ↓          ↓          ↓
Non-contiguous (the chains — flexible, dynamic):
[Node]→[Node]  [Node]  [Node]→[Node]→[Node]  [Node]
```

You get the best of both worlds:
- The **array** for instant O(1) bucket lookup.
- The **linked list** for flexible, collision-safe storage within each bucket.

## Chaining vs. Open Addressing — The Big Picture

Chaining is one approach to collision resolution. The other major family is **open addressing** (linear probing, quadratic probing, double hashing) — when a collision occurs, find the next available slot inside the same array.

| Aspect               | Chaining (this topic)             | Open Addressing               |
|----------------------|-----------------------------------|-------------------------------|
| Where extra entries go | External linked list            | Inside the array itself       |
| Load factor limit    | Can exceed 1.0                    | Must stay below 1.0           |
| Deletion             | Simple — unlink the node          | Complex — needs a tombstone marker |
| Memory per entry     | Extra `.next` pointer per node    | No extra pointers             |
| Cache performance    | Slower — pointer chasing          | Faster — all data in the array |
| Implementation ease  | Simple                            | Moderate                      |

Neither is universally better. Chaining is simpler, more forgiving of high load, and easier to delete from. Open addressing is more cache-friendly and memory-compact.

## Where You'll See This in Real Life

Chaining is not a textbook curiosity — it is production code in systems you use daily:

- **Java `HashMap`** — Uses an array of linked list chains. Since Java 8, when a chain grows beyond 8 nodes, Java automatically converts that chain to a Red-Black Tree for O(log n) worst-case instead of O(n). When it shrinks back below 6, it reverts to a linked list.

- **Python `dict` (older CPython)** — Earlier versions of CPython used separate chaining internally. Modern versions use open addressing with a highly optimised compact table, but the concept is the same.

- **Linux Kernel** — The Linux kernel's internal hash tables use `hlist` — a memory-optimised doubly-linked list variant — for structures like the inode cache (indexing open files by ID).

- **Compiler symbol tables** — When a compiler processes your code, it stores variable names and function names in a hash table. Chaining handles the inevitable hash collisions between different identifiers.

- **Database hash indexes** — PostgreSQL's hash indexes use bucket-based chaining to handle collisions in indexed column values.

## Summary

| Concept | What It Means |
|---|---|
| Collision | Two different keys hash to the same array index |
| Chaining | Each array slot holds the head of a linked list |
| Node in chaining | Stores `key`, `value`, and `next` pointer |
| Insert | Hash → prepend new Node at bucket head → O(1) |
| Search | Hash → traverse chain, match by `key` → O(1 + α) average |
| Delete | Hash → traverse chain, unlink matching Node → O(1 + α) average |
| Load factor α | n / m — the average chain length; keep it below 0.75 |
| Resize | When α is too high, double the array and re-hash all entries |
