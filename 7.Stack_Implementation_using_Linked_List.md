# Stack — Linked List Implementation

---

## The Limit of the Array Approach

In the previous topic, we built a stack using Python's built-in list. Push was O(1) amortised. Pop was O(1). The implementation was concise and practical. For the majority of use cases, it is the right choice.

But it rests on one hidden assumption: **memory is reserved in advance, even for elements that have not yet arrived**.

A Python list maintains an internal array. When that array fills up, Python allocates a new one roughly twice the size and copies every existing element into it. This keeps the amortised cost low, but at any given moment the list may hold twice as much memory as the number of elements actually requires. There is no way to know, from the outside, how much is reserved versus how much is used.

More critically, there is no way to enforce an exact memory budget. You either accept the overhead or write additional logic to manage it yourself.

The linked list takes a different position. **Memory is requested exactly once per element, at the moment it is pushed. It is released exactly once per element, at the moment it is popped.** The stack's memory footprint at any instant is proportional to exactly the number of elements it currently holds — no more, no less.

This is the case for a linked-list-backed stack: no pre-allocation, no resize events, no wasted capacity.

---

## Rethinking the Stack as a Chain

In the list-based stack, elements occupy consecutive positions in an array. The top of the stack is tracked by an index.

In a linked stack, elements are **individual nodes scattered in memory**, each connected to the one below it by a pointer. The top of the stack is tracked by a reference to the topmost node.

```
List-based stack:               Linked-list-based stack:

Index:  0    1    2             Nodes linked by pointers:
      ┌────┬────┬────┐
      │ 10 │ 20 │ 30 │          top
      └────┴────┴────┘           │
                  ▲              ▼
                 top         ┌──────────┐
                             │ 30 │  ───┼►    ┌──────────┐
                             └──────────┘     │ 20 │   ──┼──►  ┌──────────┐
                                              └──────────┘     │ 10 │None │
                                                               └──────────┘
```

Both represent the same stack — 10 at the bottom, 30 at the top. The difference is purely structural: one uses an index into a contiguous block, the other uses a pointer into a chain of nodes.

The key insight is that **only the head of the linked list matters**. Every push adds a node at the front. Every pop removes a node from the front. The tail is never touched.

---

## The Node

Each element in the stack lives in a node with two fields.

```python
class Node:
    def __init__(self, data):
        self.data = data    # The value stored at this position
        self.next = None    # Reference to the node beneath this one in the stack
```

The `next` field points **downward** in the stack — toward the bottom, toward older elements. The most recently pushed node's `next` points to the second-most recently pushed node, and so on.

---

## The Stack Class

```python
class Stack:
    def __init__(self):
        self.top = None   # Points to the topmost node; None means empty
        self._size = 0    # Maintained explicitly to keep len() at O(1)
```

That is the entire state. One reference and one counter. No array. No capacity. No index.

---

## Push — Inserting at the Front

Pushing is prepending a node to the linked chain.

```python
def push(self, data):
    """Add an element to the top of the stack. O(1)."""
    node = Node(data)       # Step 1: Allocate a new node
    node.next = self.top    # Step 2: Link it to the current top
    self.top = node         # Step 3: The new node becomes the top
    self._size += 1
```

**Trace through push(30) onto a stack already holding [10, 20]:**

```
Step 1 — Create the new node:

    new_node: [30 │ None]

Step 2 — Point new_node.next at the current top:

    new_node: [30 │ ──►] ──► [20 │ ──►] ──► [10 │ None]
                              ▲
                             top  (still pointing to 20)

Step 3 — Move top to the new node:

    top
     │
     ▼
    [30 │ ──►] ──► [20 │ ──►] ──► [10 │ None]
```

Three operations. No traversal. No reallocation. **Time: O(1) — always**, not amortised.

---

## Pop — Removing from the Front

Popping is detaching the head node and returning its value.

```python
def pop(self):
    """Remove and return the top element. Raises IndexError if empty. O(1)."""
    if self.is_empty():
        raise IndexError("pop from an empty stack")
    data = self.top.data        # Step 1: Save the value
    self.top = self.top.next    # Step 2: Move top down to the next node
    self._size -= 1
    return data                 # Step 3: Return the saved value
```

**Trace through pop() on a stack holding [10, 20, 30]:**

```
Step 1 — Save the value at top:

    saved = 30

    top
     │
     ▼
    [30 │ ──►] ──► [20 │ ──►] ──► [10 │ None]

Step 2 — Advance top to top.next:

                   top
                    │
                    ▼
    [30 │ ──►] ──► [20 │ ──►] ──► [10 │ None]
     ▲
     └── No references remain. Garbage collected.

Step 3 — Return 30.
```

The popped node is immediately eligible for garbage collection because nothing references it anymore. There is no deferred cleanup, no tombstone, no resize needed. **Time: O(1).**

---

## Peek — Reading the Top

```python
def peek(self):
    """Return the top element without removing it. Raises IndexError if empty. O(1)."""
    if self.is_empty():
        raise IndexError("peek from an empty stack")
    return self.top.data
```

`top.data` is directly accessible. No traversal. **Time: O(1).**

---

## Supporting Methods

```python
def is_empty(self):
    """Return True if the stack has no elements. O(1)."""
    return self.top is None

def __len__(self):
    """Return the number of elements in the stack. O(1)."""
    return self._size

def __repr__(self):
    """Return a readable string showing the stack from top to bottom. O(n)."""
    elements = []
    current = self.top
    while current is not None:
        elements.append(repr(current.data))
        current = current.next
    return "Stack(top → bottom): [" + ", ".join(elements) + "]"
```

`__len__` is O(1) because `_size` is kept current by push and pop. If you omitted `_size` and traversed the chain every time, `len()` would be O(n) — an unnecessary cost for such a routine query.

## Complete Implementation

```python
class Node:
    def __init__(self, data):
        self.data = data
        self.next = None


class Stack:
    def __init__(self):
        self.top = None
        self._size = 0

    def push(self, data):
        """Add an element to the top. O(1)."""
        node = Node(data)
        node.next = self.top
        self.top = node
        self._size += 1

    def pop(self):
        """Remove and return the top element. O(1)."""
        if self.is_empty():
            raise IndexError("pop from an empty stack")
        data = self.top.data
        self.top = self.top.next
        self._size -= 1
        return data

    def peek(self):
        """Return the top element without removing it. O(1)."""
        if self.is_empty():
            raise IndexError("peek from an empty stack")
        return self.top.data

    def is_empty(self):
        """Return True if the stack contains no elements. O(1)."""
        return self.top is None

    def __len__(self):
        """Return the number of elements. O(1)."""
        return self._size

    def __repr__(self):
        """Display the stack from top to bottom. O(n)."""
        elements = []
        current = self.top
        while current is not None:
            elements.append(repr(current.data))
            current = current.next
        return "Stack(top → bottom): [" + ", ".join(elements) + "]"
```

## Walkthrough

```python
s = Stack()
print(s.is_empty())    # True

s.push(10)
s.push(20)
s.push(30)

print(s)               # Stack(top → bottom): [30, 20, 10]
print(len(s))          # 3
print(s.peek())        # 30  — top is unchanged

print(s.pop())         # 30
print(s.pop())         # 20
print(s)               # Stack(top → bottom): [10]
print(len(s))          # 1

print(s.pop())         # 10
print(s.is_empty())    # True

try:
    s.pop()            # Raises IndexError
except IndexError as e:
    print(e)           # pop from an empty stack
```

## Practical Patterns

### Pattern 1 — Balanced Bracket Checking

Every opening bracket must be matched by a corresponding closing bracket in the correct order. The most recently opened bracket must be the next one closed — a LIFO requirement.

```python
def is_balanced(expression):
    s = Stack()
    matching = {')': '(', ']': '[', '}': '{'}

    for char in expression:
        if char in '([{':
            s.push(char)
        elif char in ')]}':
            if s.is_empty() or s.pop() != matching[char]:
                return False

    return s.is_empty()    # Stack must be empty — every open was closed


print(is_balanced("({[]})"))      # True
print(is_balanced("({[})"))       # False  — wrong closing order
print(is_balanced("((())"))       # False  — unclosed bracket
print(is_balanced(""))            # True   — empty is valid
```

---

### Pattern 2 — Reversing a Sequence

LIFO naturally reverses the order of arrival. Push every element; pop them all back. The first pushed is the last popped.

```python
def reverse_words(sentence):
    s = Stack()
    for word in sentence.split():
        s.push(word)

    result = []
    while not s.is_empty():
        result.append(s.pop())

    return " ".join(result)


print(reverse_words("the quick brown fox"))
# "fox brown quick the"
```

---

### Pattern 3 — Undo and Redo

A classic two-stack problem. Actions are pushed onto the undo stack. Undoing pops from the undo stack and pushes onto the redo stack. Redoing reverses the direction.

```python
class Document:
    def __init__(self):
        self.content = ""
        self._undo_stack = Stack()
        self._redo_stack = Stack()

    def type(self, text):
        self._undo_stack.push(("type", text))
        self._redo_stack = Stack()    # Any new action clears the redo history
        self.content += text

    def undo(self):
        if self._undo_stack.is_empty():
            return
        action, text = self._undo_stack.pop()
        if action == "type":
            self.content = self.content[: -len(text)]
            self._redo_stack.push(("type", text))

    def redo(self):
        if self._redo_stack.is_empty():
            return
        action, text = self._redo_stack.pop()
        if action == "type":
            self.content += text
            self._undo_stack.push(("type", text))

    def __repr__(self):
        return f'Content: "{self.content}"'


doc = Document()
doc.type("Hello")
doc.type(", world")
print(doc)        # Content: "Hello, world"

doc.undo()
print(doc)        # Content: "Hello"

doc.redo()
print(doc)        # Content: "Hello, world"
```

### Pattern 4 — Iterative Depth-First Search

Recursive DFS uses the call stack implicitly. By managing an explicit stack, you gain full control — useful when the graph is deep enough to risk a recursion limit.

```python
def dfs(graph, start):
    """Iterative DFS using an explicit stack."""
    s = Stack()
    visited = set()

    s.push(start)

    order = []
    while not s.is_empty():
        vertex = s.pop()
        if vertex in visited:
            continue
        visited.add(vertex)
        order.append(vertex)
        for neighbour in graph[vertex]:    # Push neighbours to explore later
            if neighbour not in visited:
                s.push(neighbour)

    return order


graph = {
    "A": ["B", "C"],
    "B": ["A", "D", "E"],
    "C": ["A", "F"],
    "D": ["B"],
    "E": ["B"],
    "F": ["C"],
}

print(dfs(graph, "A"))    # ['A', 'C', 'F', 'B', 'E', 'D']  (one valid DFS order)
```

The stack holds vertices to be explored. Each vertex is only processed once, checked against the `visited` set.

### Pattern 5 — Postfix Expression Evaluation

Postfix notation places operators after their operands, eliminating the need for parentheses. Evaluation scans left to right: push operands, apply operators to the top two values.

```python
def evaluate_postfix(expr):
    s = Stack()
    operators = {
        '+': lambda a, b: a + b,
        '-': lambda a, b: a - b,
        '*': lambda a, b: a * b,
        '/': lambda a, b: int(a / b),
        '**': lambda a, b: a ** b,
    }

    for token in expr.split():
        if token in operators:
            b = s.pop()              # Right operand — popped first
            a = s.pop()              # Left operand — popped second
            s.push(operators[token](a, b))
        else:
            s.push(int(token))

    return s.pop()


print(evaluate_postfix("3 4 + 2 *"))          # (3 + 4) * 2 = 14
print(evaluate_postfix("5 1 2 + 4 * + 3 -"))  # 5 + ((1+2)*4) - 3 = 14
print(evaluate_postfix("2 3 ** 1 +"))          # 2**3 + 1 = 9
```

Order of popping matters. The second pop gives the left operand because it was pushed earlier. Reversing them gives wrong results for non-commutative operations like subtraction and division.

## Linked List Stack vs List-Based Stack

| Property | List-based (`list`) | Linked List (`Node` chain) |
|---|---|---|
| Push | O(1) amortised | O(1) always |
| Pop | O(1) | O(1) |
| Peek | O(1) | O(1) |
| Memory per push | Amortised low — array pre-allocated | One `Node` object per element |
| Resize events | Yes — doubles when full | Never |
| Memory released on pop | No — array slot remains allocated | Yes — node is immediately freed |
| Unused capacity | Up to 50% of internal array | None |
| Index access | O(1) | Not applicable |
| Practical default in Python | Preferred | Teaching and custom structures |

**Choose the linked list stack when:**
- Memory must be reclaimed immediately on pop.
- The stack depth is highly variable and you want no amortised overhead.
- You are building a custom data structure that embeds a stack internally.

**Choose the list-based stack when:**
- You are writing production Python code and simplicity matters.
- Push/pop frequency is high — the list is more cache-friendly due to contiguous storage.
- You want the standard library's optimised internals without maintenance overhead.

## Common Mistakes

### Mistake 1 — Forgetting to Update `top` on Push

```python
# Wrong — top is never moved forward
def push(self, data):
    node = Node(data)
    node.next = self.top
    # Missing: self.top = node
```

After this, `top` still points to the old node. Every push creates a node that is immediately orphaned. Every pop returns the same stale element.

---

### Mistake 2 — Popping Without an Empty Check

```python
s = Stack()
s.push(1)
s.pop()
s.pop()    # IndexError — stack is empty
```

Always guard with `is_empty()` or handle the exception explicitly.

```python
if not s.is_empty():
    value = s.pop()
```

---

### Mistake 3 — Wrong Operand Order in Binary Operations

When popping two values for a binary operator, the **first pop is the right operand** because it was pushed last.

```python
s.push(10)
s.push(3)

b = s.pop()    # 3  — pushed last, so it is the right operand
a = s.pop()    # 10 — pushed first, so it is the left operand

result = a - b    # 10 - 3 = 7   ✓
# Not: b - a     # 3 - 10 = -7  ✗
```

---

### Mistake 4 — Computing Size by Traversal

```python
# Avoid — O(n) every call
def __len__(self):
    count = 0
    node = self.top
    while node:
        count += 1
        node = node.next
    return count
```

Maintain a `_size` counter instead. Increment it in `push`, decrement in `pop`. Length becomes O(1) with no traversal cost.

---

### Mistake 5 — Losing the Chain During Push

```python
# Wrong — chain is broken
def push(self, data):
    self.top = Node(data)    # top reassigned before next pointer is set
    self.top.next = ???      # old top is already gone
```

Always set `node.next = self.top` **before** updating `self.top`. The order matters.

## Where This Pattern Appears

**Language Runtimes**

Every function call pushes a frame onto the call stack — a linked structure of activation records. Each frame holds local variables, parameters, and the return address. Returning from a function pops its frame. When a recursive function runs too deep, the chain of frames exhausts the allocated memory, producing a stack overflow.

**Expression Parsing**

Compilers and interpreters convert infix expressions to postfix using a stack. Operator precedence, associativity, and parentheses are resolved entirely through push and pop operations on an operator stack. The same mechanism drives syntax tree construction.

**Browser Navigation**

The back-history of a browser is a stack. Each visit pushes the current URL. Pressing Back pops it. Navigating to a new page from the middle discards everything above the current position — the same behaviour as clearing a stack down to a checkpoint.

**Iterative Tree and Graph Traversal**

Recursive traversal of trees and graphs uses the call stack implicitly. Replacing recursion with an explicit stack makes the depth visible, controllable, and immune to language recursion limits. Every DFS implementation, whether on a tree or a graph, corresponds directly to a push/pop cycle on a stack of unvisited nodes.

## Summary

| Concept | What It Means |
|---|---|
| LIFO | Last In, First Out — the defining rule of a stack |
| `top` pointer | Always references the most recently pushed node |
| Push | New node; set `next` to current `top`; move `top` to new node |
| Pop | Save `top.data`; advance `top` to `top.next`; return saved value |
| Peek | Read `top.data` — structure is unchanged |
| Node freed on pop | No deferred cleanup; memory returns at the exact moment of removal |
| All core operations | O(1) — no traversal, no reallocation |

The linked list stack is the most direct translation of the abstract stack concept into a data structure. One pointer, one counter, one node per element. No capacity, no index, no array. Just a chain that grows at the front and shrinks from the front — precisely as much as the current workload demands.
